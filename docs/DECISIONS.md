# AutoCue — Architecture Decision Records

The record of *why* — not every commit, only real architectural calls: a real trade-off, a library choice, a reversed earlier decision, something a later session might reasonably second-guess without this context. `CLAUDE.md` says *how* to build; `SPEC.md` says *what* to build; this file says *why* it's built that way instead of some other way that was genuinely considered.

Every entry uses the same five fields:

- **Decision** — the call, stated plainly.
- **Context** — what was true at the time that made this a real question, not a formality.
- **Alternatives Considered** — what else was genuinely on the table, including an option later reversed elsewhere in this log — reversals are recorded as new entries that reference the old one, never by silently editing the old entry.
- **Reason for Choice** — why this one, specifically, over the alternatives.
- **Consequences** — what this rules out, what it commits future work to, and any residual gap it doesn't close.

Entries are chronological, oldest first. `CONTRIBUTING.md` §2 and `docs/DefinitionOfDone.md` §4 both point back here for when a change needs an entry.

## 2026-08-08 — Rename `Duration` to `MediaDuration`

**Decision:** The domain's length-of-time value type is `MediaDuration`, not the originally-planned `Duration`.

**Context:** `SPEC.md`'s original schema draft named this type `Duration`. Swift's standard library ships its own `Duration` type (`Swift.Duration`), used throughout Swift Concurrency (`ContinuousClock`, `Task.sleep(for:)`) and implicitly in scope in virtually any file touching `async`/`await` timing — which is most of this codebase, given `CLAUDE.md`'s concurrency-everywhere stance.

**Alternatives Considered:**
- **Keep `Duration` and rely on module-qualification (`Swift.Duration` vs. `ACCore.Duration`) to disambiguate.** Rejected — this pushes a landmine into every future file that imports both `ACCore` and touches Concurrency APIs, rather than removing it once, before any code exists.
- **`CueDuration`.** Rejected — the type isn't cue-specific; it's also used for `Setup.productionRuntime` and `Setup.totalMusicRuntime`, neither of which is a cue.
- **`MediaDuration`.** Chosen.

**Reason for Choice:** `MediaDuration` names what the type actually represents (a length of media time) without colliding with anything in Foundation or the standard library, and without being falsely scoped to just one use site the way `CueDuration` would be.

**Consequences:** Every `SPEC.md`/`CLAUDE.md` reference to the original name was updated in the same change (`SPEC.md` §4.8 is the type's full specification). No code existed yet when this was made, so there was no retrofit cost — this is the cheapest possible time to make this call, which is exactly why it was made immediately rather than deferred.

**Full detail:** `SPEC.md` §4.8.

## 2026-08-08 — Module dependency graph: `ACFeatures` as its own package, with an explicit limitation noted

**Decision:** `Features/` is not app-target code. It is its own local Swift package, `ACFeatures`, depending only on `ACCore` and `ACDesignSystem` — never on `ACAudioKit`, `ACExport`, or `ACPersistence`. Separately: the Technology Stack table's claim that module boundaries are "compiler-enforced" is corrected to state precisely what SPM does and doesn't gate.

**Context:** The original plan kept `Features/` inside the `AutoCue` app target directly, and the original tech-stack table described the whole modularization scheme as giving "compiler-enforced module boundaries, not just folder convention." Both were reviewed together because they're the same underlying issue: the app target legitimately links `SwiftData`/`AVFoundation` for `DependencyContainer`, so nothing would have stopped a screen living in that target from importing them directly too — the "ViewModels never touch the Data layer" rule would have been convention-enforced only, on exactly the layer most likely to accumulate violations across dozens of independently-built Feature milestones, while the docs claimed a stronger guarantee than actually existed.

**Alternatives Considered:**
- **Leave `Features/` in the app target, rely on code review to catch violations.** Rejected — this is precisely the "convention-enforced, not compiler-enforced" gap the review flagged; review discipline erodes over a multi-year, multi-session project, which is the whole premise this document series exists to guard against.
- **Split `Features/` into its own package** *(chosen)*.
- **Leave the "compiler-enforced" claim as-is, since SPM does enforce cross-package boundaries.** Rejected as incomplete — SPM enforces cross-*package* boundaries but not system-framework imports *within* a package (nothing stops `import SwiftData` from compiling inside an `ACCore` file); stating "compiler-enforced" without that caveat is a claim the architecture doesn't actually back up.

**Reason for Choice:** Making `ACFeatures` a real package with a restricted `Package.swift` dependency list turns "ViewModels can't reach `ACAudioKit`/`ACExport`/`ACPersistence`" into a genuine compile error instead of a code-review miss — a real, load-bearing guarantee where one was previously only claimed. This was the right call to make immediately, before any Feature code exists — cheap now, expensive as a retrofit once 10+ milestones' worth of Views already assume app-target placement.

**Consequences:** Rules out Feature Views/ViewModels ever depending on a Data-layer package or `DependencyContainer` directly (`CLAUDE.md`, "Dependency Injection Pattern"). Does **not** fully rule out raw `import SwiftData`/`AVFoundation` inside an `ACFeatures` file — SPM genuinely cannot gate that regardless of package layout (`CLAUDE.md`, "Package Dependency Graph" limitation note). That residual gap is what `Scripts/check-import-boundaries.sh` (see the CI entry, below) exists to close mechanically, rather than leaving it convention-only forever.

**Full detail:** `CLAUDE.md` (Package Dependency Graph, Dependency Injection Pattern, Folder/Package Structure).

## 2026-08-08 — Views never use `@Query`; `ProjectRepository` exposes a live `AsyncStream` instead

**Decision:** Views never import `SwiftData` and never use `@Query`. `ProjectRepository` exposes a live-observation API (`observeAll() -> AsyncStream<[Project]>` or equivalent) alongside one-shot CRUD; a ViewModel subscribes via a wrapping Use Case and republishes into an `@Observable` property the View binds to.

**Context:** An earlier draft of `CLAUDE.md` contained a direct, internal contradiction: one section said "Views never talk to Repositories or Use Cases directly — only to their ViewModel," while the "Single Source of Truth" section said list views "should read live via `@Query` where practical." `@Query` binds directly to `@Model` (SwiftData) entity types — using it from a View means that View depends on a Data-layer persistence-schema type directly, which the first rule explicitly forbids. The two statements couldn't both hold.

**Alternatives Considered:**
- **Keep `@Query`, drop the "Views never talk to Repositories" rule for list views as a carved-out exception.** Rejected — this reopens exactly the boundary `ACFeatures`'s package split (see above) was built to close; a View importing `SwiftData` is a Data-layer dependency by definition, regardless of how convenient `@Query`'s live-update behavior is.
- **Repository-owned `AsyncStream` of domain models** *(chosen)*.

**Reason for Choice:** This keeps the live-update behavior `@Query` was being reached for (no manual refresh needed after create/delete) while keeping the dependency direction intact: `ACCore` still never imports `ACPersistence`, and a View only ever sees domain models via its ViewModel, never a SwiftData entity type. The mechanism SwiftData-sourced data reaches a screen through is the Repository *protocol* (owned by `ACCore`, implemented by `ACPersistence`) being injected — not a hard import.

**Consequences:** Every mutating `ProjectRepository` method must republish the fresh result into the shared stream — a repository implementation that forgets this silently breaks live-updating UI. Establishes the pattern for any future list-style live-updating view: wrap the stream in a small Use Case (e.g. `ObserveProjectsUseCase`), never reach for `@Query` as a shortcut.

**Full detail:** `CLAUDE.md`, "Single Source of Truth."

## 2026-08-08 — Support drop-frame timecode from v1, not deferred

**Decision:** `TimecodeFrameRate` distinguishes `.fps29_97NonDrop` and `.fps29_97Drop` as of the first implementation of `Timecode`, with real SMPTE drop-frame arithmetic (not a stub), rather than shipping non-drop-only and adding drop-frame later.

**Context:** An earlier revision of `SPEC.md` §4.9 explicitly deferred drop-frame as an out-of-scope "known gap" for v1, reasoning from `CLAUDE.md` rule 7 (no premature abstraction). `Timecode`/`TimecodeFrameRate` are foundational value types that `Cue.startTimecode`, `EmbeddedMarker.position`, and the entire editor UI's position-display logic depend on directly.

**Alternatives Considered:**
- **Ship non-drop-only, add drop-frame later if a real production needs it** *(the original plan)*. Rejected on reconsideration — cue sheets built from NTSC-derived material (29.97fps) are a realistic, known case for this app's actual domain, not a speculative one; rule 7 exists to prevent generalizing for a use case that *might never arrive*, and this one isn't that.
- **Build both modes now** *(chosen)*.

**Reason for Choice:** The retrofit cost is asymmetric in a way rule 7's usual reasoning doesn't capture: adding a second timecode "mode" after dozens of call sites already assume non-drop-only formatting math is a much larger, more error-prone change than getting the enum shape and conversion algorithm right once, before anything depends on it. This is the inverse of rule 7's typical case, not an exception to it.

**Consequences:** Rules out a future migration/schema change to `TimecodeFrameRate` solely to add drop-frame support once real cue data already references the non-drop-only version. Drop-frame arithmetic (the every-10th-minute exception, the classic bug in naive implementations) is implemented and verified now: 18 tests including a round-trip sweep across a 3-hour-equivalent frame range, `Packages/ACCore/Tests/ACCoreTests/TimecodeTests.swift`.

**Full detail:** `SPEC.md` §4.9. Implementation: `Packages/ACCore/Sources/ACCore/Models/{Timecode,TimecodeFrameRate}.swift`.

## 2026-08-08 — Waveform data: bounded overview + on-demand detail, not a full mip-map

**Decision:** `WaveformPeaks` (`ACCore`) is a fixed-resolution (4096-bucket), mono, persisted summary of the whole file, generated once at import. Zoomed-in detail views compute peaks on demand for just the visible range, uncached. No multi-resolution mip-map pyramid is built.

**Context:** `ACDesignSystem/Components/WaveformView` was named in `CLAUDE.md`'s folder structure from the project's very first commit, but no data model or generation pipeline for it existed anywhere — a real, structural gap between what the architecture named and what it actually specified.

**Alternatives Considered:**
- **A raw/downsampled sample buffer added to `AudioAsset`.** Rejected outright — `AudioAsset` has an explicit invariant (never holds raw or downsampled sample data) established specifically to keep it a small, always-in-memory-safe metadata type regardless of source file size; adding waveform data there would break that invariant for every consumer of `AudioAsset`, not just the ones that need waveform display.
- **A full multi-resolution mip-map**, as some professional DAWs build. Rejected as more machinery than this app's actual workflow needs — AutoCue is for confirming/adjusting cue boundaries, not sample-accurate waveform editing.
- **Fixed bounded overview + uncached on-demand detail** *(chosen)*.

**Reason for Choice:** A fixed bucket count (4096) keeps the persisted overview's memory cost constant (~32KB) regardless of whether the source file is 3 minutes or 3 hours — this is what lets `WaveformPeaks` exist as a plain, always-safe `ACCore` value type. The two-tier design (bounded overview, cheap uncached on-demand detail via the existing streaming reader) covers the real editing workflow without the added maintenance surface of a resolution pyramid built for a use case (sample-accurate waveform editing) this app doesn't have.

**Consequences:** `WaveformPeaks` lives as a sibling field on `Project`, never folded into `AudioAsset`. Mono mixdown only in v1 — no per-channel/stereo dual-trace representation, flagged as a real, plausible future enhancement, not designed here. `GenerateWaveformDetailUseCase` results are never cached across zoom interactions — deliberate, since the cost against a bounded time range is already negligible; revisit only if a real performance problem shows up, not preemptively.

**Full detail:** `SPEC.md` §4.15; consumption pattern: `CLAUDE.md`, Design System section (`WaveformDisplayData` adapter type).

## 2026-08-08 — Single progress/cancellation contract: `AsyncThrowingStream<OperationProgress<T>, Error>`, not Foundation `Progress`

**Decision:** Every long-running operation (WAV import, waveform generation, cue analysis, PDF/XLSX export) reports progress through one shared contract — `AsyncThrowingStream<OperationProgress<T>, Error>`, where `OperationProgress<T>` is `.progress(ProgressUpdate)` or `.completed(T)` — and cancellation is plain cooperative `Task` cancellation. Foundation's `Progress` class is not used anywhere in the app.

**Context:** `CLAUDE.md` previously referenced `AsyncStream` and Foundation's `Progress` side by side, in more than one section, as if they were interchangeable options for the same job. They aren't: `Progress` is a KVO-based Objective-C class with its own observation and cancellation model that doesn't compose with `async`/`await` — there's no way to `for await` over a `Progress`, and its cancellation tree is independent of Swift's structured-concurrency `Task` cancellation.

**Alternatives Considered:**
- **Foundation's `Progress`.** Rejected — its main real advantage is system-level UI integration (Dock icon, Finder progress, menu-bar activity), and nothing in `SPEC.md` currently asks for that; adopting it would mean carrying an incompatible concurrency model for a benefit the product doesn't use.
- **A bespoke progress enum/callback per operation, decided ad hoc per milestone.** Rejected — six different operations each inventing a slightly different shape is exactly the kind of drift `CONTRIBUTING.md` warns about, and provides no benefit over one shared contract.
- **`AsyncThrowingStream<OperationProgress<T>, Error>`, one contract for all six operations** *(chosen)*.

**Reason for Choice:** Native Swift Concurrency composes directly with everything else in this codebase (ViewModels are `@MainActor`, background work is `async`), and picking one contract before any of the six operations that need it are built prevents six independent inventions of the same idea.

**Consequences:** Rules out any future milestone introducing `Progress`, a bespoke per-operation progress enum, or a custom cancellation-token type. If system-level UI integration is ever genuinely wanted, `Progress` can be layered on top of the stream-based contract later without changing the contract itself — this decision doesn't foreclose that, it just declines to build it now for a need that doesn't exist yet.

**Full detail:** `CLAUDE.md`, "Long-Running Operations: Progress & Cancellation." Types: `SPEC.md` §4.17.

## 2026-08-08 — `libxlsxwriter` validated with a real spike, ahead of its originally-scheduled position

**Decision:** `ACExport` depends on `libxlsxwriter` as a normal remote SPM package (its own upstream `Package.swift`, pinned `from: "1.2.4"`). This dependency decision has been verified with a real, runnable smoke test — including genuine kernel-enforced App Sandbox verification — rather than left as an untested assumption inherited from `CLAUDE.md` rule 4 until the roadmap position that originally covered it.

**Context:** `CLAUDE.md` rule 4 requires checking App Sandbox compatibility, static-linkability, and maintenance status before adopting a third-party dependency. This was stated as a rule from the project's first commit but not actually exercised until deep into the original 34-milestone plan — 27 milestones of downstream export work would have been built assuming it holds, before it was ever compiled even once. That's backwards risk-ordering for the one third-party native dependency in the whole stack.

**Alternatives Considered:**
- **Trust the choice on paper, validate it when the roadmap reaches it.** Rejected — this is the exact pattern rule 4 exists to prevent, just deferred by roadmap position rather than skipped outright.
- **Validate immediately, ahead of schedule** *(chosen)*.

**Reason for Choice:** A real spike (`XLSXFeasibilitySpike` + `XLSXFeasibilitySpikeTests`) costs little and resolves the dependency question completely before anything downstream depends on the answer. Verified: builds and links as an SPM C target (system `zlib` only), targets macOS 14 cleanly, produces a genuine ZIP/OOXML workbook with correct cell contents.

**App Sandbox verification, specifically:** an initial `sandbox-exec`-based attempt was correctly reported as inconclusive rather than a pass — the tool doesn't function at all in the execution environment used (confirmed against a trivial control case, `/bin/echo`, which failed identically). That was superseded by a real test: the spike binary packaged into a minimal `.app` bundle, ad-hoc code-signed with the actual `com.apple.security.app-sandbox` entitlement, and run directly. A write to an unauthorized location (`~/Desktop`) was genuinely blocked by the kernel (`Operation not permitted`, surfaced as a normal error, not a crash); a write inside the app's own sandbox container succeeded with correct output.

**Consequences:** Rules out treating "we chose `libxlsxwriter` under rule 4" as sufficient justification without ever having compiled it, and rules out treating the inconclusive `sandbox-exec` attempt as evidence either way. **Residual gap, narrower than general sandbox compatibility:** the real app's `NSSavePanel`-granted write flow (dynamic, Powerbox-mediated access to a user-chosen destination) wasn't tested — only the baseline container-write case was. This is `ROADMAP.md` D15/T15.2's job, once the real app target and final entitlements exist — a small, low-risk confirmation, not a reopening of this decision.

**Full detail:** `CLAUDE.md`, "Export Architecture (PDF & XLSX)." Spike: `Packages/ACExport/Sources/ACExport/Spike/XLSXFeasibilitySpike.swift`; tests: `Packages/ACExport/Tests/ACExportTests/XLSXFeasibilitySpikeTests.swift`.

## 2026-08-08 — Minimum deployment target: macOS 14.0 (Sonoma)

**Decision:** AutoCue targets macOS 14.0 as its minimum supported version, pinned explicitly in every package's `Package.swift` and (once it exists) the App target.

**Context:** `@Observable` and `SwiftData` — both already-committed architectural choices, not proposals — require macOS 14+. No document ever actually stated a minimum deployment target; it was only ever implied by those two dependencies, which meant nothing enforced it and a stray newer-OS-only API could have been introduced without anyone noticing it silently raised the floor.

**Alternatives Considered:**
- **Target a newer macOS version** (e.g. the current release at time of writing) for access to newer APIs. Rejected — nothing in the current feature scope needs anything newer than macOS 14 offers, and a lower minimum means more of AutoCue's actual user base (video/audio post-production professionals, who don't always run the newest OS on a production machine) can run the app.
- **Leave it unstated/implicit**, as before. Rejected — this is exactly the kind of undocumented assumption that erodes over a multi-year, multi-session project.
- **macOS 14.0, the floor already required by `@Observable`/`SwiftData`** *(chosen)*.

**Reason for Choice:** macOS 14.0 isn't really a new choice being made here so much as the floor already implied by decisions already locked in — this decision's job is to make that floor explicit and enforced, not to pick a version for its own sake.

**Consequences:** Raising the floor later is cheap and reversible (loosen an availability check) the moment a real newer-OS-only API is needed. Lowering it is not possible without dropping `@Observable` or `SwiftData`, which would be a much larger reversal than this document anticipates.

**Full detail:** `CLAUDE.md`, "Deployment Target"; `SPEC.md` §0.

## 2026-08-08 — Navigation Model: three always-visible tabs (Setup / Cue Sheet / Review & Export), not a sheet-based flow

**Decision:** Each Project window shows exactly three co-equal, always-accessible navigation destinations — **Setup**, **Cue Sheet**, and **Review & Export** — in a 2-column `NavigationSplitView`. None is ever presented as a modal sheet. `Settings` is entirely outside this hierarchy, via SwiftUI's standard `Settings` scene.

**Context:** The original product brief specifies three tabs, always visible and accessible at any time, like browser tabs. `ROADMAP.md`'s original milestone plan (M11) only ever described a 2-column sidebar+detail shell with no explicit resolution of what the "more than two screens per project" (Setup, Cues, Review, Export) actually meant for navigation depth.

**Alternatives Considered:**
- **Four separate tabs** (Setup, Cue Sheet, Review, Export as independent destinations). Not pursued — the brief specifies three, and Export's readiness is derived from Review's validation state, so treating them as fully independent destinations doesn't reflect their actual relationship.
- **Export as a modal sheet triggered from Review**, reasoning that export is "a triggered action with a result," not a place to navigate to and stay. **This was actually built at one point**, then reversed — it directly contradicted the brief's explicit "three tabs, always visible" requirement, which was the actual, binding product specification and should have been checked against before this alternative was chosen.
- **Three tabs, Review and Export combined into one persistent destination** *(chosen, and what the brief specified from the start)*.

**Reason for Choice:** Matches the original product brief exactly. Independently, combining Review and Export is also the architecturally cleaner choice on its own merits: export readiness is *derived from* validation state (`Settings.shareValidationStrictness` gates export on the same issues Review surfaces), so the two were never fully independent concerns — one `ReviewAndExportViewModel` avoids two ViewModels coordinating shared state across a presentation boundary.

**Consequences:** Rules out any future work reintroducing a `.sheet()`-presented export flow, or treating Export as reachable only from within Review rather than as its own always-visible tab. `DependencyContainer.makeReviewAndExportViewModel(for:)` replaces what would otherwise have been two separate factory methods.

**Full detail:** `CLAUDE.md`, "Navigation Model." Affected: `ROADMAP.md` D11 (T11.1, T11.5).

## 2026-08-08 — Document & Window Model: multi-window (`WindowGroup(for: Project.ID.self)`), not single-window

**Decision:** AutoCue is multi-window: a singleton Library scene for browsing/creating/opening Projects, plus a `WindowGroup(for: Project.ID.self)` scene allowing any number of Project windows open simultaneously, each independently editing one `Project`. Duplicate opens of the same `Project` are prevented by an explicit app-wide `OpenProjectWindowRegistry` (focus the existing window instead of opening a second one). `ProjectRepositoryImpl` serializes writes per-`Project.ID`, not behind a single app-wide lock.

**Context:** AutoCue is a single-composer desktop tool — one person building one cue sheet at a time is the normal case — which made single-window a real, defensible option, not an obviously wrong one.

**Alternatives Considered:**
- **Single window, single active Project at a time.** **This was the original decision**, reasoned from "fewer, well-separated moving parts": a single window eliminates the same-project-open-twice and cross-window-save-race problems *by construction*, with no coordination logic needed, and was explicit about the resulting limitation (no side-by-side comparison of two Projects) rather than silently overlooking it. Reversed — not because this reasoning was wrong at the time, but because of an explicit product requirement discovered afterward: the ability to compare/reference two Projects side by side in separate windows, which single-window structurally precludes.
- **A literal `DocumentGroup`** (file-backed documents, `FileDocument`/`ReferenceFileDocument`). Considered when reversing single-window, and rejected — `DocumentGroup` presumes each document is a file the system's Open/Save panels manage directly, which doesn't match AutoCue's actual persistence model: `Project`s are rows in one shared SwiftData store behind `ProjectRepository`, an already-validated decision this reversal does not reopen. Adopting `DocumentGroup` would have meant either abandoning that persistence model or fighting the framework with a synthetic `FileDocument` that doesn't represent real storage.
- **`WindowGroup(for: Project.ID.self)`, multi-window over app-managed (non-file) data** *(chosen)*.

**Reason for Choice:** `WindowGroup(for: Project.ID.self)` gives the same user-facing outcome multi-window `DocumentGroup` apps offer (multiple windows, one data item each) without requiring a file-per-project persistence model this app doesn't have. Reversing single-window meant its two "solved by construction" problems had to be solved explicitly instead: same-project-open-twice is now prevented by `OpenProjectWindowRegistry`; cross-window save races are now prevented by scoping `ProjectRepositoryImpl`'s write serialization per-`Project.ID` rather than relying on there only ever being one Project loaded.

**Consequences:** Rules out a future milestone reintroducing a single global `AppState`/`selectedProjectID`, or a save-serialization scheme that isn't scoped per-`Project.ID`. `AppState` is now constructed once per Project window (holding only `selectedSection`), not once per app. The original single-window decision was written into `CLAUDE.md` directly at the time but never logged in this file — an omission corrected retroactively here, recording both the original reasoning and its reversal together rather than only the final state.

**Full detail:** `CLAUDE.md`, "Document & Window Model." Affected: `ROADMAP.md` D6.

## 2026-08-08 — CI, lint, and Definition-of-Done process introduced at D1, and the roadmap restructured into Deliverables

**Decision:** CI (`.github/workflows/ci.yml`), `SwiftFormat`/`SwiftLint` config, and two architecture-boundary scripts (`Scripts/check-import-boundaries.sh`, `Scripts/check-color-literals.sh`) are introduced at `ROADMAP.md` Deliverable D1 — the very first buildable state — rather than at the roadmap position that originally covered this (deep into the 34-milestone plan, alongside XLSX validation). The roadmap itself is restructured from 34 flat milestones into 17 Deliverables with nested Tasks, each carrying Goal/Dependencies/Tasks/Acceptance Criteria/Testing Requirements/Documentation Requirements/Suggested Commit Boundary. `docs/DefinitionOfDone.md` and `docs/REVIEW.md` are added as the checklist and running log those fields point back to.

**Context:** Every architecture rule that mattered in this project (`ACCore` importing nothing beyond Foundation, no raw color literals outside the design system, no force-unwraps) was, before this decision, checked manually exactly once — as the acceptance criterion of the milestone that introduced it — and never re-verified again. Nothing prevented a later, unrelated milestone from silently reintroducing a violation. Separately, the flat 34-milestone list didn't sequence architectural prerequisites (CI, the XLSX feasibility question) strictly before the feature work that implicitly depended on them holding.

**Alternatives Considered:**
- **Leave enforcement manual, add CI when the roadmap reaches its originally-planned position.** Rejected — this is the same backwards risk-ordering the `libxlsxwriter` entry (above) already identified and corrected for that one dependency; the same reasoning applies to every architecture rule, not just that one.
- **Keep the flat 34-milestone structure, just reorder items 15/scoped-CI earlier within it.** Rejected — some milestones (Review, Export) only make sense built as a unit once the Navigation Model decision (above) combined them; a flat list of 34 independent-looking items invites exactly that kind of mismatch again.
- **Introduce CI/lint at D1, restructure into Deliverables with nested Tasks** *(chosen)*.

**Reason for Choice:** Every later Deliverable inherits automated enforcement from day one instead of trusting 27+ Deliverables' worth of unverified assumptions — the same logic already applied to the XLSX dependency, generalized to the whole architecture. Grouping related Tasks into Deliverables (e.g., Review + Export into D11) makes the unit-that-must-be-finished-together explicit in the planning document itself, not just discovered mid-implementation the way the sheet-vs-tab mistake was.

**Consequences:** `Scripts/check-import-boundaries.sh` and `Scripts/check-color-literals.sh` are a fixed set of forbidden-import/pattern checks, not a general-purpose architecture linter — a new rule added to `CLAUDE.md` doesn't automatically get CI coverage; the scripts need updating in the same change (`CLAUDE.md`'s "Package Dependency Graph" limitation note says this explicitly). The CI workflow's pinned Xcode version (`15.4`, for GitHub-hosted `macos-14` runners) was written without access to a live runner to confirm against — flagged in the workflow file itself and in `docs/REVIEW.md`'s seed entry as something to confirm on first real run, not asserted as verified. **Update: it was run for real and did fail** — see the entry below for the actual outcome and fix, rather than treating this flag as still open.

**Full detail:** `CONTRIBUTING.md` §8; `docs/DefinitionOfDone.md`; `docs/REVIEW.md`; `ROADMAP.md` (full restructuring, D1 specifically for the CI/lint work itself).

## 2026-08-08 — CI's first real run failed on a Swift tools-version mismatch; fixed by lowering the manifest version, not the Xcode pin

**Decision:** `Packages/ACCore/Package.swift` and `Packages/ACExport/Package.swift` declare `// swift-tools-version: 5.10`, not `6.1`. CI's pinned Xcode version (`15.4`) is kept as-is.

**Context:** The CI workflow's Xcode pin was explicitly flagged, at the point it was written, as unverified against a live GitHub-hosted runner (see the CI/lint entry above). The first real push after it was added genuinely failed: both `swift test — ACCore` and `swift test — ACExport` errored identically — `package 'X' is using Swift tools version 6.1.0 but the installed version is 5.10.0` — diagnosed directly from `gh run view --log-failed`, not guessed at. GitHub's `macos-14` runner image ships Xcode 15.3/15.4 (default) and 16.1/16.2 (confirmed via the public `actions/runner-images` manifest) — none of which bundle a Swift 6.1 toolchain (that shipped with Xcode 16.3, not available on this image at all).

**Alternatives Considered:**
- **Bump the CI Xcode pin to 16.2** (the newest available on this runner image). Rejected — 16.2 ships Swift 6.0.x, still short of a manifest declared at 6.1; would have "fixed" the symptom while leaving the actual mismatch (declared tools-version higher than anything the runner offers) unresolved for the next dependency bump.
- **Switch `runs-on` to a newer runner image (`macos-15`) that might carry Xcode 16.3+.** Rejected without even confirming — moving the runner image is a bigger, less-targeted change than the actual problem calls for, and would abandon the deliberate choice (made when this workflow was written) to validate against `CLAUDE.md`'s documented minimum-supported Xcode version (15+), not whatever's newest.
- **Lower `swift-tools-version` in both `Package.swift` files to `5.10`** *(chosen)* — matches Xcode 15.4's actual installed Swift version exactly, and neither package's manifest uses any language/manifest feature that isn't available at 5.10 (both are plain `Package`/`.target`/`.testTarget`/`.macOS(.v14)` declarations, nothing 6.x-specific).

**Reason for Choice:** `6.1` was never a deliberate requirement — it was simply whatever `swift --version` reported in the local sandbox environment these two packages were originally built in, carried into the manifest without being chosen for a reason. Lowering it doesn't lose anything and directly fixes root cause: CI now validates against the same toolchain floor `CLAUDE.md` already documents as this project's actual minimum (Xcode 15+), rather than requiring CI to chase whatever Xcode version happens to be locally installed on a given contributor's machine.

## 2026-08-08 — Cue deletion: immediate save, no confirmation dialog, standard ⌘Z undo

**Decision:** `UpdateCueUseCase`'s add/delete/reorder operations write through to `ProjectRepository` immediately (never debounced) — only continuous field-level edits within a `Cue` remain debounced. Deleting a `Cue` requires no confirmation dialog, regardless of how many `CueRightHolder` entries are attached, but is undoable via standard ⌘Z through the environment `UndoManager`.

**Context:** `UpdateCueUseCase`'s delete path was already specified as a data operation (`ROADMAP.md` D10/T10.1), but nothing specified its save timing or its interaction contract. `CLAUDE.md`'s blanket "autosave is debounced" statement, read literally, would have applied to deletion too — which would have meant a deleted row could remain persisted for up to the debounce interval, directly undermining "Review & Export reflects the current cue list with no manual refresh."

**Alternatives Considered:**
- **Debounce deletion the same as field edits.** Rejected — debouncing exists to avoid a save-per-keystroke storm during continuous typing; a delete is a discrete, complete action with nothing further to type, so the same reasoning doesn't apply, and debouncing it actively breaks the "no manual refresh" requirement.
- **Immediate save for structural mutations (add/delete/reorder), debounced for field edits** *(chosen)*.
- **Require a confirmation dialog before deleting a `Cue`, especially one with multiple attached `CueRightHolder` entries.** Rejected — a confirmation dialog is the wrong safety mechanism for a common, easily-reversible action; Apple's HIG stance (no confirmation where a real, discoverable undo path exists) applies directly, and layering a dialog on top of undo would be redundant friction, not additional safety. The right-holder count doesn't change this: deletion is atomic (a `Cue` and its `[CueRightHolder]` entries are removed together), so there's no scenario where "how many right-holders" changes the actual risk.
- **No undo at all, rely on the confirmation dialog instead.** Rejected together with the dialog itself — this would have been strictly worse: no safety net *and* the friction of a dialog.
- **Standard ⌘Z via the environment `UndoManager`** *(chosen)*, rather than a bespoke undo stack — no reason to build a custom mechanism when the platform-standard one exists and is what users already expect.

**Reason for Choice:** Immediate save is what actually makes "no manual refresh" true rather than aspirational — verified concretely by a specified cross-ViewModel test (`ROADMAP.md` D11's acceptance criteria) rather than left as an architectural assertion. No-confirmation-plus-real-undo is the standard, well-understood macOS pattern for this exact situation, and is genuinely safer in practice than a confirmation dialog most users click through without reading.

**Consequences:** `CLAUDE.md`'s "autosave is debounced" statement (Performance Considerations, Single Source of Truth) was corrected in the same change to state the field-edit-vs-structural-mutation distinction explicitly — leaving the old blanket statement standing would have directly contradicted this decision. Rules out any future Deliverable reintroducing a confirmation dialog for cue deletion, or debouncing a structural mutation.

**Full detail:** `SPEC.md` §4.18. Affected: `CLAUDE.md` ("Performance Considerations," "Single Source of Truth"); `ROADMAP.md` D10 (T10.1, T10.2), D11 (cross-ViewModel propagation test).

## 2026-08-08 — Manual cue correction happens at the `Cue` level; `AudioAsset`/`EmbeddedMarker` stay immutable

**Decision:** Correcting a misjudged cue detection — adding a missed cue, removing a wrong one, repositioning a boundary — is entirely `Cue`-level editing via the existing `UpdateCueUseCase`. `AudioAsset.embeddedMarkers` is never edited. - **Introduce a new, separate "marker correction" concept distinct from `Cue` editing.** Rejected — by the time a user would ever want to correct something, `DetectCuesUseCase` has already merged embedded markers and silence detection into `Cue` entities (per the existing "Combining with embedded markers" rule); there is no separate "marker" left to correct independently, and building one anyway would duplicate `Cue`'s already-existing edit/delete/add capability for no benefit — exactly what `CLAUDE.md` rule 7 (no premature abstraction) argues against.

- **For re-run protection: add a new state (e.g. a `hasBeenManuallyAdjusted` flag, or a fourth `source` case) to distinguish "detected, then human-confirmed" from "detected, untouched."** Rejected as unneeded precision — reclassifying to the existing `.manual` case on any edit reuses the re-run protection rule that already exists for that case, with no new state, no new rule, and no meaningfully lost information for what the UI actually needs to show.

**Reason for Choice:** `Cue` is already the app's editable interpretation of a work's usage, built from raw detection data — "correcting a detection" and "editing a `Cue`" are the same action once that merge has happened, so no new architectural surface is needed, only wiring the existing `UpdateCueUseCase` into three concrete entry points (add via `CueTableView`, remove via the same delete control as ordinary deletion, reposition via a direct timecode field or a new interactive `WaveformView` drag mode). **Consequences:** `WaveformView` — named in `CLAUDE.md`'s folder structure since the project's first commit but never actually scoped as buildable work anywhere in the roadmap — now has a real home: `ROADMAP.md` D9/T9.3, both its display mode (`SPEC.md` §4.15) and this interactive drag mode. Rules out ever mutating `AudioAsset.embeddedMarkers` post-import, and rules out a future Deliverable reintroducing a separate provenance-tracking state beyond the existing three-case `source` enum.

**Full detail:** `SPEC.md` §4.19 (and its cross-references in §4.3, §4.10, §4.11, §4.15). Affected: `ROADMAP.md` D9 (T9.2, T9.3), D10 (T10.1, T10.2).

## 2026-08-09 — D4: `WaveformPeaksEntity` stores two `[Float]` attributes, not a hand-packed `Data` blob — reversed after a real CI crash, not a local review

**Decision:** `WaveformPeaksEntity` (`ACPersistence`) persists `WaveformPeaks.buckets` as two parallel SwiftData `[Float]` attributes (`minValues`/`maxValues`, index-aligned), not a single manually byte-packed `Data` blob.

**Context:** D4's original design (proposed and approved before implementation) packed `[WaveformPeakBucket]` into one `Data` blob — `min`/`max` `Float` pairs written via `withUnsafeBytes(of:)` and read back via `data[offset..<offset+4].withUnsafeBytes { $0.load(as: Float.self) }` — specifically to avoid 4096 separate child `@Model` rows for a type whose whole reason for existing is a bounded ~32KB memory footprint (SPEC.md §4.15). This passed every local check: `swift test` (25 consecutive clean runs of the concurrency-sensitive suite, plus the full suite), `swiftformat --lint`, `swiftlint lint --strict`, both architecture scripts, and a full local `xcodebuild build`/`test`. It then genuinely failed on PR #4's real CI run, on the Xcode-15.4-pinned runner specifically: `swift test — ACPersistence` crashed with `signal 5` (SIGTRAP) partway through `ProjectRoundTripTests`, diagnosed directly from `gh run view --log-failed`, not guessed at. The crash was in `unpack`'s `load(as:)` call — that API has a strict alignment precondition, and a `Data` value fetched back out of SwiftData's persisted representation isn't guaranteed to satisfy it the way a freshly-built in-memory `Data` (the only kind exercised locally) happens to. The same fail-fast matrix strategy that surfaced this real failure also cancelled five sibling `swift test` matrix legs mid-run (including `ACFeatures`, a package this Deliverable never touched) — confirmed via `gh api .../jobs/<id>` showing `conclusion: "cancelled"` despite every one of that job's own steps reporting `"success"`; not a second real bug, just `fail-fast: true`'s normal effect on a matrix once one leg fails.

**Alternatives Considered:**
- **Patch the existing `Data`-blob design with `loadUnaligned(fromByteOffset:as:)`** (available since Swift 5.7/macOS 13, so within this project's macOS 14 floor) instead of `load(as:)`, keeping the hand-rolled packing scheme otherwise unchanged. Rejected — this would have fixed the one instance of the bug CI happened to catch, but not the underlying pattern (manual byte-level (de)serialization of a type crossing a persistence boundary) that produced it; the same class of mistake could recur the next time this code is touched.

**Reason for Choice:** A `[Float]` SwiftData attribute is still one flat column per entity, not a per-bucket relationship row — the actual property this design needs (bounded footprint, no 4096-row overhead) holds exactly as well as the `Data`-blob version did, without reinventing serialization SwiftData already does correctly. Letting SwiftData own that encoding removes the whole class of bug (alignment, endianness, cross-version `Data`-representation assumptions), not just the one instance of it a real CI run happened to expose. This is the same standing lesson this log has recorded multiple times before for this project (the two `swift-tools-version`/`--swiftversion` CI-fix entries above): local success — even a thorough one — is not proof; only a real run on the actual CI-pinned toolchain is.

**Consequences:** `WaveformPeaksEntity.bucketsData: Data` → `minValues`/`maxValues: [Float]`; `WaveformPeaksMapper.pack`/`unpack` (manual byte manipulation) removed entirely in favor of plain `.map(\.min)`/`.map(\.max)`/`zip`. `MappingError.corruptWaveformPeaksData`'s associated values changed from byte counts to element counts, matching the new shape. Establishes a going-forward rule for this Deliverable's own pattern: a persistence entity that needs to store a domain array of scalars should default to a native SwiftData array attribute, not a hand-packed `Data` blob, unless a real, demonstrated reason rules that out.

## 2026-08-09 — D4: the real cause of PR #4's crash — a Swift exclusivity violation in the mapper's inverse-relationship assignment, found via a real crash report after two more wrong guesses

**Decision:** Every mapper that assembles a parent entity together with a to-many child collection (`ProjectMapper.toEntity` for `cues`/`people`/`labels`, `CueMapper.toEntity` for `rightHolders`, `AudioAssetMapper.toEntity` for `embeddedMarkers`) now fully materializes the child array into a local variable **first**, assigns it to the parent's relationship property, and only **then**, in a separate subsequent loop, sets each child's inverse back-reference. Previously, the back-reference was set from inside the very `.map` closure that produced the array being assigned to the parent property — e.g. `entity.rightHolders = cue.rightHolders.map { ...; rightHolderEntity.cue = entity; return rightHolderEntity }`.

**Context:** The entry above records a wrong diagnosis of PR #4's `ACPersistence` CI crash (`signal 5`/SIGTRAP, 100% reproducible, always at the exact same point: the first test of `ProjectRoundTripTests`, immediately after `ProjectRepositoryImplTests` finishes). Three targeted fixes were tried in sequence, each based on a plausible-looking correlation rather than a confirmed cause, and each had **zero effect** on an identical crash:
1. Redesigning `WaveformPeaksEntity` (the entry above) — ruled out once fixing it changed nothing.
2. Removing `@Attribute(.unique)` from `PersonEntity`/`LabelEntity.id` (multiple unique constraints across `@Model` types in one schema is a documented early-SwiftData crash source) — also independently justified (nothing in `ProjectRepositoryImpl` queries by those IDs) but also had zero effect.
3. Replacing a shared `static let Schema` with a fresh `Schema` built per `ModelContainer` (a single `Schema` instance reused across ~11 containers in one process being a plausible corruption source) — also zero effect.

After three misses, continuing to guess stopped being defensible. A temporary diagnostic step was added to `.github/workflows/ci.yml` (`if: failure()`, dumps `~/Library/Logs/DiagnosticReports`/`/Library/Logs/DiagnosticReports` after a short wait for `ReportCrash` to finish writing) — removed again in this same change once it had done its job. The first attempt found only stale, pre-baked VM-image reports; a second attempt (waiting 20s, filtered to recently-modified files) found the real one: `xctest-2026-08-09-131719.ips`. It showed `"exception": {"type":"EXC_BREAKPOINT","signal":"SIGTRAP"}`, crashing thread 0 inside `swift_beginAccess`, with register values naming `type metadata for CueEntity` and `type metadata for CueRightHolderEntity`, at a frame inside `@__swiftmacro_...CueRightHolderEntityC3cue..._PersistedProperty` — SwiftData's `@Model`-macro-generated accessor for `CueRightHolderEntity.cue`.

That pointed directly at a real bug: setting `rightHolderEntity.cue = entity` (the inverse side of a declared `inverse:` relationship pair) while `entity.rightHolders = <array still being computed>` (the forward side) is still mid-assignment is a genuine Swift exclusivity violation — SwiftData's macro-generated relationship accessors can touch the other side of an `inverse:` pair when one side is written, and doing that while the forward assignment's RHS closure is still executing overlaps two accesses to the same stored property. `swift_beginAccess` traps exactly this. It explains every observation at once: why it only reproduced with a non-empty child array (`[].map { ... }` never runs the closure body, so `ProjectRepositoryImplTests`'s minimal-fixture tests — 10 of them, all passing — never hit the code path at all); why none of the three earlier fixes moved it (none touched this code); and why it didn't reproduce locally on a newer toolchain (exclusivity-check/relationship-accessor behavior differs enough between Swift 5.10 and 6.2 that the same code traps on one and not the other).

**Alternatives Considered:**
- **Keep guessing at further plausible SwiftData-version quirks.** Rejected after the third miss — three misses in a row is the signal to get real evidence, not to keep pattern-matching against SwiftData folklore.
- **Get a real crash report from the CI runner and diagnose from it directly** *(chosen)*.
- **Fix the ordering (materialize children, assign, then set back-references) in all five affected call sites** *(chosen, once the cause was confirmed)*, over e.g. suppressing exclusivity checking for these files (`-Onone`-style enforcement flags) — rejected, since that would silence the compiler's own correctness check rather than fix the actual overlapping-access bug, and exclusivity checking exists precisely to catch bugs like this one.

**Reason for Choice:** This is the same lesson the tools-version/`--swiftversion` entries and the (wrong) entry above all point at, sharpened one step further: not just "a real CI run is the only real verification," but "a plausible-looking correlation is not a diagnosis — when the first fix based on one doesn't work, get real evidence before trying a second." A crash report naming the exact crashing function and the exact types involved is unambiguous in a way three rounds of "this looks like it could be the cause" never were.

**Consequences:** `CueMapper.swift`, `AudioAssetMapper.swift`, `ProjectMapper.swift` all changed to the materialize-then-assign-then-backreference pattern, each with a doc comment pointing back to this entry so a future change to these mappers doesn't reintroduce the interleaved version by "simplifying" it back. The `.unique`-removal and fresh-`Schema`-per-container changes from the two wrong-guess attempts are kept (both independently correct, per their own entries/comments) but are not what fixed this. The temporary CI diagnostic step is removed — not a permanent addition, its job was done once it produced the real crash report.

**Full detail:** `Packages/ACPersistence/Sources/ACPersistence/Mappers/{Cue,AudioAsset,Project}Mapper.swift`. PR #4.

**Correction, recorded once the real cause was found (see the entry below):** this entry's diagnosis was *also* wrong — a fourth wrong guess, not the third's replacement. Two things proved it, in order: (1) a deliberate fixture bisection found the crash already reproduces at the simplest possible case — one `Cue` with **zero** `CueRightHolder`s — which never executes the `rightHolders`-array closure body at all, meaning the exclusivity scenario this entry describes physically cannot occur there; (2) pinning CI to a newer Xcode made the crash disappear entirely, with this exact reordering still present and unchanged, on code that had never needed it. The reordering itself is harmless and stays in place, but it fixed nothing — recorded here rather than silently correcting the entry above, per this log's standing practice.

## 2026-08-09 — D4's real, confirmed root cause: a genuine Xcode 15.4 SwiftData relationship-handling defect — CI repinned to macos-15/Xcode 26.3

**Decision:** `.github/workflows/ci.yml`'s three jobs move from `runs-on: macos-14` / `xcode-version: "15.4"` to `runs-on: macos-15` / `xcode-version: "26.3"`. The PR #4 `ACPersistence` crash was never a bug in this project's code — it is a real defect in Xcode 15.4's SwiftData framework, specifically in handling a `@Model` to-many relationship with an explicit `@Relationship(deleteRule:inverse:)` on one side and a bare, un-annotated inverse `var` on the other (exactly `CLAUDE.md`'s and this codebase's own established pattern, used correctly).

**Context:** Four consecutive code-level fixes (`WaveformPeaksEntity` redesign, dropping duplicate `@Attribute(.unique)` constraints, a fresh `Schema` per `ModelContainer`, and the mapper exclusivity-violation reordering — the four entries directly above) each had **zero effect** on a fully deterministic `SIGTRAP`/`EXC_BREAKPOINT` crash, always at the same point, always on the first non-empty-`cues` `Project` inserted in the process. At the user's direction, the investigation stopped guessing at code fixes and instead isolated the actual variable, in three further steps, each confirmed on the real CI runner before moving to the next:

1. **Fixture bisection.** Seven staged tests, each adding one piece of complexity on top of the last (bare `Cue` → `+CueRightHolder` → `+Person` → `+Label` → `+AudioAsset`/`EmbeddedMarker` → `+WaveformPeaks` → the full fixture). The crash hit at **stage 1** — one `Cue`, zero `CueRightHolder`s, nothing else — immediately, as the very first test in the process. This ruled out every one of the four prior "fixes" outright: none of them touch code that stage 1 even reaches.
2. **Isolated toy reproduction.** Two brand-new `@Model` types (`ToyParent`/`ToyChild`) with zero connection to any real entity in this codebase, structurally identical in shape to `ProjectEntity.cues`/`CueEntity.project` (explicit `@Relationship(deleteRule:inverse:)` on the to-many side, bare optional on the inverse side). One insert, one save. Crashed identically on CI, every time; passed locally under Xcode 26.3 every time, under both `swift test` and a from-scratch `xcodebuild test` run against the bare package (Xcode natively infers a scheme for an un-wrapped SPM package — no hand-authored `.xcodeproj` needed). This ruled out the real schema's specific shape as the cause and ruled out the SPM-CLI-vs-Xcode-test-runner distinction as the explanation (both harnesses agreed, on both toolchains).
3. **Environment isolation.** Per GitHub's own `runner-images` documentation (github.com/actions/runner-images): `macos-14` offers Xcode 15.0.1–16.2 (15.4 default, this project's pin since D1); `macos-15` offers Xcode 16.0–26.3 (16.4 default). `26.3` is available on `macos-15` and is the exact local Xcode version already confirmed never to reproduce this crash. A config-only change (`ci.yml` only, zero source/test files touched, so the result cleanly isolates one variable) repinned all three CI jobs to `macos-15`/`26.3`. Result: **every job passed**, including `swift test — ACPersistence` (19/19 tests, including the toy test, `test_arrayOrderSurvivesRoundTrip`, and every other previously-crashing test) — the first fully green `ACPersistence` CI run in this entire investigation.

**Alternatives Considered:**
- **Keep trying code-level fixes against the real schema.** Rejected after the fourth miss — by that point the evidence (bisection reaching a trivially simple case; an isolated toy model reproducing identically) already pointed away from this project's code entirely; continuing to edit `ProjectEntity`/`CueEntity` would have been debugging the wrong layer.
- **Bisect the fixture data instead of the code, then isolate the toolchain as its own variable, only then change CI** *(chosen)* — each step was a single, cheap, reversible experiment that either confirmed or ruled out one specific hypothesis before the next was tried, rather than another round of plausible-looking correlation.
- **Pin to an intermediate Xcode version (e.g. 16.2, the newest available on `macos-14`) rather than jumping to 26.3.** Not tried — 26.3 was chosen specifically because it's the exact version already confirmed clean locally, giving the cleanest possible signal; a narrower bisection of *which* Xcode version between 15.4 and 26.3 first fixes it was not attempted and isn't needed to close this out, though it would be a reasonable follow-up if this project ever wants to pin the oldest-safe version rather than the newest-available one.

**Reason for Choice:** This closes out real, load-bearing uncertainty rather than papering over a symptom. `CLAUDE.md` rule 4's spirit (verify a dependency rather than trust it) applies here too, generalized to the toolchain itself: Xcode 15.4 was pinned at D1 specifically *because* it was `CLAUDE.md`'s documented minimum-supported-Xcode floor, on the assumption that "the documented minimum" and "actually works" were the same claim. D4 is the first Deliverable to build a real, relationship-heavy SwiftData schema, and it's what exposed that assumption was false for this specific SwiftData/Xcode combination.

**Consequences:** `CLAUDE.md`'s "Deployment Target"/"Toolchain implication" section currently states "Xcode 15 or newer" as the build-toolchain floor. That statement is now known to be actively wrong for any contributor doing real `ACPersistence`-style SwiftData relationship work: Xcode 15.4 doesn't just lack some newer convenience, it produces a genuine runtime crash on correct, ordinary relationship code. **This needs a real, explicit correction to `CLAUDE.md` in a follow-up change** (raising the stated minimum Xcode floor, not just the CI pin) — flagged here rather than silently left stale, per rule 8, but deliberately not made in this same commit since it wasn't part of what was asked for here. The four "fix" commits already in `ACPersistence`'s mapper/entity code (D4's other `docs/DECISIONS.md` entries) are harmless and stay as-is — none of them caused a problem, they just weren't the actual fix. The temporary bisection/toy-model test files (`BisectionTests.swift`, since removed; `AAAToyRelationshipTests.swift`, still present) — whether to delete the latter now that its job is done is an open question for whoever picks this up next, not decided here.

**Full detail:** `.github/workflows/ci.yml`. PR #4.

## 2026-08-10 — Per-`Project` window frame persistence: explicit `Project.ID`-keyed store, not `NSWindow.setFrameAutosaveName`

**Decision:** A Project window's size and position are persisted and restored via a custom mechanism — `ProjectWindowFrameStore` (a `Project.ID`-keyed `UserDefaults` entry, stored as a human-readable `"x,y,width,height"` string) plus `ProjectWindowFrameSaver` (an `NSWindow.willCloseNotification` observer scoped to the specific window). `NSWindow.setFrameAutosaveName` — AppKit's own, standard, built-in mechanism for exactly this purpose — is not used.

**Context:** Manual verification during D6 found that a Project window's size didn't survive being resized, closed, and reopened for the same `Project` — it reopened at the app's default size every time. The first implementation used `NSWindow.setFrameAutosaveName("ProjectWindow-\(projectID.uuidString)")` inside `WindowAccessor`'s window-resolution callback — the textbook-correct AppKit API for "remember this window's frame across close/reopen," and the obvious first thing to reach for. It was reported back as still not working. Rather than trust that the "correct" API must be working somehow, the actual `UserDefaults` state was inspected directly: `defaults read com.autocue.AutoCue` after a real resize-then-quit cycle showed **no** `"NSWindow Frame ProjectWindow-<uuid>"` key anywhere — the call had never persisted anything. What *was* present: keys like `"NSWindow Frame SwiftUI.PresentedWindowContent<Foundation.UUID, Swift.Optional<AutoCue.ProjectWindowView>>-2-AppWindow-1"` — SwiftUI's own `WindowGroup(for:)` already runs an internal frame-restoration system of its own, keyed by an auto-generated name tied to window-open *ordinal*, not `Project.ID`. That's the most plausible reason `setFrameAutosaveName` never actually engaged (SwiftUI already owns frame restoration for this window kind) and, independently, it's exactly the kind of ordinal-vs-identity mismatch that explains the observed symptom: reopening the same `Project` doesn't reliably map back to the same saved entry.

**Alternatives Considered:**
- **`NSWindow.setFrameAutosaveName`.** Rejected — empirically confirmed, not assumed, not to persist anything in this `WindowGroup(for:)` context. Kept as a documented dead end specifically so a future session doesn't lose the same time re-discovering this: it looks correct, compiles without error, and produces no visible failure — it just silently doesn't work.
- **A custom `Project.ID`-keyed `UserDefaults` store, written explicitly on `NSWindow.willCloseNotification` and read explicitly when the window is created** *(chosen)*.

**Reason for Choice:** Full, direct control removes SwiftUI's competing restoration system from the equation entirely, rather than trying to coexist with or override it. Storing the frame as a plain `"x,y,width,height"` string (not `NSStringFromRect`/a binary blob) was a deliberate choice too — it stays directly inspectable via the same `defaults read` method that caught the original failure, so the next time something in this area doesn't work, the state is checkable in one command rather than requiring another investigation to even see what's stored. The fix was verified the same way the bug was found — empirically, not by re-trusting a "should work" API: a real `NSWindow`, real `NotificationCenter` delivery, and real `UserDefaults` (`ProjectWindowFrameStoreTests`) confirm a window's frame is actually captured and persisted when its close notification fires, and manual testing with two Project windows open simultaneously confirmed both position and size are correctly remembered per-window.

**Consequences:** Rules out reaching for `NSWindow.setFrameAutosaveName` again for any future window-frame-persistence need in this app without first checking whether the same `WindowGroup(for:)`-restoration conflict applies — check this entry first. `ProjectWindowFrameSaver` observes `NSWindow.willCloseNotification` rather than becoming `window.delegate`, deliberately: `WindowGroup(for:)` may already be using that single delegate slot internally, and overwriting it wholesale risked silently breaking whatever else relies on it — a notification observer coexists safely regardless. A real, unrelated bug was caught while building the verifying test, not carried forward: calling `.close()` on a programmatically-created `NSWindow` inside the `AutoCueTests` host reliably crashed (`EXC_BAD_ACCESS` inside XCTest's own post-test memory-deallocation checker, confirmed via a real crash report) — worked around by posting `NSWindow.willCloseNotification` directly instead of calling `.close()`, which exercises the same observed code path without triggering AppKit's real window-close teardown inside the test host.

**Full detail:** `docs/REVIEW.md`'s D6 entries. Implementation: `AutoCue/ProjectWindowFrameStore.swift`, `AutoCue/ProjectWindowFrameSaver.swift`, `AutoCue/ProjectWindowView.swift`; tests: `AutoCueTests/ProjectWindowFrameStoreTests.swift`. `ROADMAP.md` D6.

## 2026-08-10 — `SetupViewModel` starts with a placeholder empty `Setup`, loaded asynchronously — `DependencyContainer` factories stay synchronous

**Decision:** `SetupViewModel.init` no longer takes an `initialSetup: Setup` parameter. It constructs with a placeholder empty `Setup` (the same shape `CreateProjectUseCase.makeDefaultSetup` produces for a brand-new `Project`) and exposes `load() async`, which fetches the real persisted value from `ObserveProjectsUseCase.observeAll()`'s stream and populates `setup` — but **only on its first successful call**; every subsequent call refreshes `people`/`labels` only, never overwriting `setup` again. `SetupView`'s `.task` calls `load()` once on appear, then re-seeds its own local `draft` mirror from `viewModel.setup` immediately after — a one-time handoff, not a live sync.

**Alternatives Considered:**
- **Add a synchronous, cached "last known Setup" lookup to `DependencyContainer` or `ProjectRepository`.** Rejected — this would mean `DependencyContainer` (or the repository) keeping its own shadow cache of `Project` data outside `ProjectRepository`'s own live-observation stream, a second source of truth for exactly the state `CLAUDE.md`'s "Single Source of Truth" section already settled (SwiftData behind `ProjectRepository`, observed via `AsyncStream`) — reintroducing a cache to dodge an `async` boundary is a worse trade than the one this decision actually makes.

Rejected — SwiftUI's `@ViewBuilder` doesn't support this directly, and even if it did, it would freeze tab-switching on every navigation to Setup, worse UX than a brief placeholder-then-populate flash.

**Reason for Choice:** Keeps the synchronous-factory-call-site rule (`CLAUDE.md`'s Dependency Injection Pattern) intact rather than carving out an exception for Setup, and reuses an already-proven pattern instead of inventing a new one. The "populate `setup` only once" guard is what makes this safe for the "this window is the sole editor" invariant `SetupViewModel`'s own doc comment establishes — without it, a second `load()` call (e.g. triggered by the party picker's own directory refresh) could silently overwrite an in-progress, not-yet-saved edit with the stream's stale snapshot.

## 2026-08-10 — Native AppKit-backed controls need `.environment(\.colorScheme:)` forced; `.foregroundStyle()` alone doesn't reach them

**Decision:** Every primary-surface screen forces `.fixedAppearance(for: .primary)` (a new `ACDesignSystem` modifier wrapping `.environment(\.colorScheme, .light)`) at its root — `SetupView` and its sheets (`PartyPickerView`/`PersonEditorSheet`/`LabelEditorSheet`) are the first real users. Reversed-surface screens (Review & Export, D11) will use `.fixedAppearance(for: .reversed)` (`.dark`) once they exist.

**Context:** The user's manual click-through of D7's Setup screen found ghost/placeholder text missing on every field, a `List` rendering unreadable black-on-black, a `Picker`'s selected value invisible, and (separately) stepper arrows on `DatePicker`. Rather than guess at fixes, each was reproduced and diagnosed with a real, live, windowed test app (a throwaway SwiftPM executable target using SwiftUI's own `App`/`WindowGroup`, launched and screenshotted the same way `docs/REVIEW.md`'s D6 entries already established for this session's Accessibility-permission-less environment) — `ImageRenderer` was tried first but cannot render `TextField`/`Picker`/`DatePicker` at all outside a live app window (confirmed: a plain `Text` renders fine via `ImageRenderer`, proving the harness itself works; every AppKit-backed control renders as a "content unsupported" placeholder glyph instead).

The real, confirmed cause: this session's system is in Dark Mode, and several native-control rendering paths — a `TextField`'s `prompt:` placeholder, a `Picker`'s own selected-value label — follow the *system's actual* Dark/Light Mode setting internally, via AppKit, regardless of any SwiftUI-level `.foregroundStyle()` applied to them. This is different from, and not fixed by, the same techniques that already worked for D6's bugs (a `TextField`'s *typed* text, and a `List`'s background material) — those follow SwiftUI's own rendering path and respond correctly to `.foregroundStyle()`/`.scrollContentBackground(.hidden)`. Confirmed directly, not inferred: a manual-overlay placeholder (`ZStack` + conditional `Text`, bypassing `prompt:` entirely) rendered correctly; the exact same `GhostTextField` code, unchanged, rendered correctly too once `.environment(\.colorScheme, .light)` was applied to the screen — proving the mechanism, not just patching the symptom.

**Alternatives Considered:**
- **Rebuild `GhostTextField` to use a manual `ZStack` overlay instead of `TextField`'s `prompt:` parameter.** Considered and confirmed to work in isolation — but doesn't fix `Picker`'s selected-value display (which has no `prompt:`-equivalent escape hatch to work around at all), so it would only have solved one of the three affected control types, leaving Picker's blank-value bug as a separate, unexplained mystery. Rejected once the more general fix was found and confirmed to also fix the placeholder case.
- **Patch each affected control individually** (e.g. hardcode a light-appearance override only on the specific `Picker`/`TextField` instances that were reported broken). Rejected — this is a real, general property of every native AppKit-backed control this fixed-appearance app will ever use, not a per-control quirk; a screen-level fix prevents the same bug recurring silently on the next Picker/DatePicker/ColorPicker/etc. a future Deliverable adds.
- **Force `.environment(\.colorScheme:)` once, screen-wide** *(chosen)*.

**Reason for Choice:** `CLAUDE.md`'s Visual Language already commits this app to a fixed, non-adaptive appearance — this decision doesn't change that commitment, it closes a real gap in how it was being enforced. D6 fixed the SwiftUI-level instances of "doesn't respect our fixed palette" (typed-text color, List background material) that its own manual click-through happened to exercise; D7's Setup screen was the first to exercise enough *native-control* surface area (Picker, DatePicker, TextField placeholders) to expose that a second, AppKit-level enforcement mechanism was still missing entirely.

**Consequences:** Every future primary-surface screen (Cue Sheet Editor, D10) should apply `.fixedAppearance(for: .primary)` at its own root from the start, not rediscover this after a similar bug report — flagged here so it isn't. D6's `ProjectLibraryView`/`LibraryWindowView` don't currently use any `Picker`/`DatePicker`, so they're not retroactively broken by this finding, but would benefit from the same modifier if either is ever added there. `List`'s background material still needs its own separate `.scrollContentBackground(.hidden)` + explicit `.background()` fix regardless of this modifier — the two address genuinely different rendering paths that happened to share the same underlying "follows real system appearance" cause.

## 2026-08-10 — Four reported data-loss bugs traced to two independent, real root causes: `detail`-computed-property ViewModel reconstruction, and a repository-level fetch-then-write race

**Decision:** Fixed both causes rather than four separate symptom-level patches. (1) `ProjectWindowView.setupViewModel`/`.rightHolderDirectoryViewModel` are now constructed exactly once per window, via `@State`, instead of being minted fresh by `DependencyContainer` inside `detail`'s `.setup` case on every `body` re-evaluation. (2) `ProjectRepository` gained `update(id:transform:)`, an atomic fetch-transform-write operation serialized through the same per-`Project.ID` `writeTails` queue as every other write; `UpdateSetupUseCase`/`UpdateRightHolderDirectoryUseCase` now use it instead of a caller-side `fetch` followed by a separate `update(_:)` call. A third, smaller fix closes the remaining gap: `ProjectWindowSaveFlusher` flushes any pending debounced `SetupViewModel` edit on `NSWindow.willCloseNotification`, the same mechanism `ProjectWindowFrameSaver` already established for window-close events in this `WindowGroup(for:)` context.

**Context:** The user reported, from a real manual click-through: (a) using the Declarant picker wiped the entire Setup form, including the Artists/collaborators roster; (b) switching tabs away from and back to Setup caused the same full wipe; (c) closing a Project window lost typed text-field edits but not checkbox/toggle state or previously-saved Artists; (d) re-adding a Person under a role that already had one sometimes created a genuine duplicate. The instruction was to find the *shared* root cause rather than patch each symptom individually.

Investigation, traced end-to-end rather than guessed:
- **Cause 1 (explains a, b, and most of c).** `ProjectWindowView.detail` was a plain `@ViewBuilder` computed property whose `.setup` case called `container.makeSetupViewModel(for:)`/`.makeRightHolderDirectoryViewModel(for:)` directly. Computed properties re-run their entire body on every access, and SwiftUI re-evaluates `body` (and therefore `detail`) for reasons well beyond an explicit tab switch (any picker selection touching `@Observable` state elsewhere in the hierarchy is enough). Every re-evaluation silently minted a **brand-new** `SetupViewModel` with `hasLoadedInitialSetup = false` and empty `people`/`labels` — from the user's perspective indistinguishable from "everything just vanished," because the View was now pointed at a fresh, not-yet-loaded object, not the one holding their actual edits. This also put any in-flight *debounced* save at real risk: `SetupViewModel.updateDebounced`'s scheduled `Task` captures `[weak self]`, so if the only strong reference to that specific `SetupViewModel` instance (the discarded old `SetupView`'s dependency) went away before the 500ms debounce fired, the save was silently dropped — a second, independent way the same bug could look like plain data loss.
- **Cause 2 (a real, separate structural risk, confirmed by reading `ProjectRepositoryImpl` — not hypothetical).** `fetch(id:)` was never part of the per-`Project.ID` write-serialization mechanism (`writeTails`/`enqueueWrite`) — only `create`/`update`/`delete` were. `UpdateSetupUseCase` and `UpdateRightHolderDirectoryUseCase` each independently did "fetch the current `Project`, replace one disjoint slice, write the whole thing back" — both Use Cases' own doc comments at the time claimed this was safe because each "fetches fresh at write time," but that reasoning only holds against a *single* writer. Two concurrent callers (exactly `SetupViewModel`'s debounced Setup save racing `RightHolderDirectoryViewModel`'s Person/Label save, from the same Project window) can both fetch before either writes; the second write then persists a `Project` built from a pre-write snapshot and silently discards the first write's change, even though the two SwiftData writes themselves land in the correct, fully serialized order relative to each other.
- **Cause 1 alone fully explains (a) and (b)**, and the text-field half of (c). It does not fully explain why (c) spared checkbox/toggle state and previously-saved Artists — that's simply because those had already round-tripped through `updateImmediately`/prior debounced saves before the window closed, while in-flight *text* edits were still sitting in a not-yet-fired debounce Task at close time; `ProjectWindowSaveFlusher` closes that specific gap. **Cause 2 was not the primary trigger for the four reported symptoms** (cause 1 already explains all of them), but it is a real, confirmed, independently-reproducible bug in its own right — closing it was not scope creep, it's the same class of "SetupViewModel not backed by a real debounced-save-to-repository pattern" risk the user explicitly asked to be ruled out, and leaving it unfixed after finding it would mean shipping a known data-loss bug.
- **Bug (d) (duplicate Person creation) is a downstream *consequence* of cause 1, not a fourth independent bug**, exactly as the user suspected: once `PartyPickerView`'s directory listing came from a freshly-reconstructed, not-yet-loaded `RightHolderDirectoryViewModel`, the picker would show an empty or stale roster, making a name that already existed look "new" to the user, who would then add it again. Fixing cause 1 removes the *trigger* for accidental duplicates but does not prevent a duplicate created deliberately or via any other path — real duplicate-name detection (below) was implemented as its own, separate fix, per the user's explicit separate request.

**Verification — not just "it compiles":**
- **Cause 1 fix.** `ProjectWindowView`'s new doc comment traces exactly why `@State` (not a plain `let`, which was tried and self-caught as wrong mid-implementation — `init` reruns on every SwiftUI reconstruction, a plain `let` would reconstruct just as often as the original bug did) makes construction happen exactly once per window identity. Confirmed via a real `xcodebuild build` of the `AutoCue` app target (this bug lives in the App target, which SwiftPM can't build/typecheck on its own) and via a full `xcodebuild test` run (13 `AutoCueTests`, all passing) after the fix landed.
- **Cause 2 fix.** A new deterministic test, `ProjectRepositoryImplTests.test_concurrentAtomicUpdatesToDisjointSlicesBothSurvive`, drives the *exact* interleaving described above — one `update(id:transform:)` call adding a `Person`, paused mid-write via the existing `Signal`/`setWriteHook` seam; a second `update(id:transform:)` call renaming the `Project`, submitted while the first is still paused; released, and both awaited — and asserts **both** the rename and the added `Person` survive in the final persisted state. Run against the pre-fix code shape (plain `fetch` + `update(_:)`), the equivalent interleaving loses one of the two changes; against the new `update(id:transform:)`, both survive because the fetch and the write for each call are now one operation inside the same serialized per-`Project.ID` queue. All 31 `ACPersistenceTests` (including this one), all 177 `ACCoreTests`, and all 28 `ACFeaturesTests` pass.
- **`ProjectWindowSaveFlusher`.** Mirrors `ProjectWindowFrameSaver`'s already-established, already-verified `NSWindow.willCloseNotification` mechanism exactly — no new pattern introduced, so no new verification gap beyond confirming it's wired into `WindowAccessor` alongside the frame saver, which the App target build confirms compiles and links.

**Alternatives Considered (cause 2 fix specifically):**
- **Leave `DeleteRightHolderUseCase` on the same fetch-then-`update(_:)` shape.** Its `project` argument is caller-supplied (from the ViewModel's held snapshot), not independently fetched inside the Use Case, so fixing it atomically would require a larger signature change (the reference-location guard-check needs the full `Project`, and `update(id:transform:)`'s `transform` closure has no way to signal "checked, but blocked — don't write" short of throwing, which would need a second sentinel error type and still perform a real SwiftData write attempt shape it doesn't have today). Rejected for this round on scope grounds — deletion is a deliberate, explicit, comparatively rare user action, not a background debounced-save race like the confirmed bug — but the risk is real and is flagged here rather than silently ignored, consistent with how the XLSX `NSSavePanel` residual gap is tracked in the "Export Architecture" section of `CLAUDE.md`. A future pass should extend `update(id:transform:)` (or a `throws`-aware sibling) to cover it.
- **Serialize the whole `ProjectRepositoryImpl` actor instead of adding a new atomic method.** Rejected — this is exactly the coarser design `ProjectRepositoryImpl`'s own doc comment already argues against (D4's "different `Project.ID` writes don't block each other" requirement), and would reintroduce cross-window blocking for unrelated Projects to fix a same-Project-ID problem.

**Reason for Choice:** Both fixes close the actual mechanism the user asked to be found, not just the four visible symptoms. `update(id:transform:)` generalizes cleanly to every future Use Case that needs "read the current `Project`, change one slice, persist" — `ROADMAP.md` D9/D10's cue-detection and cue-editing Use Cases will have the same shape and should use it from the start rather than reintroducing the fetch-then-write pattern this fix just removed.

**Consequences:** `ProjectRepository`'s protocol grew a new required method — both conformers (`ProjectRepositoryImpl`, `InMemoryProjectRepository`) implement it; no other type conforms to the protocol. `UpdateSetupUseCase`/`UpdateRightHolderDirectoryUseCase`'s doc comments, which previously (incorrectly) asserted fetch-then-write was already race-safe, are corrected to describe the actual fix.

## 2026-08-10 — Duplicate-`Person`/`Label` name detection lives in `UpdateRightHolderDirectoryUseCase`, checked atomically inside the same write

**Decision:** `UpdateRightHolderDirectoryUseCase.savePerson`/`.saveLabel` now return `SavePersonResult`/`SaveLabelResult` (`.saved(Project)` / `.duplicateName(existing:)`) instead of a bare `Project`. A duplicate is a trimmed, case-insensitive match on `Person.firstName`+`.lastName` or `Label.name` against any *other* entry (`id` differs) already in the same `Project`'s directory. The check runs inside the same `update(id:transform:)` call that performs the write — against the truly-current directory, not a separately-fetched snapshot — so it can't reintroduce the fetch-then-write race the sibling fix (above) just closed. `PersonEditorSheet`/`LabelEditorSheet`'s `onSave` closures became `async`, returning the result; the sheet stays open and shows an inline message (reusing `ACDesignSystem`'s existing `.errorAlert(message:)`, not a new bespoke warning component) on `.duplicateName` instead of dismissing and silently creating a second entry.

**Context:** Requested separately from the four data-loss bugs, as a related but independent fix: re-adding a `Person` under a role that already had one could create a genuine duplicate — confirmed as a downstream *consequence* of the ViewModel-reconstruction bug above (a stale/empty picker roster makes an existing name look unclaimed), not an independent fourth root cause, but real duplicate-prevention is still needed regardless of what triggers the attempt.

**Alternatives Considered:**
- **Check for duplicates in `RightHolderDirectoryViewModel` (Presentation layer).** Rejected — `CLAUDE.md`'s MVVM rules assign business rules to Use Cases, not ViewModels; a ViewModel "orchestrates and holds view state, it does not decide domain logic." Duplicate-identity is a domain-level judgment about the right-holder directory, not view state.
- **Fetch-then-check-then-write** (fetch the `Project`, check for a duplicate against that snapshot, then call `update(id:transform:)` separately). Rejected — this reintroduces exactly the race the atomic-update fix above exists to prevent, just for the duplicate *check* instead of the write: a `Person` added concurrently between the check-fetch and the write could be missed. Checking inside `transform` itself closes this.
- **Hard save-blocking silent failure** (just don't add the duplicate, no message). Rejected — the user's request was "prevented or flagged," and a silent no-op looks indistinguishable from a bug to the user (they'd have no idea their Save click did nothing).

**Reason for Choice:** Matches the existing `DeletePartyResult`-style pattern this Use Case's sibling (`DeleteRightHolderUseCase`) already established for "the Use Case reports back a structured outcome, the caller decides what to show" — no new architectural shape introduced. Throwing a private, non-public error type (`DuplicatePersonNameError`/`DuplicateLabelNameError`) from inside the `transform` closure, caught immediately in `savePerson`/`saveLabel`, was the mechanism that let the check run inside the same atomic operation as the write without changing `ProjectRepository.update(id:transform:)`'s public signature.

**Consequences:** `PersonEditorSheet`/`LabelEditorSheet`'s `onSave` closure type changed from `(Person) -> Void`/`(Label) -> Void` to `(Person) async -> SavePersonResult?`/`(Label) async -> SaveLabelResult?` — all four call sites (`PartyPickerView`, `SetupView+CollaboratorsSection`, for both Person and Label) updated to only dismiss their sheet on `.saved`. `RightHolderDirectoryViewModelTests` covers both the duplicate-blocked case and that editing an entry's own existing name (same `id`) is never mistaken for a collision with itself.

**Full detail:** `Packages/ACCore/Sources/ACCore/UseCases/UpdateRightHolderDirectoryUseCase.swift`; `Packages/ACFeatures/Sources/ACFeatures/CueSheetEditor/{ViewModels/RightHolderDirectoryViewModel,Views/PersonEditorSheet,Views/LabelEditorSheet,Views/PartyPickerView,Views/SetupView+CollaboratorsSection}.swift`; test: `Packages/ACFeatures/Tests/ACFeaturesTests/RightHolderDirectoryViewModelTests.swift`. `ROADMAP.md` D7.

## 2026-08-10 — `Person.intendedRole` → `intendedRoles: Set<PersonIntendedRole>`; every roster bucket's "+ Add" replaced with the shared "Select" picker

**Decision:** `Person.intendedRole: PersonIntendedRole?` (at most one role) becomes `Person.intendedRoles: Set<PersonIntendedRole>` (zero or more, simultaneously) — persisted as `PersonEntity.intendedRolesRawValues: [String]`, the same `[String]`-raw-values pattern `SetupEntity` already uses for `Set<ProductionType>`/`Set<ExploitationType>`/`Set<AttachmentType>`. `PartyPickerView` (previously built only for `Setup.producer`/`.directorOrPrincipal`/`.declarant`) is now the single "Select" entry point everywhere a Party/role slot exists — the Collaborators section's Komponist*in/Arrangeur*in/Interpret*in/Label buckets (`SetupView+CollaboratorsSection.swift`) had their own separate, always-create-new "+ Add" flow replaced with it, scoped via a new `PartyPickerScope` (`.any`/`.personOnly`/`.labelOnly`) parameter. Selecting an existing `Person` from a bucket adds that one role to their set if not already present (no-op if it is — the actual duplicate-prevention this whole change exists for); each bucket's "✕" now removes only that one role from the person (`intendedRoles.subtracting`), not the whole directory entry — confirmed via a direct question, not assumed, since the obvious-looking alternative (keep "✕" as full deletion) would silently remove someone from every *other* bucket they're also in the moment multi-role became possible. Separately, `SetupView.partyFieldRow`'s "Not set" plain-color literal was replaced with ghost-styled ("No {field} selected", `Theme.Colors.ghostTextPrimary`) placeholder text, matching `GhostTextField`'s existing de-emphasis convention.

**Context:** Reported as a real UX gap: adding someone under Komponist*in, then separately needing the same person as Interpret*in, had no path except creating a second, duplicate `Person` — the just-shipped duplicate-name detection correctly *blocked* that, but blocking with no alternative isn't a fix, it's a dead end. The fix required confronting a real, previously-unstated constraint: `PersonIntendedRole?` (singular) cannot represent "this person holds two roles on this project" at all — flagged and confirmed via a direct question (`CLAUDE.md` rule 9: a domain field's shape is not a call to make silently) rather than guessed, given two structurally different ways to solve it (a plural field on `Person` itself, vs. a separate per-bucket membership record living elsewhere). `Set<PersonIntendedRole>` was chosen as the one that keeps "which roles does this person hold" a property of the person, not a second, easily-desynced association living in a different place — consistent with `CLAUDE.md`'s "Single Source of Truth" reasoning that already drove removing `RightHolderDirectoryViewModel`'s stale cached `Project` earlier the same day.

**Alternatives Considered:**
- **A separate multi-role membership record, not stored on `Person` at all** (e.g. `Set<Person.ID>` per role, kept on `Setup` or `Project`). Rejected — this duplicates identity tracking outside the `Person` model itself, is a second place "which roles does X hold" could get out of sync, and has no natural owner among existing types (`Setup` is production-header info, not a roster index).
- **Keep `intendedRole` singular; reusing a person from a second bucket's picker just overwrites their one role**, moving them out of their first bucket. Rejected — directly contradicts the reported need (both roles must hold *simultaneously*), and silently relocating someone out of a bucket they were legitimately added to is a worse surprise than the bug being fixed.
- **`Set<PersonIntendedRole>` on `Person`** *(chosen)*.
- For the roster "✕" action specifically: **keep it as full `Project.people` deletion** (the pre-existing behavior, unchanged) vs. **narrow it to "remove this one role"** *(chosen, confirmed via a direct question — see above)*.

**Reason for Choice:** `Set<PersonIntendedRole>` is the minimal schema change that makes "reuse an existing person under a second role" a real, first-class operation rather than a workaround, and keeps the single-source-of-truth property `CLAUDE.md` already establishes: one field, on the one type that actually has the identity in question, is the only place this state lives.

**Consequences (real, not hypothetical):** this changes `PersonEntity`'s persisted shape from an optional scalar to a mandatory array column, which is **not** a SwiftData lightweight-migratable change — confirmed the hard way: the real app crashed on launch against this session's own already-existing local dev store (`NSCocoaErrorDomain 134110`, "Cannot migrate store in-place: Validation error missing attribute values on mandatory destination attribute"). Fixed by deleting the local dev container's SwiftData store (`~/Library/Containers/com.autocue.AutoCue/Data/Library/Application Support/default.store*`) and letting the app recreate it fresh — acceptable and expected at this pre-ship stage (no real users, no migration plan exists yet, `ROADMAP.md` D15 is where packaging/distribution concerns like this get addressed for real), but discards this session's own manually-entered test data in that store. No production migration path is implied or needed by this entry; if a schema change like this happens again post-D15 (a real shipped store with real user data), it will need an actual `SchemaMigrationPlan`, not a delete-and-recreate — flagged here so that's not rediscovered from scratch later. `Person.intendedRole`'s few remaining call sites (`PersonEditorSheet`'s `initialIntendedRole` pre-fill, `PersonMapperTests`, `PersonTests`) updated for the plural field; `DeletePartyResult`/`referenceLocations` and everything else touching `Person` identity (not roles) is unaffected.

## 2026-08-11 — `SharpCheckboxToggleStyle`'s `Color.clear` fill silently broke hit-testing for the unchecked state only — traced to root cause, not patched around

**Decision:** `SharpCheckboxToggleStyle.box(isOn:)`'s unchecked-state fill changes from `Color.clear` to `surface.background` — always a real, opaque fill in both states, never literally zero-alpha. `.contentShape(Rectangle())` is also applied directly to the box itself, not only to the outer `Button`, as defense in depth.

**Context:** The user's manual review of the immediately-preceding `SharpCheckboxToggleStyle` fix (above) found a real, asymmetric bug: tapping the checkbox glyph itself only toggled ON→OFF, never OFF→ON, while tapping the label text worked in both directions. The user explicitly asked for the actual view-hierarchy/hit-testing cause to be traced before patching, flagging that the asymmetry itself was a real clue (a generic missing-`.contentShape` bug would affect both directions equally).

**Root cause, confirmed by tracing the code, not guessed:** the unchecked state's box was drawn as `Rectangle().fill(Color.clear)` plus a `strokeBorder` (a thin 1pt ring only) — genuinely zero-alpha over its entire interior. `.contentShape(Rectangle())` was already applied to the outer `Button`, but on macOS this does not reliably override a nested, fully-transparent fill's own hit-testing exclusion for a `.plain`-styled `Button` with a custom multi-layer `ZStack` label — the interior, aside from the thin ring, simply wasn't tappable. The checked state's fill (`Theme.Colors.accent`, fully opaque) has real pixels to hit-test against directly, which is exactly why toggling OFF via the box worked while toggling ON via the box didn't — the *only* structural difference between the two states was real-fill-vs-zero-alpha-fill, matching the reported asymmetry exactly.

**Alternatives Considered:**
- **Add more/different `.contentShape` calls without changing the fill.** Rejected once the root cause was actually traced — the ancestor `Button` already had `.contentShape(Rectangle())`; the problem was the zero-alpha fill specifically, not a missing content-shape declaration, so stacking more of the same modifier wouldn't have addressed the actual cause.
- **`Color.clear` replaced with a technically-non-zero but visually-imperceptible opacity (e.g. `.opacity(0.001)`).** A well-known workaround for this exact class of SwiftUI/macOS bug. Considered, but rejected in favor of the next option, which achieves the same hit-testing guarantee without an arbitrary near-zero magic number.
- **`surface.background` as the unchecked fill** *(chosen)* — always genuinely opaque (alpha 1), and visually indistinguishable from "no fill" specifically because it matches the surrounding screen's own background color at every real call site on this project.

**Reason for Choice:** `surface.background` is both semantically honest (the box's interior really is filled with *something*, matching the page it sits on) and robust regardless of whatever AppKit-level hit-testing quirk caused `Color.clear` to be excluded — it doesn't depend on a near-zero-opacity magic number continuing to be treated as "present" by a future OS/SwiftUI version.

**Consequences:** Both checked and unchecked states now have real, opaque, identically-shaped tappable regions. Standing lesson, generalized from `.tint()`'s own finding immediately above in this log: a `Color.clear` fill inside a custom `Button`-based control on macOS should not be assumed hit-testable just because an ancestor declares `.contentShape(_:)` — verify against a real click, not just the API contract.

## 2026-08-12 — D8 silence-detection accuracy: 1 frame (not a fixed time value), verified by a two-tier test suite

**Decision:** Before D8 implementation begins, its acceptance criteria are corrected from the vague "detected boundaries fall within a defined sample tolerance" to a concrete target: **detected cue boundaries must be accurate to within 1 frame of the project's configured `Setup.timecodeFrameRate`** (`SPEC.md` §4.9), not a fixed millisecond or sample-count number. `SilenceDetector` must convert "1 frame" into a sample-count tolerance at run time from the `AudioAsset`'s actual sample rate and the configured `TimecodeFrameRate`'s real FPS — never a hardcoded constant. Separately, test coverage for this criterion is split into two required tiers: synthetic buffers with known clean loud/silent transitions (as originally scoped), **plus** a small library of real, hand-verified audio fixture clips, each isolating one hard scenario a synthetic buffer doesn't exercise — a gradually fading-in cue, a cue mixed quietly under ambient sound, two cues separated by a short non-silent gap — each with a known ground-truth boundary timecode.

**Context:** Reviewing D8's acceptance criteria ahead of planning surfaced two real gaps, not stylistic ones. First, "a defined sample tolerance" was never actually defined — nothing in `SPEC.md` §4.11 or `ROADMAP.md` D8 stated a concrete number, leaving `SilenceDetector`'s own test suite with no fixed target to assert against, and leaving open the question of whether that tolerance should be one fixed sample/millisecond count across every project regardless of frame rate (it shouldn't — see Alternatives, below). Second, and more substantively: `SPEC.md` §4.11's own "Ambience/room tone vs. silence" section already documents, from research recorded elsewhere in this log around the normalization-vs-adaptive-thresholding question, that a level-threshold detector cannot semantically distinguish quiet music from room tone or ambient noise — that's deliberately left to human review, not solved at the DSP layer. A synthetic buffer with a clean, artificially generated loud/silent transition never actually tests that risk at all; it only proves the detector can find an edge that a human ear would find trivially too. The real risk this section already acknowledges — quiet, gradually-entering, or background-mixed music — is exactly the case the originally-scoped test tier never covered.

**Alternatives Considered:**
- **A fixed tolerance in milliseconds or samples, e.g. "±20ms" or "±1000 samples at 48kHz," applied uniformly regardless of project frame rate.** Rejected — a fixed time value doesn't correspond to anything the user actually perceives as "accurate": the user's own frame of reference for boundary precision is the frame grid they're editing against (`Setup.timecodeFrameRate`, §4.9), which already varies per production (24/25/29.97/30fps) for real reasons (matching a production's actual edit timeline, §4.9's own reasoning). A fixed millisecond number would be simultaneously too loose at some frame rates and too tight at others, and a fixed sample-count number would additionally silently stop meaning "1 frame" the moment two projects use different sample rates.
- **1 frame at the project's configured `TimecodeFrameRate`, converted to a sample-count tolerance at run time** *(chosen)* — ties the accuracy guarantee to the same unit the user already reasons about boundaries in, and to `TimecodeFrameRate`'s existing "Real FPS" table (§4.9) rather than inventing a second, parallel precision concept.
- **Leave test coverage at synthetic-only, treat real hard cases as a manual/exploratory QA concern rather than a required automated tier.** Rejected — `CLAUDE.md` rule 6 already requires every package be tested against real fixtures, not just synthesized ones, and the specific failure modes at risk here (fade-ins, quiet mixes, short gaps) are exactly the kind of thing a manual pass is likely to sample inconsistently or skip once time is short; a required, repeatable automated tier is the only way this risk actually stays covered as the codebase evolves.
- **Synthesize the hard-case fixtures programmatically (e.g. a sine tone faded in over N seconds, mixed with generated pink noise) instead of sourcing real audio.** Rejected — a synthetic fade-in or synthetic quiet-mix is still a clean, parametrically-generated signal with none of the actual spectral/dynamic messiness of real scored material; it would prove the detector handles the *shape* of these scenarios without proving it handles what they actually sound like in practice, which is the entire point of adding this tier. Real excerpts from past scoring work, with boundaries the project owner has already determined by ear, are the only fixtures that genuinely test this.

**Reason for Choice:** The 1-frame target is the smallest unit of precision the app's own UI (`Timecode`'s `HH:MM:SS:FF` display, §4.9) can even show, making it the natural, non-arbitrary accuracy bar; expressing it in frames rather than fixed time keeps the target meaningful across every frame rate the app already supports rather than picking one project's convention as an implicit default. The two-tier test approach directly follows from `SPEC.md` §4.11's own already-documented acknowledgment that ambience/quiet-music discrimination is a real, unsolved-at-the-DSP-layer risk — a test suite that never exercises that risk would leave the codebase's only evidence of correctness pointed at the case that was never actually in doubt.

**Consequences:**
- `ROADMAP.md` D8's Acceptance Criteria and Testing Requirements are updated in the same change (this entry's originating change) to state the 1-frame target explicitly and to require both test tiers.
- `SPEC.md` §4.11 gains a new "Boundary accuracy target" subsection stating the same 1-frame contract, so `SilenceDetector`'s implementation (`ROADMAP.md` D8/T8.3) has an unambiguous, already-specified target rather than inferring one from the roadmap alone.
- **Real, external prerequisite, flagged explicitly rather than left implicit:** the real-audio fixture clips for the hard-case tier must be supplied by the project owner (real excerpts from past scoring work, with ground-truth boundaries he's determined by ear) — the same category of required external input T8.2's fixture WAV (real `cue`/`labl`/`ltxt`/`bext` chunks) already is for that Task. D8's silence-detection test suite is not complete until these are supplied; this is not something to synthesize or invent as a substitute.
- This entry is documentation-only — no `SilenceDetector` implementation exists yet at the time of this change; D8 has not started.

**Full detail:** `ROADMAP.md` D8 (Acceptance Criteria, Testing Requirements); `SPEC.md` §4.11 ("Boundary accuracy target").

This is accepted as correct, not a shortcoming to fix later: the alternative (fixtures in git) is the actual risk being avoided.

## 2026-08-13 — D8's `SilenceDetector` gains a second, spectral flux-based onset-refinement stage; speech/music discrimination explicitly ruled out

**Decision:** `SilenceDetector` (`ROADMAP.md` D8/T8.3) becomes a two-stage pipeline, not RMS-threshold alone. Stage 1 is unchanged from `SPEC.md` §4.11's original contract — windowed RMS level-threshold detection locates the rough candidate region for each boundary. Stage 2, new in this pass, is **spectral flux-based onset refinement**: within the stage-1 candidate region, the frame-to-frame change in FFT magnitude spectrum (a standard MIR onset-detection technique, computed via `Accelerate`'s existing vDSP FFT support) is used to relocate the boundary to the actual moment of spectral/musical change, rather than leaving it at an arbitrary RMS level-crossing point. Two new `AnalysisSettings` fields govern it: `spectralFluxRefinementSearchWindowSeconds` (default `0.5`, how far stage 2 searches around the stage-1 boundary) and `spectralFluxOnsetSensitivity` (default `0.3`, normalized peak-picking sensitivity). If no clear flux peak is found in the search window, stage 2 leaves the stage-1 boundary unchanged. Scope is deliberately bounded to cue-*start* (silence→sound) boundaries — cue-end/reverb-tail timing stays governed entirely by the existing `tailToleranceDb`/`tailCapSeconds` mechanism, unchanged by this addition. **Separately, and just as deliberately: speech/music discrimination and any ML-based/trained classification are explicitly ruled out of `SilenceDetector`'s scope, now and going forward.**

**Context:** `SPEC.md` §4.11's "Ambience/room tone vs. silence" section already documented a known, real weakness of pure RMS-threshold detection: it cannot semantically distinguish quiet music from ambience, and — the more specific failure this entry addresses — for a cue that fades in gradually or is mixed in deliberately quiet, there is *no single clean level-crossing moment at all*, since the level ramps up by construction. Wherever the RMS threshold sits, the crossing point it finds is somewhat arbitrary relative to where a human editor would actually place the cue's start, and empirically tends to land late. This is exactly the hardest case the real-audio fixture tier (entry above, 2026-08-12) was introduced specifically to catch — a fade-in or quiet-mix fixture is precisely the scenario where RMS-threshold-alone is expected to underperform. Researching techniques better suited to this specific failure mode (locating a precise onset moment, not classifying content) led to spectral flux — a well-established, non-ML MIR onset-detection technique that directly targets "where did the spectral content actually start changing," which is a different and more tractable question than "is this section music or ambience."

**Alternatives Considered:**
- **Leave `SilenceDetector` at RMS-threshold-only, accept that fade-ins/quiet mixes land within a looser tolerance.** Rejected — this doesn't fix the underlying problem, only widens the tolerance band around a boundary placement that's still arbitrary; the real-fixture hard-case tier exists specifically to catch this failure, so leaving it unaddressed would mean deliberately shipping a known-inaccurate result for a case already flagged as a real risk.
- **Machine-learning-based onset/boundary detection (e.g. a trained onset-detection or music/speech-segmentation model).** Rejected — no training data exists or is planned for this app, adding an ML dependency conflicts with `CLAUDE.md`'s "fewer, well-separated moving parts," "offline-only," and App Store-eligibility constraints (model packaging/size, no dynamically loaded code) for a problem a much simpler, deterministic DSP technique already solves well; and see the speech/music point below — the specific thing ML classification would most plausibly buy here (distinguishing speech from music) isn't a real problem this app has at all.
- **Speech/music discrimination as part of stage 2 or a future stage** *(explicitly considered and rejected)* — this was raised as a hypothetical during the spectral-flux research (spectral-flux-adjacent MIR literature commonly pairs onset detection with speech/music segmentation) and explicitly ruled out: AutoCue's audio imports are music-only, sourced from film/TV scoring work — they never contain dialogue or sound design content requiring discrimination from music. Building a speech/music classifier would be solving a problem this app's actual input material doesn't present, which is exactly the premature-generalization `CLAUDE.md` rule 7 warns against, just discovered here through research rather than through writing the code first.
- **Spectral flux-based onset refinement as a second stage, applied only within the RMS-located candidate region** *(chosen)* — a deterministic, well-understood, `Accelerate`-computable technique that directly targets the actual failure mode (imprecise onset timing on gradual/quiet cues) without overreaching into a classification problem this app doesn't have.

**Reason for Choice:** Spectral flux is the narrowest fix that actually addresses the documented failure mode — it answers "when did the spectral content really start changing" without attempting to answer "is this music" (already correctly left to human review per §4.11's existing "Ambience/room tone" rule) or "is this speech" (not a real question for this app's input material at all). Keeping it as a strict second stage — refining, never replacing, stage 1 — preserves the entire existing RMS-threshold contract (calibration modes, reverb-tail handling, merge tolerance) rather than requiring it to be redesigned.

**Consequences:**
- `ROADMAP.md` D8/T8.3's task description and Acceptance Criteria are updated in the same change to scope in the two-stage pipeline, including synthetic coverage for stage 2 specifically (a synthetic gradual-fade-in buffer, and a flat-spectrum control buffer proving the fallback-to-stage-1 behavior) and an explicit goal for the real-fixture hard-case tier: proving stage 2 measurably improves (or at least never worsens) accuracy on the fade-in/quiet-mix fixtures specifically, relative to stage 1 alone.
- `SPEC.md` §4.11 gains the two new `AnalysisSettings` fields (`spectralFluxRefinementSearchWindowSeconds`, `spectralFluxOnsetSensitivity`) and a new "Spectral flux-based onset refinement" subsection stating the full stage-2 contract, its cue-start-only scope, its fallback behavior, and the speech/music-discrimination scope boundary — so a future session reads this as an already-settled boundary, not an open question to re-litigate or a gap to fill.
- This entry is documentation-only — no `SilenceDetector`/spectral-flux implementation exists yet at the time of this change; D8 has not started.

## 2026-08-13 — Onset refinement upgraded from plain spectral flux to SuperFlux specifically; offset detection formally, permanently excluded from any onset-detection technique

**Decision:** Two corrections to the entry immediately above, made before any implementation exists — prompted by a further research pass specifically requested to make the algorithm design precise enough to implement and debug against without re-deriving the reasoning:

1. **Stage 2 uses SuperFlux (Böck & Widmer, "Maximum Filter Vibrato Suppression for Onset Detection," DAFx 2013), not plain spectral flux.** SuperFlux adds one mechanism on top of plain spectral flux: a maximum filter across neighboring log-frequency bins, applied to the log-compressed magnitude spectrogram, before the half-wave-rectified frame-to-frame novelty difference is computed. This directly suppresses false-positive onsets caused by vibrato/tremolo — natural pitch/amplitude wobble on a sustained note, which plain spectral flux cannot distinguish from a genuine re-attack because both look like a frame-to-frame spectral increase. This matters concretely for this app: its actual input material is dominated by sustained strings, legato brass/woodwind swells, and vocal lines — exactly the instrumentation vibrato/tremolo occurs in — not a hypothetical edge case. `AnalysisSettings.spectralFluxOnsetSensitivity`/`spectralFluxRefinementSearchWindowSeconds` are renamed to `superFluxOnsetSensitivity`/`superFluxRefinementSearchWindowSeconds` (meaning unchanged), and a new field, `superFluxMaxFilterBandwidthBins` (default `3`), controls the max-filter neighborhood width — the parameter the original entry flagged as possibly needed but didn't yet specify.
2. **Offset (cue-*end*) detection is formally and permanently excluded from SuperFlux, plain spectral flux, and any onset-detection-family technique.** The original entry already scoped stage 2 to cue-starts only, but didn't state the *reason* precisely — this entry adds it. Offsets continue to use the existing two-threshold reverb-tail mechanism (`tailToleranceDb`/`tailCapSeconds`), completely unchanged by this pass.

**Context:** the prior entry's spectral-flux description was accurate as a *name* but not detailed enough to implement or debug against without re-deriving the mechanism from scratch — a documentation-precision gap flagged before D8 begins, the same "close the gap before the milestone starts" pattern already used ahead of D6/D7 (see the 2026-08-09 and 2026-08-11 Definition-of-Done entries above). Researching plain spectral flux's actual failure modes against this app's real material surfaced two findings:
- Plain spectral flux is documented in the MIR literature to false-positive on vibrato/tremolo-heavy material, because natural pitch/amplitude modulation shifts a note's energy slightly in frequency from frame to frame, which a naive frame-to-frame magnitude difference reads as a spectral change indistinguishable from a real onset.
- Onset-detection-family novelty functions — SuperFlux included — are asymmetric by design: they half-wave-rectify away energy *decreases*, keeping only increases, because that's definitionally what an attack transient is. Applying the same technique to locate an *offset*, even inverted to look for decreases, would at best find the start of a decaying tail's spectral change (the moment direct sound stops and the tail begins dominating) rather than the point the tail has decayed to the perceptually-true end a human editor would mark. General onset-detection surveys treat offset detection as a separate, harder, not-solved-by-the-same-techniques problem — Bello, Daudet, Abdallah, Duxbury, Davies & Sandler, "A Tutorial on Onset Detection in Music Signals," *IEEE Transactions on Speech and Audio Processing*, 2005, is cited here as exactly that kind of general onset-detection tutorial making this onset/offset distinction, not as a dedicated offset-detection study.

**Alternatives Considered:**
- **Keep plain spectral flux; tune `spectralFluxOnsetSensitivity` down to be less sensitive on vibrato-heavy material.** Rejected — sensitivity is a single global scalar; it can't distinguish "a real quiet onset" from "vibrato-driven flux on a sustained note," because both produce comparably small flux values. Detuning it to suppress vibrato false-positives would also suppress genuinely quiet real onsets, trading one failure mode for another rather than fixing either.
- **Apply the onset novelty function (SuperFlux or plain), inverted, to offsets too — "reuse the one detector for both."** Rejected, and stated here as a permanent architectural boundary, not a case-by-case judgment call — see the offset-timing research finding above. Inverting the rectification doesn't fix the underlying issue: the largest energy/spectral decrease in a decaying passage is at the *start* of the decay, not its perceptual end, so an inverted onset detector would systematically mark cue ends too early, at the reverb-tail's onset. This is a structural limitation of the technique family, not a tuning problem — no choice of sensitivity or search window fixes it.
- **SuperFlux for onsets; the existing two-threshold reverb-tail mechanism for offsets, unchanged** *(chosen)* — each mechanism is used for the problem it's actually suited to: SuperFlux for precise, vibrato-robust onset timing, and simple sustained-threshold tracking for offsets, which doesn't need spectral analysis at all, since a decaying tail's *energy* (not its spectral content) is what determines when a human editor considers it inaudible.

**Reason for Choice:** SuperFlux directly targets this app's actual, documented false-positive risk (vibrato/tremolo on sustained film-score material) with a published, verified result (up to 60% false-positive reduction on solo strings/sung vocals, without missing genuine onsets) rather than a generic "spectral flux, but a different name" swap. Keeping offsets on the existing, unrelated two-threshold mechanism avoids importing onset-detection's structural early-offset bias into a part of the pipeline that doesn't have that problem today, and preserves the entire existing reverb-tail contract (already-defined `tailToleranceDb`/`tailCapSeconds` values) without requiring it to be redesigned.

**Consequences:**
- `ROADMAP.md` D8/T8.3 is updated in the same change: the task description names SuperFlux specifically (not generic "spectral flux") and describes its actual mechanism (log-frequency spectrogram → log compression → max filter → half-wave-rectified novelty difference); Acceptance Criteria now test onset accuracy and offset accuracy against the real-fixture hard-case tier as two explicitly independent assertions, so a future regression in one can't hide behind the other passing; synthetic coverage gains a vibrato/tremolo-modulated buffer proving stage 2 does not false-positive on it; the real-fixture manifest convention gains an optional `groundTruthEndOffsetSeconds` field for clips with a decaying tail.
- `SPEC.md` §4.11 is updated in the same change: the `AnalysisSettings` table renames the two existing SuperFlux-related fields and adds `superFluxMaxFilterBandwidthBins`; the "Spectral flux-based onset refinement" subsection is replaced with a fully-specified "SuperFlux-based onset refinement" subsection giving the signal chain step by step (log-frequency spectrogram, log compression, max filter, half-wave-rectified novelty function, peak-picking); and a new "Why offset detection does not use SuperFlux or any onset-detection technique" subsection states the permanent architectural boundary, cites the research finding, and cross-references the unchanged reverb-tail mechanism as the correct offset approach.
- This entry, like the one it corrects, is documentation-only — no `SilenceDetector` implementation exists yet; D8 has not started.

**Full detail:** `ROADMAP.md` D8/T8.3 (task description, Acceptance Criteria, Testing Requirements, real-fixture manifest convention); `SPEC.md` §4.11 ("SuperFlux-based onset refinement," "Why offset detection does not use SuperFlux or any onset-detection technique," `AnalysisSettings` table).

## 2026-08-13 — RMS mechanism gains a decoupled hop size and dB-domain threshold-crossing interpolation, closing a real offset-accuracy gap the two SuperFlux entries above left unresolved

**Decision:** `AnalysisSettings` gains a new field, `analysisWindowHopMilliseconds` (default `10.0`), decoupling how often an RMS window is computed from `analysisWindowMilliseconds` (the window's *length*, unchanged at `50.0`ms). Windows now overlap by default (`50.0`ms windows every `10.0`ms). Every RMS threshold crossing this contract defines — the main `silenceThresholdDb` gap boundary and the stricter `tailToleranceDb` reverb-tail-truncation crossing alike — is now located by linear interpolation *in the dB domain* between the two window-center measurements straddling the threshold, rather than reported as the hop-quantized window the crossing happened to fall in.

**Context:** the two SuperFlux entries above (this same date) made cue-*start* accuracy precise by adding a second, spectrogram-resolution stage, and correctly ruled that same stage out for cue-*ends* on structural grounds. What neither entry checked is whether the *first* stage — windowed RMS, the only stage offsets ever get — was actually precise enough on its own to hit the 1-frame target (`33.3`–`41.7`ms depending on frame rate) once nothing downstream could correct for it. It wasn't: as originally specified, `analysisWindowMilliseconds` defaulted to `50.0`ms with no documented hop (implying hop == window, i.e. non-overlapping windows) and no documented interpolation, meaning a threshold crossing could only be reported to the nearest window edge — up to `50.0`ms of quantization error, worse than even the loosest 1-frame tolerance. This was invisible for onsets, because SuperFlux's stage 2 relocates the boundary independently of stage 1's precision; it was a real, load-bearing gap for offsets, which have no equivalent second pass. This was flagged and required resolving, by design, before D8 begins — the same "close the gap before the milestone starts" pattern as every other entry in this run.

**Alternatives Considered:**
- **Shrink `analysisWindowMilliseconds` itself (e.g. to `10.0`ms) instead of adding a separate hop.** Rejected — the window length exists specifically to average out noise/transients (this section's original reason for using RMS over instantaneous samples at all); shrinking it directly would trade away that stability for resolution instead of getting both, which a decoupled hop achieves without the tradeoff.
- **Hop reduction only, no interpolation.** Considered viable on its own — at the chosen `10.0`ms default, hop-quantization alone already bounds error to `10.0`ms, comfortably under the tightest `33.3`ms tolerance with better than 3× margin. Not rejected as insufficient, but interpolation was added anyway: it's effectively free (two-point linear interpolation, not a loop over samples), it removes the residual quantization bias entirely rather than leaving a nonzero worst-case bound, and it keeps the mechanism robust if a project is ever configured with a coarser custom hop for performance reasons on an unusually long file.
- **A spectral/novelty-based offset refinement stage instead (revisiting the SuperFlux-for-offsets question from the entry above).** Not reconsidered — already ruled out on structural grounds (offsets systematically land at the reverb tail's onset under any flux-family technique), and unnecessary here regardless: the actual gap was RMS-mechanism resolution, not a missing second stage, and a plain RMS-domain fix closes it without reopening the onset/offset-separation decision.
- **Hop size plus dB-domain interpolation** *(chosen)* — closes the gap with a plain RMS/energy-domain technique, consistent with offsets deliberately staying off any onset-detection-family (spectral/novelty) approach, and gives comfortable margin under the tolerance rather than landing at its edge.

**Reason for Choice:** this is the narrowest fix that actually closes the identified gap — it doesn't touch calibration, reverb-tail thresholds, or the onset/offset architectural split, all already correctly designed; it only fixes the RMS mechanism's own time resolution, which was the one piece nobody had actually checked against the 1-frame target once SuperFlux took onsets off the table.

**Consequences:**
- `SPEC.md` §4.11 gains the `analysisWindowHopMilliseconds` field (table) and a new "RMS time resolution and threshold-crossing interpolation" subsection giving the mechanism in full — hop/window decoupling, the dB-domain interpolation formula and why dB rather than linear amplitude, the margin arithmetic against the 1-frame tolerance, and a performance note on the ~5× increase in RMS window count. "Boundary accuracy target," "Reverb tails," and "Why offset detection does not use SuperFlux..." are each updated with a cross-reference so the tolerance claim they already made is now actually substantiated for cue ends, not merely asserted.
- `ROADMAP.md` D8/T8.3's task description and Acceptance Criteria are updated in the same change: the `SilenceDetector` description now names the overlapping-hop/interpolation mechanism explicitly, and a new synthetic Acceptance Criterion requires a non-hop-aligned transition buffer specifically, so a naive hop-quantized-only implementation (which a hop-boundary-aligned test buffer could pass by coincidence) is actually caught.
- This entry, like the two above, is documentation-only — no `SilenceDetector` implementation exists yet; D8 has not started.

**Full detail:** `ROADMAP.md` D8/T8.3 (task description, Acceptance Criteria); `SPEC.md` §4.11 ("RMS time resolution and threshold-crossing interpolation," "Boundary accuracy target," `AnalysisSettings` table).

## 2026-08-14 — Stage 2 peak-picking made locally adaptive (retiring `superFluxOnsetSensitivity`); STFT window specified as Hann; three techniques researched and deliberately not adopted

**Decision:** Two corrections to `SPEC.md` §4.11, made before any implementation exists — prompted by a further research pass into CCRMA/Stanford spectral-audio-processing and MIR literature (Julius O. Smith's *Spectral Audio Signal Processing*, CCRMA's MIR Workshop onset-detection material, cross-checked against Bello et al. 2005, already cited):

1. **SuperFlux stage 2's peak-picking becomes locally adaptive, replacing the fixed-global-threshold behavior of `superFluxOnsetSensitivity`.** `superFluxOnsetSensitivity` is retired outright, not kept alongside the replacement. Three new `AnalysisSettings` fields govern the new behavior: `superFluxAdaptiveThresholdWindowSeconds` (default `0.1`s — length of the local window, centered on a candidate frame, over which the novelty function's local median is computed), `superFluxAdaptiveThresholdMultiplier` (default `1.5`, dimensionless `λ` — multiplicative margin over the local median; the primary adaptive-sensitivity control), and `superFluxAdaptiveThresholdOffset` (default `0.05`, `δ` — an additive floor expressed as a fraction of the current search window's peak novelty value, not an absolute novelty unit, since that scale is signal-level-dependent). A candidate frame is accepted only if it is a local maximum on the novelty function *and* clears `median(novelty, window) × λ + δ × peakNoveltyInSearchWindow`.
2. **The SuperFlux STFT step (signal chain step 1) is now explicitly specified as using a Hann window** — previously unspecified. This matches Böck & Widmer's own reference implementation and standard practice for general-purpose (non-sinusoid-resolving) spectral analysis; SuperFlux's coarse, ~24-bands-per-octave log-frequency novelty function doesn't need a window family tuned for resolving closely-spaced partials.

**Context:** the two 2026-08-13 entries above made onset *timing* precise (SuperFlux) and separately made offset *timing* precise (RMS hop/interpolation), but neither checked whether stage 2's *peak-acceptance* decision itself was well-specified across a whole file's varying conditions. It wasn't: `superFluxOnsetSensitivity` is one fixed, global (`0`...`1`) value applied uniformly everywhere, which is exactly the category of limitation stage 1's calibration already solved once — a single fixed `silenceThresholdDb` doesn't hold up across a long file's changing conditions, which is why `noiseFloorReestimationIntervalSeconds` exists at all. Stage 2 had an unaddressed version of the same problem: the novelty function's baseline level and variance genuinely differ between a dense, loud passage and a sparse, quiet one, so one fixed sensitivity can't be well-tuned for both — too permissive and it over-triggers during busy passages, too strict and it misses real onsets during quiet ones. This was flagged and required resolving, by design, before D8 begins — the same "close the gap before the milestone starts" pattern as every other entry in this run.

Separately, the STFT window function — a real, load-bearing parameter of any spectral analysis, and one the paper's reference implementation actually specifies — had been left unstated in the signal chain description, an omission of the same kind (a precise-in-the-literature value not yet transcribed into this contract) already flagged and fixed for the filterbank resolution (~24 bands/octave) in the 2026-08-13 entry above.

This same research pass also considered three further techniques and deliberately did not adopt any of them:
- **Complex-domain/phase-based onset detection** (magnitude *and* phase deviation, not magnitude alone). A real technique — it can theoretically catch onsets with minimal magnitude change but a genuine phase discontinuity. Not adopted: phase estimates are well-documented in the literature as noisier and more fragile in practice than magnitude-based flux methods, which is exactly why flux-family techniques (SuperFlux included) are the more robust, commonly-deployed choice for this kind of material. Not adopted without evidence, from real-fixture testing, that SuperFlux is actually insufficient — a hypothetical improvement, not a response to an observed failure.
- **Full multi-band, separate-decision-then-fusion onset detection** — running onset detection independently per frequency band and fusing the per-band decisions. A legitimate technique family, but SuperFlux's own signal chain already computes its novelty contribution per log-frequency bin (step 4, `Σ_k HWR(...)`) before summing into one novelty value — much of the same benefit multi-band fusion aims for is already captured by that per-bin computation. A second, separately-tuned fusion layer on top would be redundant with a mechanism SuperFlux already has, not a genuine improvement.
- **Double-windowing for the RMS envelope mechanism** — a technique for reducing envelope-follower transition artifacts by combining two window lengths. A real technique, but not adopted here because it would be solving an already-solved problem: the existing `analysisWindowHopMilliseconds`/dB-domain threshold-crossing interpolation mechanism (2026-08-13 entry above) already closes the RMS timing-accuracy gap with several times the required margin (hop-quantization alone bounds error to `10.0`ms against a `33.3`ms tightest tolerance, before interpolation is even applied) — there is no remaining accuracy gap for a second windowing mechanism to close.

**Alternatives Considered:**
- **Keep `superFluxOnsetSensitivity`, add the three adaptive-threshold fields alongside it, let an implementation detail decide how they combine.** Rejected — a fixed global value and a locally-adaptive threshold are two different, non-composable models of the same accept/reject decision; leaving both in the schema would make it ambiguous which one actually governs acceptance at implementation time, deferring a design decision that belongs in this contract, not in `ROADMAP.md` T8.3's implementation.
- **Express `superFluxAdaptiveThresholdOffset` as an absolute novelty-function unit (matching how `silenceThresholdDb` is an absolute dBFS unit) instead of a fraction of the search window's peak.** Rejected — unlike `silenceThresholdDb`, the novelty function has no fixed, signal-independent scale (its log-compression step, §4.11 step 2, still leaves the result dependent on the input's absolute level); an absolute default would need re-tuning per source loudness to remain meaningful, defeating the point of a documented default. Expressing it as a fraction of the current window's own peak keeps the field meaningful across arbitrarily different clip loudnesses without per-project tuning.
- **Leave the STFT window unspecified, as "an implementation detail."** Rejected — the window function measurably affects spectral leakage and therefore the shape of the novelty function stage 2 depends on for accurate peak-picking; per this section's own established convention (already applied to the filterbank resolution and the noise-floor statistic), a value that's precise-in-the-source-literature and load-bearing for correctness gets documented here, not left implicit.
- **Adaptive local peak-picking (window/multiplier/offset) plus an explicit Hann window** *(chosen)* — closes both a real, previously-unaddressed precision gap (peak-picking) and a real, previously-unstated implementation parameter (the window function), consistent with how every other precision gap in this run has been resolved: document the mechanism fully, don't leave it to be re-derived or guessed at implementation time.

**Reason for Choice:** the adaptive-threshold fix is the direct structural analogue of a fix this contract already made once, for stage 1's calibration — recognizing that "one global value can't serve both loud and quiet local conditions" is the same insight, applied to the one place in stage 2 it had been missed. The Hann window addition costs nothing (it doesn't change any already-defined default or add new complexity) and closes a real specification gap before an implementer would otherwise have had to choose one unprompted. The three rejected techniques were each evaluated on their actual merit against this app's real material and existing mechanisms, not dismissed by default — each has a stated, specific reason it doesn't apply here, not a generic "too complex."

**Consequences:**
- `SPEC.md` §4.11 is updated in the same change: the `AnalysisSettings` table retires `superFluxOnsetSensitivity` and adds `superFluxAdaptiveThresholdWindowSeconds`/`superFluxAdaptiveThresholdMultiplier`/`superFluxAdaptiveThresholdOffset`; a new "Adaptive local peak-picking" subsection gives the acceptance formula, the edge-padding treatment for frames near the search window's boundary, and the explicit retirement rationale; signal-chain step 1 now states the Hann window and why; step 5 ("Peak-picking") is renamed "Adaptive local peak-picking" and points to the new subsection; the fallback paragraph is reworded from "no peak clears `superFluxOnsetSensitivity`" to "no candidate frame clears the adaptive threshold."
- `ROADMAP.md` D8/T8.3 is updated in the same change: the task description now names the Hann window and the adaptive peak-picking mechanism (and its three governing fields) instead of the retired single-sensitivity field; a new synthetic Acceptance Criterion requires a single buffer combining a loud/dense passage and a quiet/sparse passage, asserting genuine onsets in *both* are correctly detected — the specific failure mode a fixed global sensitivity value cannot handle in both regions at once — with a fixed-sensitivity control expected to fail at least one side of that assertion; the Testing Requirements paragraph's synthetic-buffer list gains this combined buffer alongside the existing fade-in/flat-spectrum/vibrato buffers.
- This entry, like the three above it in this run, is documentation-only — no `SilenceDetector` implementation exists yet; D8 has not started.

**Full detail:** `ROADMAP.md` D8/T8.3 (task description, Acceptance Criteria, Testing Requirements); `SPEC.md` §4.11 ("Adaptive local peak-picking," signal-chain step 1, `AnalysisSettings` table).

## 2026-08-14 — SuperFlux's own STFT hop size pinned as `superFluxHopSeconds` (default `10`ms), closing a gap the entry above left unclosed

**Decision:** `AnalysisSettings` gains `superFluxHopSeconds` (default `0.01`s, `10`ms) — how often stage 2's STFT frame (and therefore its novelty-function value) is computed, matching Böck & Widmer's own reference configuration (44.1kHz sample rate, hop size `441` samples = `10`ms, ~100 frames/second). This is pinned as an explicit documented default in the `AnalysisSettings` table, not left as a T8.3 implementation-time-only value the way the filterbank resolution (~24 bands/octave) correctly still is.

**Context:** raised as a direct question after the entry immediately above was accepted: that entry's new `superFluxAdaptiveThresholdWindowSeconds` field converts from seconds to a frame count using "the novelty function's own frame rate (the STFT hop used to build it)" — and that hop had never actually been given a value anywhere in this contract, despite the RMS mechanism's own hop having been pinned two entries earlier (2026-08-13) for exactly this reason: a hop size that determines a *reported boundary's* time-quantization is load-bearing for the 1-frame accuracy target, not an internal detail safe to leave open the way the filterbank-resolution value is. The "How each boundary type actually achieves this tolerance" subsection's claim that SuperFlux resolves "at a time resolution far finer than any RMS window" was, on inspection, resting on a number that was never actually specified anywhere — an unsubstantiated precision claim of exactly the kind this whole documentation pass exists to catch and close, just found one entry later than it should have been.

**Alternatives Considered:**
- **Leave the STFT hop as an implementation-time-confirmed value, same treatment as the filterbank resolution.** Rejected — the two aren't the same kind of value. Filterbank resolution affects spectral fidelity and therefore vibrato-suppression *quality*, not the temporal grid the final boundary is reported on; the STFT hop directly *is* that temporal grid. Leaving it open would mean the "meets the 1-frame target" claim for cue starts is still asserted rather than substantiated, the exact gap the RMS-hop entry (2026-08-13) already established as unacceptable for a load-bearing timing parameter.
- **Pin the hop, and also add a second, interpolation-style step on top of it (mirroring the RMS mechanism's dB-domain threshold-crossing interpolation) to remove the residual quantization bound entirely.** Considered, not adopted now — the RMS mechanism's own hop-only bound already left more than 3× margin under the tightest 1-frame tolerance, and interpolation was still added there because it was "effectively free" and removed a nonzero worst-case bound. The same margin math applies here (`10`ms hop vs. `33.3`ms tightest tolerance), so the *margin* argument for adding a further step is identically weak/strong in both cases — but unlike RMS's continuous threshold crossing, a peak-picked frame has no natural "point between two measurements" for linear interpolation to target; the analogous technique (parabolic/quadratic peak interpolation) is a distinct method, not a trivial port of the RMS technique. Deferred per `CLAUDE.md` rule 7 (no premature abstraction) until a real accuracy audit shows the plain hop-quantization margin insufficient — not added speculatively alongside a margin that already clears the bar.
- **Pin `superFluxHopSeconds` as an explicit default; no added interpolation step (for now)** *(chosen)* — closes the actual gap (an unpinned, load-bearing timing parameter) without manufacturing a second gap by importing a technique that isn't a natural fit and isn't yet motivated by any observed shortfall.

**Reason for Choice:** this is the narrowest fix for the actual problem raised — an unpinned timing parameter masquerading as an already-substantiated claim — using the exact same justification and margin-arithmetic standard already applied to `analysisWindowHopMilliseconds`, so the two hop-based mechanisms in this contract (RMS and SuperFlux) are now documented to the same standard of rigor rather than one being pinned and the other quietly left open.

**Consequences:**
- `SPEC.md` §4.11 gains the `superFluxHopSeconds` field (table) and a new "SuperFlux hop size and reported-boundary resolution" subsection (immediately after the signal-chain steps) giving the margin arithmetic and stating explicitly why no interpolation step is added on top, for now. Signal-chain step 1 now states the hop value alongside the already-stated Hann window. The `superFluxAdaptiveThresholdWindowSeconds` table row's frame-count conversion is reworded from "an implementation-time value" to a direct reference to `superFluxHopSeconds`. "How each boundary type actually achieves this tolerance" is reworded from the unsubstantiated "far finer than any RMS window" to the actual `10`ms figure and its margin against the tightest 1-frame tolerance.
- `ROADMAP.md` D8/T8.3's task description is updated in the same change to name `superFluxHopSeconds` and state why it's pinned rather than left implementation-time-only.
- This entry, like the four above it in this run, is documentation-only — no `SilenceDetector` implementation exists yet; D8 has not started.

**Full detail:** `ROADMAP.md` D8/T8.3 (task description); `SPEC.md` §4.11 ("SuperFlux hop size and reported-boundary resolution," signal-chain step 1, "How each boundary type actually achieves this tolerance," `AnalysisSettings` table).
