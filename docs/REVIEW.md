# AutoCue — Review Log

An append-only log, one entry per completed `ROADMAP.md` Deliverable (occasionally per significant Task, for a large Deliverable). This is where architecture/code-quality observations, technical debt, and refactoring suggestions actually get recorded — not left in a closed Claude Code session's memory, not scattered across commit messages nobody re-reads. `CONTRIBUTING.md` §1 requires an entry here as part of finishing a Deliverable; `docs/DefinitionOfDone.md` §6 makes it part of the Definition of Done, not optional polish.

**Rules for this file:**
- **Append, don't edit history.** If a later Deliverable reveals an earlier observation was wrong, add a new entry noting that — don't go back and rewrite the old one. The log's value is in showing what was actually known/believed at each point, including when that turned out to be incomplete.
- **Newest entry last**, so reading top-to-bottom follows the project's actual timeline.
- **Every entry uses the template below, all five fields** — an entry that skips "Technical Debt" because "there wasn't any" should say that explicitly, not omit the heading.

## Template

```markdown
## YYYY-MM-DD — Deliverable DN — <short title>

**Architecture observations:** Did the actual implementation match what CLAUDE.md/ROADMAP.md described going in? Any boundary that was harder to hold than expected, or easier?

**Code quality observations:** Anything about the resulting code worth flagging — good or bad — that isn't already obvious from reading it (a pattern worth repeating elsewhere, a shortcut taken under time pressure, a test that turned out to be more valuable than expected).

**Technical debt:** Anything deliberately deferred, any known gap, any place a future Deliverable will need to revisit this one's work. Reference the specific file/type, not just a vague concern.

**Refactoring suggestions:** Concrete, not vague — "rule of three" candidates (CONTRIBUTING.md §3) that are now two-of-three and worth watching, not "this could probably be cleaner."

**Follow-ups filed:** Any `// TODO(DN.T)` comments added, any `docs/DECISIONS.md` entries this Deliverable produced.
```

## 2026-08-08 — Pre-Implementation Architecture Review (Batches 1–4)

Not a `ROADMAP.md` Deliverable in the normal sense — this entry documents the four-batch review-and-correction pass performed on `CLAUDE.md`/`SPEC.md`/`ROADMAP.md` *before* Deliverable D1 (or, at the time, "Milestone 1") began, seeded here so the log has real history from day one rather than starting empty at the first feature Deliverable.

**Architecture observations:** The original architecture documents (single initial commit) were internally consistent enough to look complete on a first read, but contained several real contradictions that would only have surfaced mid-implementation: `CLAUDE.md` told Views both to never touch `@Query`/SwiftData *and* to use `@Query` for list views, in two different sections; the tech-stack table claimed "compiler-enforced module boundaries" for a `Features/` folder that lived inside the app target, where nothing actually enforced that; `AsyncStream` and Foundation's `Progress` were referenced as if interchangeable despite having incompatible concurrency models. None of these would have been caught by "does it compile" — they're the kind of thing that only shows up once two different sessions, months apart, each read a different half of a contradiction and built against it.

**Code quality observations:** Two small pieces of real, tested code were built ahead of schedule specifically to de-risk locked-in architectural bets rather than leave them as unverified assumptions: `Packages/ACCore` (SMPTE drop-frame `Timecode` arithmetic, 18 tests including a 3-hour-equivalent round-trip sweep) and `Packages/ACExport` (a `libxlsxwriter` feasibility spike, verified under real kernel-enforced App Sandbox via an ad-hoc-signed `.app` bundle, not just source-code review). Both are minimal scaffolds, not the real feature work — see the `Package.swift` header comment in each for the explicit "don't mistake this for Deliverable completion" note.

**Technical debt:** `ROADMAP.md`'s pre-restructuring milestones (M13–M25, M31, in the old numbering) still referenced the pre-`ACFeatures`-package `Features/...` path instead of `Packages/ACFeatures/Sources/ACFeatures/...` at the time of this entry — a known, tracked gap, not silently carried forward. **Refactoring suggestions:** None yet — no feature code exists to refactor. The two spike packages (`ACCore`, `ACExport`) will need to be merged into the real Deliverable D1–D3 / D11 package structure rather than treated as separate, permanent scaffolds; that merge is Deliverable D1's job, not a follow-up refactor after the fact.

**Follow-ups filed:** `docs/DECISIONS.md` — full set of entries covering the `MediaDuration` rename, `ACFeatures` package split, drop-frame timecode, `libxlsxwriter` validation, progress/cancellation contract, waveform architecture, deployment target, Views/`@Query` resolution, module dependency graph, navigation model, and document/window model (including its single-window-then-multi-window reversal). ## 2026-08-08 — CI's second real run (same-day follow-up — the first fix was incomplete)

**Architecture observations:** The entry above closed too early. The debt this surfaces is process debt: "verified locally" was asserted in the prior entry (and, briefly, in a `docs/DECISIONS.md` entry since corrected) before the corresponding CI run had actually been watched to completion — a gap between "I ran a command that should confirm this" and "I confirmed it," worth remembering on any future infra change in this repo, not just this one.

## 2026-08-08 — Deliverable D2 — Domain Identity, Setup & Cue Models

**Architecture observations:** Two real gaps surfaced during planning, before any T2.x code was written — both fixed in this Deliverable rather than carried forward silently. First: D1 had claimed `MediaDuration` was implemented ahead of schedule alongside `Timecode`/`TimecodeFrameRate`; checking the actual source tree (not trusting the prior claim) found it was never merged — no `MediaDuration.swift` existed anywhere. Since `Setup.productionRuntime`/`totalMusicRuntime` and `Cue.duration` all depend on it directly, this was built first, as corrective work, with `ROADMAP.md`'s D1 section corrected to admit the gap plainly rather than rewritten to look clean. Second: `SPEC.md` specified `CueRightHolder.arrangementAuthorizationAttached` as required "iff... the original work is still copyright-protected," but no field anywhere in the schema (`Cue` or `CueRightHolder`) actually carried that fact — the condition referenced data that didn't exist. Resolved by adding `Cue.isArrangementOfProtectedOriginal: Bool` (default `false`), as a property of the work rather than of any one right-holder row, with `SPEC.md` §4.3/§4.4/§4.6 and `CLAUDE.md`'s Data Model summary updated in the same change per rule 9. Beyond those two, D2 matched `CLAUDE.md`/`ROADMAP.md` closely: `Party`'s D1-era `UUID`-typed cases resolved to `Person.ID`/`Label.ID` with genuinely zero rework, confirming the forward-compatibility claim from D1's `docs/DECISIONS.md` entry held exactly as predicted. The delete-guard (§4.12), `PartyResolver` (§4.13), and `RecalculateTotalMusicRuntimeUseCase` (§4.14) were all correctly left for D3/D10 rather than built ahead of schedule, even though `PartyResolver` in particular was technically buildable the moment `Person`/`Label` existed — held off specifically to respect `ROADMAP.md`'s Task boundaries per `CONTRIBUTING.md` §1, not because of a technical blocker.

**Code quality observations:** A real correctness trap surfaced while writing `ValidateCueRightHolderSharesUseCase`'s tests: a `Decimal` float literal (e.g. `33.33` written directly as a `Decimal`-typed argument) is *not* exact — Swift converts it via `Double` first, so `CueRightHolder(performanceBroadcastShare: 33.33, ...).performanceBroadcastShare` printed as `33.32999999999999488` in a failing test, not `33.33`. This is exactly the binary-rounding problem `Decimal` was chosen specifically to avoid (SPEC.md §4.6), just relocated to how a `Decimal` value gets *constructed* rather than how it's summed. Fixed throughout by constructing exact test fixtures via `Decimal(string:)` (wrapped in `XCTUnwrap`, never force-unwrapped, per `CONTRIBUTING.md` §9) instead of float literals. Worth remembering for any future Deliverable that parses user-entered percentage shares from text fields (D7/D10): the input must go through `Decimal(string:)`-style exact parsing, not a `Double`-typed text-field binding coerced to `Decimal` after the fact, or this Deliverable's whole reason for choosing `Decimal` is silently defeated at the UI boundary. `ValidateCueRightHolderSharesUseCase` and (once D3 lands) `PartyResolver` now share one real precedent for a Repository-free Use Case: a `public enum` namespace with `static func`, matching the "pure static helper" shape SPEC.md §4.14 already specifies for `RecalculateTotalMusicRuntimeUseCase` — worth following again rather than defaulting to an instantiable `struct` for the next Repository-free Use Case that comes up.

**Technical debt:** `CueRightHolder` has no `id` field — matching SPEC.md §4.4's schema exactly, not an oversight, but a real forward risk worth flagging explicitly rather than only mentioning in passing: D10/T10.2's per-cue right-holder editing UI (add/remove/reorder within `Cue.rightHolders`) will need per-row identity for SwiftUI list diffing, and `CueRightHolder` currently has nothing to provide it. Whether that's solved by finally giving it an `id` field (with a `SPEC.md`/`CLAUDE.md` update at that point, per rule 9) or by some index-based identity scheme is an open question for D10 to resolve, not decided here — don't add an `id` preemptively before D10 actually needs it (rule 7). Separately, not debt but worth naming: `RecalculateTotalMusicRuntimeUseCase` (SPEC.md §4.14) and `PartyResolver` (§4.13) are still unbuilt — correctly scoped to D10 and D3 respectively, not gaps in D2.

**Refactoring suggestions:** None yet. The "small, tightly-coupled enum co-located in its parent model's file" convention (`TimecodeComponents` in `Timecode.swift` from D1; `AdditionalWorksDeclaration` in `Setup.swift`, `CueSource` in `Cue.swift`, `CueRightHolderRole` in `CueRightHolder.swift` from D2) is now used four times — not a "rule of three" duplication candidate (there's no shared logic to extract, just a shared file-organization choice), but worth continuing to apply deliberately rather than reconsidering per type.

**Follow-ups filed:** `docs/DECISIONS.md` gets one new entry: the `MediaDuration` gap and its correction. `ROADMAP.md` D1's Status/T1.4 corrected to admit the gap; D2 and its three Tasks marked complete in the same change. `SPEC.md` §4.3/§4.4/§4.6 and `CLAUDE.md`'s Data Model section updated for `Cue.isArrangementOfProtectedOriginal`. ## 2026-08-09 — Deliverable D4 — Persistence

**Architecture observations:** The persistence design itself matched `CLAUDE.md`/`ROADMAP.md` closely: `@Model` entities map 1:1 to `ACCore` domain aggregates with all conversion isolated in `Mappers/`; `Party` references stay bare kind+id columns, never promoted to a real `@Relationship`, specifically to avoid reintroducing cascade/nullify behavior behind D3's `DeleteRightHolderUseCase` delete guard's back; `observeAll()`'s live-observation mirrors `InMemoryProjectRepository`'s existing subscriber-dictionary contract exactly, now backed by real SwiftData. `ProjectRepositoryImpl`'s per-`Project.ID` write serialization (`CLAUDE.md`, "Document & Window Model") needed real, non-obvious design: `ModelContext`'s fetch/save calls are synchronous, not `async`, so a naive `actor`-only implementation would not have delivered "different `Project.ID`s don't block each other" — the actual design chains each write onto that ID's previous pending `Task`, with the real SwiftData work dispatched into its own unstructured `Task` per call, off the actor's exclusive-execution path. One deliberate scope deviation from T4.1's literal file list: `SettingsEntity` was not built (see `ROADMAP.md` D4's Status note for why) — `Settings` isn't part of `Project`'s aggregate and has no repository until D15.

The real story of this Deliverable, though, is the investigation, not the schema. Four consecutive code-level fixes for a fully deterministic `ACPersistence` CI crash — a `WaveformPeaksEntity` redesign (`Data` blob → native `[Float]` attributes), dropping duplicate `@Attribute(.unique)` constraints, building a fresh `Schema` per `ModelContainer` instead of sharing one `static let`, and reordering mapper writes to fix a hypothesized Swift exclusivity violation — each passed every local check and each turned out to have **zero effect** on the actual crash. The fourth fix was based on a real crash report pulled from the CI runner (`xctest-*.ips`, via a temporary diagnostic CI step), which still turned out to be a misread. What actually found the cause, at the user's explicit direction, was abandoning code-level guessing entirely: a staged fixture bisection (seven tests, each adding one piece of complexity) found the crash already reproduces at the simplest possible case — one `Cue`, zero `CueRightHolder`s — ruling out every one of the four "fixes" outright, since none of them touch code that case even reaches. An isolated toy `@Model` pair (`ToyParent`/`ToyChild`), with zero connection to any real entity in this codebase but the same relationship shape, reproduced the crash identically on CI and never once locally, under both `swift test` and a from-scratch `xcodebuild test` run against a bare, un-wrapped SPM package. That pointed at the toolchain itself, not the code: per GitHub's `runner-images` docs, `macos-15` offers Xcode up to `26.3` (the exact local version already confirmed clean) versus `macos-14`'s ceiling of `16.2` (with `15.4` — this project's original pin — as default). A config-only `ci.yml` change (zero source files touched, to cleanly isolate the one variable) repinned CI to `macos-15`/Xcode `26.3`. Result: `ACPersistence`'s CI job went from 8 consecutive real-run failures to a clean, fully green pass, unchanged code, confirmed again on the post-merge `main` run.

**Code quality observations:** The per-`Project.ID` write-tail chaining pattern in `ProjectRepositoryImpl` is the one genuinely novel piece of concurrency architecture in this Deliverable, and it earned real scrutiny before being trusted — including an explicit, load-bearing invariant (the read-modify-write of the tail dictionary must contain no `await`) documented directly in the source as a comment, not just asserted in a PR description. The persistence-only `order` field needed on `CueEntity`/`CueRightHolderEntity`/`PersonEntity`/`LabelEntity`/`EmbeddedMarkerEntity` (SwiftData gives no to-many fetch-order guarantee, but `Project`'s synthesized `Equatable` compares arrays order-sensitively) was **not** anticipated going in — it was caught by an actual failing round-trip test (`Person`/`Label` order flipping across runs) before the fix reordering ever reached CI, a real example of a round-trip test earning its keep rather than being pro-forma coverage. Every mapper that assembles a parent + to-many children (`ProjectMapper`, `CueMapper`, `AudioAssetMapper`) now uses an identical "materialize children fully, assign to parent, set back-references afterward" pattern — three real instances of the same shape, each carrying its own doc comment explaining why the ordering was investigated (even though the investigation's conclusion was that this specific ordering wasn't what fixed the crash) — a rule-of-three candidate for extraction into a shared helper if a fourth relationship-with-backreference mapper is ever added, not extracted now since the per-call-site comments carry real, non-obvious context a generic helper would obscure.

**Technical debt:** None deliberately deferred within the persistence schema itself. The one real, load-bearing thing this Deliverable changes for every future session: the project's actual minimum viable Xcode version is now `26.3`, not `15+` — `CLAUDE.md`'s "Deployment Target" section is corrected in this same PR, but any contributor (human or a future Claude Code session) who assumes "Xcode 15.x should work, `CLAUDE.md` said so" before this correction landed would hit a real, reproducible crash the moment they touched a `@Model` relationship, not a hypothetical risk.

**Refactoring suggestions:** The materialize-then-assign-then-backreference mapper pattern (above) — watch for a fourth call site; that's the point at which extraction stops being premature.

**Follow-ups filed:** `docs/DECISIONS.md` gained three real entries from this investigation, two of them carrying their own honest corrections rather than silent edits: the `WaveformPeaksEntity` redesign (corrected once proven not to be the cause), "the real cause of PR #4's crash" — the exclusivity-violation diagnosis (also corrected once proven wrong), and the final "D4's real, confirmed root cause" entry documenting the actual Xcode 15.4 SwiftData defect and the CI fix. `CLAUDE.md`'s "Deployment Target"/"Toolchain implication" section corrected in the same PR. `ROADMAP.md` D4 and its three Tasks marked complete, with the `SettingsEntity` scope deviation noted explicitly rather than silently. Two throwaway diagnostic files (`BisectionTests.swift`, `AAAToyRelationshipTests.swift`) were created during the investigation and both removed once their jobs were done — neither shipped in the merged state.

## 2026-08-09 — Deliverable D5 — Design System Foundations

**Architecture observations:** The real work in this Deliverable wasn't the tokens/components themselves — it was discovering, before any code was written, that the visual design AutoCue actually targets (brand palette, Space Grotesk, sharp corners, ghost-text tint, transition timing, default window size) had never been captured anywhere in this repository. `SPEC.md` §3 explicitly scopes UI/visual design out of that document, and `ROADMAP.md` D5's own Acceptance Criteria — "every color/font token uses semantic, dark-mode-safe definitions," "a SwiftUI preview renders a token swatch sheet in both appearances" — turned out to be generic SwiftUI-best-practice boilerplate written before any real brief existed, not a description of what this project actually wants. A direct grep across every doc in the repo (`SPEC.md`, `CLAUDE.md`, `ROADMAP.md`, `CONTRIBUTING.md`, `docs/DECISIONS.md`, `docs/DefinitionOfDone.md`, `docs/REVIEW.md`) for the specific values in the brief (`Space Grotesk`, `Burgundy`, `93032E`, `Carbon Black`, `202020`, `ghost text`) came back with zero matches before implementation began — confirmed rather than assumed, the same discipline this log has applied to every other claim worth checking. Once the real brief was supplied, it directly conflicted with the roadmap's placeholder wording: AutoCue commits to two **fixed** surface styles selected per screen (Setup/Cue Sheet: white background, black text; Review & Export: black background, white text), not colors that adapt to the system Light/Dark Mode setting. Resolved by treating this as a real, debatable architectural call worth its own `docs/DECISIONS.md` entry ("AutoCue does not adapt to system Light/Dark Mode") and correcting `ROADMAP.md` D5's Acceptance Criteria in the same change, rather than silently building against the literal old wording or silently building against the new brief without reconciling the two on the record.

**Code quality observations:** Two real bugs were caught during local verification, before either reached CI — worth recording because both are the kind of mistake that "it compiled" would not have caught. First: `Theme.Typography`'s lazy font-registration trigger called `Bundle.module.url(forResource:withExtension:)` without a `subdirectory` argument. `Package.swift` declares the font resources as `.copy("Resources/Fonts")`, which — confirmed by inspecting the actual built `.bundle` directory structure, not assumed from the API name — copies the whole `Fonts/` folder as a subdirectory *inside* the resource bundle, not flattened to the bundle root. The unqualified lookup would have returned `nil` for every weight, silently, both in the real running app and in Previews; a real font-registration failure that "the code compiles and the previews render sample text" would never have surfaced, since SwiftUI's `Font.custom` silently falls back to a system font on a missing PostScript name rather than crashing. Caught by a real test (`test_bundledFontWeights_areActuallyPresentInTheResourceBundle`) that inspects the resource bundle directly rather than trusting the registration call to have worked — the same "verify the artifact, don't trust the API call" discipline `ACExportTests`' `XLSXFeasibilitySpikeTests` established for `libxlsxwriter`. ## 2026-08-10 — Deliverable D6 — third manual click-through round: divider centering, resolved by measurement not padding math (PR #9, pre-merge)

**Architecture observations:** Two consecutive rounds tried to fix the Library divider's centering with padding math (row content symmetric `.xs`, divider symmetric `.padding(.vertical, sm)`) and both were reported back by the user as still visibly off — correctly, since the second attempt was reported as "looks even" based on describing a screenshot, not measuring it. That number pointed straight at the cause: the divider lived as the *last* element inside the *previous* project's own `List` row (one `ForEach` iteration = one `List` row = one `VStack` containing that row's `ProjectRow` + its trailing `Divider`), so the gap *above* the divider was entirely intra-`VStack`, while the gap *below* it crossed a real `List`-native row boundary — and `List` on macOS applies its own default inter-row spacing there that `.listRowSpacing` can't zero out (confirmed unavailable on macOS by a real build error the previous round, not assumed). **Code quality observations:** The general lesson here generalizes past this one screen: a `List`/`ForEach` pairing where `ForEach` is `List`'s *direct* child gives up control over inter-cell spacing to macOS in a way that isn't fully overridable on this platform (`.listRowSpacing` is iOS/watchOS/tvOS-only).
