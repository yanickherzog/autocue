# AutoCue — Roadmap

Structured as **Deliverables** (D1, D2, …) — larger, coherent vertical slices — with **Tasks** nested underneath each. A Task is roughly what the original one-milestone-per-session plan called a "milestone"; a Deliverable groups the Tasks that only make sense finished together. Work sequentially — later Deliverables assume every earlier one is done unless stated otherwise.

Every Deliverable's fields, in order: **Goal**, **Dependencies**, **Tasks**, **Acceptance Criteria**, **Testing Requirements**, **Documentation Requirements**, **Suggested Commit Boundary**. See `docs/DefinitionOfDone.md` for the checklist that applies to all of them uniformly (builds, tests pass, zero warnings, docs updated, this file updated, architecture preserved) — not restated per Deliverable below.

Commit messages follow Conventional Commits, matching the style already implied by `CLAUDE.md`/`SPEC.md`'s own framing.

**Minimum deployment target: macOS 14.0 (Sonoma).** Required by `@Observable`/`SwiftData` — see `CLAUDE.md`, "Deployment Target," and `SPEC.md` §0. Every package's `Package.swift` and the App target's deployment target setting must target this; don't use an API newer than macOS 14 without updating that section first.

## Why this structure, and what changed from the original 34-milestone plan

The original plan was 34 fine-grained milestones across 12 phases, each scoped to one Claude Code session. That granularity is preserved below as **Tasks** — nothing was deleted — but two things were wrong with treating each one as an independent top-level unit:

1. **Architectural prerequisites weren't sequenced before what depends on them.** CI/lint enforcement was originally scoped for M28 territory — 27 milestones of unenforced work would have happened first. The `libxlsxwriter` feasibility spike was originally scoped for M28 too, with everything from M1 onward implicitly trusting it would work. Both are now front-loaded: CI/lint is **Deliverable D1**, and the XLSX feasibility question is **already answered** — see D11's note.
2. **Some milestones only make sense as a unit.** M26 (Review) and M27–M29 (Export) are now one combined, always-visible navigation destination (`CLAUDE.md`, "Navigation Model") — building them as unrelated milestones invited exactly the sheet-vs-tab mistake an earlier draft of this project actually made (see `docs/DECISIONS.md`).

## D8 — Audio Analysis Pipeline

**Goal:** Read WAV files in bounded chunks, extract embedded markers, detect silence-gap boundaries, generate waveform peak data, and let the user import a file into a project — all without ever loading a full file into memory.

**Dependencies:** D3 (for `AudioAnalysisRepository`/`AnalysisSettings`/`WaveformPeaks`), D6 (for the app shell to host the import UI).

**Tasks:**
- **T8.1 — WAV streaming reader** *(was M16)*. `Packages/ACAudioKit/Sources/ACAudioKit/Streaming/WAVStreamingReader.swift` + tests with a small fixture WAV.
- **T8.2 — RIFF/BWF chunk parser** *(was M17)*. `Packages/ACAudioKit/Sources/ACAudioKit/WAVParsing/{RIFFChunkParser,BroadcastWaveMetadata}.swift` + tests with a fixture WAV containing `cue`/`labl`/`ltxt`/`bext` chunks.
- **T8.3 — Silence/level analysis, with SuperFlux-based onset refinement** *(new required input — see Testing Requirements, below)* *(was M18)*. `Packages/ACAudioKit/Sources/ACAudioKit/Analysis/SilenceDetector.swift` (vDSP-based, implementing the full contract in `SPEC.md` §4.11 — overlapping-hop windowed RMS with dB-domain threshold-crossing interpolation, manual/automatic threshold calibration, reverb-tail truncation, embedded-marker merge tolerance, 1-frame boundary-accuracy tolerance) + tests against both a synthetic buffer library and a hand-verified real-audio fixture library (see Testing Requirements, below). **Two-stage boundary detection, not RMS alone, and only ever applied to cue starts:** stage 1 (windowed RMS, as already scoped) finds the rough candidate boundary region; stage 2, new in this pass, refines a silence→sound (cue-start) candidate boundary within that region using **SuperFlux** (Böck & Widmer, "Maximum Filter Vibrato Suppression for Onset Detection," DAFx 2013) — a **Hann-windowed** STFT (computed every `superFluxHopSeconds`, default `10`ms — pinned explicitly, since it directly sets stage 2's reported-boundary time resolution, not left implementation-time-only) mapped to a log-frequency-scaled, log-compressed magnitude spectrogram, a maximum filter across neighboring frequency bins (vibrato/tremolo suppression), then a half-wave-rectified frame-to-frame novelty difference, computed via `Accelerate`'s existing `vDSP_fft_zrip`/`vDSP` FFT support (no ML, no training data, no new architecture) — to locate the actual moment of spectral/musical change rather than an arbitrary RMS level-crossing point. This directly targets the hardest real case in this Task's own scope: a cue that fades in gradually or is mixed in quietly, where a level threshold alone tends to land late or imprecisely because there's no single clean crossing point by construction — and SuperFlux specifically (not plain spectral flux) suppresses the false-positive onsets this app's typical material (sustained strings, legato brass/woodwind, vocals) would otherwise trigger via natural vibrato/tremolo. **Peak acceptance on the novelty function is locally adaptive, not gated by one fixed global sensitivity value:** a candidate peak is accepted only if it's a local maximum on the novelty function *and* clears a threshold computed from the local median novelty over `superFluxAdaptiveThresholdWindowSeconds`, scaled by `superFluxAdaptiveThresholdMultiplier` plus `superFluxAdaptiveThresholdOffset` — per `SPEC.md` §4.11's "Adaptive local peak-picking" subsection, which retires `superFluxOnsetSensitivity` outright. **Cue-*end* (offset) detection is explicitly and permanently out of scope for SuperFlux or any onset-detection technique** — it remains governed entirely by the existing reverb-tail truncation mechanism (`tailToleranceDb`/`tailCapSeconds`), per `SPEC.md` §4.11's "Why offset detection does not use SuperFlux or any onset-detection technique" subsection; this is an architectural boundary, not a gap to fill later. See `SPEC.md` §4.11's "SuperFlux-based onset refinement" and "Adaptive local peak-picking" subsections for the full step-by-step contract, and `docs/DECISIONS.md`, 2026-08-13 and 2026-08-14, for why plain spectral flux was upgraded to SuperFlux specifically, why peak-picking was made locally adaptive, why onset and offset detection deliberately use two different mechanisms, and why speech/music discrimination is explicitly out of scope.
- **T8.4 — Waveform peak extraction** *(new — `SPEC.md` §4.15)*. `Packages/ACAudioKit/Sources/ACAudioKit/Analysis/WaveformPeakExtractor.swift` (vDSP min/max reduction per bucket, computed via the same streaming reader from T8.1 — never a second full-file read).

**Acceptance Criteria:**
- Streaming reader reports sample rate, channel count, bit depth, and duration correctly for the fixture; a test asserts multiple chunk callbacks occur for a file larger than one chunk (proves it isn't loading the whole file at once).
- Chunk parser extracts all marker entries with sample-accurate positions from the fixture; returns an empty result (not a crash or throw) for a WAV with none of these chunks.
- **Synthetic tier.** Given a synthetic buffer with known silent/loud regions, detected boundaries are accurate to within **1 frame at the project's configured `TimecodeFrameRate`** — not a fixed millisecond/sample number, since one frame's duration differs by frame rate (`SPEC.md` §4.9's "Real FPS" column: `1/24s` at `.fps24`, `1/25s` at `.fps25`, `1/29.97s` at either `.fps29_97NonDrop`/`.fps29_97Drop`, `1/30s` at `.fps30`). `SilenceDetector`'s tolerance check converts this into a sample-count tolerance from the project's actual sample rate and the configured `TimecodeFrameRate`'s real FPS at run time — never a hardcoded sample-count or millisecond constant. A performance test analyzing a ~10-minute synthetic buffer completes within a documented time budget, validating the approach scales toward 3 hours. Both manual and automatic `noiseFloorCalibrationMode` are covered, including the every-`noiseFloorReestimationIntervalSeconds` re-calibration behavior.
- **Real-fixture hard-case tier — onset accuracy.** Against the hand-verified real-audio fixture library (see Testing Requirements, below), detected cue-*start* boundaries for every fixture clip fall within the 1-frame tolerance of that clip's documented ground-truth timecode. This tier exists because a synthetic clean loud/silent buffer doesn't exercise the failure modes a level-threshold approach is most exposed to — a gradually fading-in cue, a cue mixed quietly under ambient sound, two cues separated by a short non-silent gap — see `docs/DECISIONS.md`, 2026-08-12. **Explicit goal of this tier, now that SuperFlux refinement exists:** for the fade-in and quiet-mix fixture clips specifically, a test compares stage-1-only (RMS-threshold) boundary placement against the full two-stage (RMS + SuperFlux refinement) result, and confirms refinement measurably improves — or at minimum never worsens — accuracy against that clip's ground-truth timecode on exactly these two scenarios, which is the failure mode refinement was added to address.
- **Real-fixture hard-case tier — offset accuracy, validated as an independent assertion from onset accuracy.** Against the same fixture library, detected cue-*end* boundaries also fall within the 1-frame tolerance of that clip's documented ground-truth end timecode — graded as a separate pass/fail from the onset-accuracy criterion above, never combined into one assertion, since starts and ends are produced by two different mechanisms (stage 1 + SuperFlux for starts; the unchanged reverb-tail two-threshold mechanism for ends per `SPEC.md` §4.11) that must be able to regress independently and be caught independently. This criterion exists specifically to confirm the reverb-tail mechanism keeps producing a perceptually-correct end (not a too-early boundary at the reverb tail's onset) on any fixture clip with a decaying tail, and — just as importantly — to prove SuperFlux was correctly *not* applied to ends, since applying it would be expected to regress this criterion specifically per the offset-timing research finding in `docs/DECISIONS.md`, 2026-08-13.
- **SuperFlux refinement, synthetic coverage.** A synthetic buffer with a tone ramped up gradually over several seconds (a synthetic fade-in, distinct from the clean instant-transition buffers used elsewhere in the synthetic tier) proves stage 2 relocates the detected boundary closer to the true ramp-onset than stage 1 (RMS-threshold crossing) alone. A synthetic buffer with no meaningful spectral change within the stage-1 candidate region (e.g. a steady tone crossing the RMS threshold with a flat spectrum) proves stage 2 falls back to the stage-1 boundary unchanged, per `SPEC.md` §4.11's documented fallback rule, rather than relocating the boundary to a spurious peak. A synthetic buffer with vibrato/tremolo modulation on an otherwise-sustained tone (amplitude or pitch wobbling within the stage-1 candidate region, no genuine re-attack) proves stage 2 does **not** relocate the boundary to a spurious vibrato-driven peak — the specific false-positive SuperFlux's max-filter step exists to suppress, distinct from the flat-spectrum fallback case above.
- **Adaptive local peak-picking, synthetic coverage — proves the threshold responds to differing local conditions, not just one fixed value tuned for one of them.** A single synthetic buffer combines a loud/dense passage (multiple overlapping onsets in quick succession, each a genuine re-attack) and a quiet/sparse passage (a single subtle onset well below the loud passage's novelty level) within one buffer, separated by a stretch long enough that each passage's local median (over `superFluxAdaptiveThresholdWindowSeconds`) is dominated by its own region, not the other's. The test asserts **both**: every genuine onset in the loud/dense passage is still correctly detected (not suppressed by a threshold effectively calibrated to the quiet passage's lower baseline) *and* the quiet passage's genuine onset is also correctly detected (not missed by a threshold effectively calibrated to the loud passage's higher baseline) — a single fixed global `superFluxOnsetSensitivity` value, evaluated as a control against this same buffer, is expected to fail at least one side of this assertion, which is the specific failure mode adaptive peak-picking exists to fix per `SPEC.md` §4.11's "Adaptive local peak-picking" subsection.
- **RMS time-resolution, synthetic coverage — the mechanism cue ends depend on entirely.** A synthetic buffer with a clean level transition placed at a deliberately non-hop-aligned offset (not a whole multiple of `analysisWindowHopMilliseconds`) proves the dB-domain threshold-crossing interpolation in `SPEC.md` §4.11's "RMS time resolution and threshold-crossing interpolation" subsection actually locates the crossing within 1-frame tolerance — not merely the hop-quantized window it happened to fall in. This specifically exercises the resolution fix cue *ends* depend on entirely, since they have no SuperFlux-equivalent second stage to correct for RMS quantization error the way onsets do; a naive implementation that reports the crossing window's boundary instead of interpolating would fail specifically this buffer, even though a transition that happens to land on a hop boundary would pass by coincidence.
- Waveform peak extraction produces exactly `resolution` (4096) buckets regardless of source file duration; a test confirms the persisted overview's memory footprint matches the documented ~32KB bound.
- `loadAsset(from:)` returns a populated `AudioAsset` (including embedded markers) for the fixture file; `GenerateWaveformPeaksUseCase` runs immediately after import and persists to `Project.waveformPeaks` per `SPEC.md` §4.15's lifecycle rule.
- Progress is emitted via the shared `AsyncThrowingStream<OperationProgress<T>, Error>` contract (`CLAUDE.md`, "Long-Running Operations") with at least start/intermediate/complete events for a multi-chunk file — for both import and waveform generation.
- Manually verified with a real multi-minute WAV file via `fileImporter`: progress updates without blocking the UI, resulting `AudioAsset` and `WaveformPeaks` are persisted on the project; security-scoped bookmark is stored and file access survives an app relaunch (required under App Sandbox).

**Real-fixture location, gitignore, and manifest convention** (decided 2026-08-12; see `docs/DECISIONS.md` for the "why" — this is the "how"):

- **Location: `Audio_Analysis_Test/` at the repo root, entirely outside version control.** `.gitignore` excludes `/Audio_Analysis_Test/` in full — the project owner drops real WAV excerpts there directly; nothing under that folder can ever be accidentally committed, since the whole folder is ignored, not just a file-extension pattern within it. This repo is public and these are potentially client-confidential excerpts from real scoring work, so they never enter git history at all, not even in a squashed/rebased form.
- **The manifest lives inside the same ignored folder, not in `ACAudioKitTests/`.** `Audio_Analysis_Test/manifest.json` — a flat JSON array, one entry per fixture clip: `filename` (matches a `.wav` in the same folder), `scenario` (a short plain-text tag — e.g. `"gradual fade-in"`, `"quiet under ambient"`, `"short non-silent gap"`, `"decaying reverb tail"`), `groundTruthOffsetSeconds` (`Double` — the true cue-*start* boundary position, as a plain offset, not a `Timecode`/frame-rate-formatted value, so the manifest itself carries no frame-rate assumption), an optional `groundTruthEndOffsetSeconds` (`Double?` — the true cue-*end* boundary position, same plain-offset convention; supplied only for clips that include a decaying tail worth grading offset accuracy against, per the offset-accuracy Acceptance Criterion above), and an optional free-text `notes`. Because it lives inside `Audio_Analysis_Test/`, it's covered by the same gitignore entry automatically — filenames and scenario descriptions could themselves hint at confidential source material, so the manifest gets exactly the same non-committed treatment as the audio, not weaker protection.
- **Workflow — no JSON/tooling knowledge required from the project owner:** (1) the project owner places `.wav` files in `Audio_Analysis_Test/` with descriptive filenames (e.g. `fade-in-quiet-cue.wav`); (2) in plain language, in conversation, the owner states each file's true boundary or boundaries (e.g. "the cue in `fade-in-quiet-cue.wav` actually starts at 1:23.5" and, where relevant, "...and the tail is really over by 1:47.0"); (3) Claude converts each plain-language statement into `groundTruthOffsetSeconds`/`groundTruthEndOffsetSeconds` values and writes/updates `Audio_Analysis_Test/manifest.json` accordingly; (4) the owner reviews the generated manifest and confirms it's correct before it's relied on by any test. The manifest is regenerated the same way any time a fixture is added, removed, or a stated boundary is corrected — never hand-edited as JSON by the owner directly.
- **Test suite reads the path directly; it does not require the folder to exist in git history.** `SilenceDetectorRealFixtureTests` (or equivalent, named at T8.3 implementation time) resolves `Audio_Analysis_Test/` relative to the repo root at test-run time, parses `manifest.json` if present, and runs one boundary-accuracy assertion per manifest entry. **If the folder or manifest is absent, these tests report a skip (e.g. `XCTSkip`), never a failure** — this is what keeps CI green: `Audio_Analysis_Test/` is gitignored, so it will never exist on a clean CI checkout, and a hard failure there would make this tier permanently unpassable in CI regardless of local state. The synthetic tier (Acceptance Criteria, above) has no such exemption and always runs in CI. Confirming these tests actually execute (not silently skip) is a manual, local-machine step once the owner's fixtures and manifest are in place — noted here rather than left as an unstated assumption.
