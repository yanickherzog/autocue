# AutoCue — Application Specification

Status: data model and compliance target finalized. No UI or business logic implemented yet.

## 0. Platform Requirements

Minimum supported macOS version: **14.0 (Sonoma)** — the floor required by `SwiftData` and `@Observable`, both already-committed architectural choices. Full reasoning and enforcement points: `CLAUDE.md`, "Deployment Target."

## 1. Purpose

AutoCue is a native macOS application that generates Swiss film/TV cue sheets from WAV audio files. It analyzes a production's audio (embedded markers plus signal analysis) to identify the musical works it contains, and produces a cue sheet compliant with the format SUISA (Swiss authors'/publishers' rights society) requires for royalty distribution, exportable as PDF and XLSX.

## 2. Compliance Target

### 2.1 SUISA — "Declaration of musical works for films and audiovisual productions" (WA Film)

This is the primary, binding target format. It is SUISA's own paper/PDF form (form codes `WA Film 2007-01` main form + `WA Film II 2007-01` additional-works continuation, obtained directly from suisa.ch), submitted to SUISA's Film Department to report the musical works contained in a production and how performance/broadcast and mechanical rights are split between right-holders.

**Corrected 2026-09-27 — the form codes above read `2011-01` in every earlier revision of this document; that was wrong.** `ROADMAP.md` D11/T11.3's revalidation checkpoint (§2.3) text-extracted the real, freshly-downloaded, actively-used form directly from suisa.ch: its embedded filename is genuinely `WA Film 2007-01 D.doc` (main) / `WA Film II 2007-01 F.doc` (continuation) — 2007, not 2011. This is a correction to a prior transcription error in this document, not evidence the form itself changed between 2007 and 2011 or since. **The year in the filename is not evidence the form is stale** — SUISA's own internal filename and the form's actual current validity are two different things; a form can (and, per this checkpoint's own direct confirmation, does) stay the genuinely current, actively-accepted version for years after the file it's served from was last renamed. Treat the filename as an identifier, not a freshness signal. See `docs/DECISIONS.md`, 2026-09-27, for the full checkpoint outcome.

Structurally, this form is **not** a US-style (ASCAP/BMI) scene-by-scene cue log with usage categories (Background Instrumental, Visual Vocal, Main Title, etc.) and in/out timecodes. It is a **rights-accounting declaration**: for each musical work used in the production, it records the work's title, duration of use, and every right-holder's role and percentage share of performance/broadcast rights and mechanical rights. AutoCue's data model follows this shape. Do not import US cue-sheet conventions into required fields.

The main form holds 5 musical works per page and paginates with a 4-per-page continuation sheet ("Additional works") beyond that — this is an export/layout concern, not a data-model concern; the domain model has no fixed limit on the number of Cues per Project.

### 2.2 SWISSPERFORM

SWISSPERFORM (Swiss neighboring-rights society for performers and producers) does **not** have an equivalent per-production cue-sheet document. Its audiovisual-participation reporting is performer-centric and self-service: each performer registers their own participation (film/episode title, series/season, director, production country/year, function/role, shooting days or takes, role weighting) directly through SWISSPERFORM's online portal, not through a document the production company fills in per-production the way SUISA's WA Film form works.

Consequently, AutoCue does not attempt to generate a "SWISSPERFORM cue sheet" — no such artifact exists in the same shape as SUISA's. What it does instead: the `Person` model carries an optional `swissPerformNumber`, `Setup` carries the production-identity fields (series/season, director, country, language) that a performer would need when self-registering, and — as of `ROADMAP.md` D7's planning — a `Cue`'s right-holders can now carry a `.performer` role (§4.4) alongside composer/author/arranger/publisher, informational only and excluded from both share sums and the PDF export. All three are the same story: data AutoCue already collects can be reused/exported as reference information for SWISSPERFORM registration, without AutoCue claiming to produce an official SWISSPERFORM filing. Adding `.performer` doesn't change that conclusion — it only grows the list of data that supports it.

## 3. Functional Scope (data-model relevant)

1. Import a WAV file (up to ~3 hours) as a `Project`'s `AudioAsset`.
2. Detect candidate `Cue`s via embedded WAV markers and/or silence-gap analysis.
3. Let the user edit/confirm Cues and attach right-holder (`Person`/`Label`) information and rights shares.
4. Maintain a production-level `Setup` (the SUISA form header).
5. Validate the data set against SUISA's rules (100%-share sums, required attachments for certain roles).
6. Export the finished cue sheet as PDF (a landscape, column-based document of its own design — see §4.16 — never a replica of the WA Film form's own layout, corrected 2026-09-27) and XLSX. **Corrected 2026-09-29** (`ROADMAP.md` D11/T11.4, `docs/DECISIONS.md`): XLSX is **not** a flat, one-row-per-Cue-×-right-holder relational export — that was this document's original, never-implemented intent, superseded by an explicit project-owner decision that XLSX must render the identical content and structure as the PDF cue sheet, one row per `Cue`, in a spreadsheet instead of a page (`XLSXCueSheetWriter`, `ACExport`). Same title block, same header-block fields, same ten table columns in the same order, same Interpret\*in/Arrangeur\*in summary blocks — adapted only where the medium genuinely requires it (Dur. is a real numeric duration cell and TOTAL MUSIK a live `=SUM()` formula, not static text, so a user's own spreadsheet math actually works; everything else is an exact text match). Producing the literal, portrait, pixel-accurate SUISA *WA Film* registration form itself is a separate concern — see `docs/DECISIONS.md`, 2026-09-27.

UI flows and use-case logic are out of scope for this document — see `CLAUDE.md` for architectural rules governing where that logic lives.

**TC In, TC Out, and Length — three related cue-sheet display values, one shared nil-safety rule.** New this pass, found during a pre-D9/D10 UI scope review (`docs/DECISIONS.md`, 2026-08-14) that checked what `ROADMAP.md` D10/T10.2's `CueTableView` actually displays for a cue's position and duration.

- **TC In** — **not `Cue.startTimecode` alone.** `Cue.startTimecode` (§4.9) is, and stays, an offset from the start of the *audio file* — that's the coordinate system the waveform view, playback, and every drag/split/merge computation actually operate in, and it must stay that way regardless of what this bullet displays (see "Why the addition happens here and nowhere upstream," below). TC In is `Timecode(offsetSeconds: (Setup.timecodeStart?.offsetSeconds ?? 0) + startTimecode.offsetSeconds)`, formatted `HH:MM:SS:FF` via `Setup.timecodeFrameRate` (§4.9) — the film's actual absolute timecode, not the audio file's own internal position. **Corrected 2026-09-10:** this document's original wording here ("`Cue.startTimecode` itself") never added `Setup.timecodeStart` at all — a real bug, not a rewording; every previously-displayed TC In/TC Out was silently wrong relative to the actual film whenever `Setup.timecodeStart` was non-zero (its default, per `docs/DECISIONS.md`, is `09:59:52:00`, not `0`). See `docs/DECISIONS.md`, 2026-09-10, for the fix and the full reasoning below.
- **TC Out** — **derived, never stored:** `Timecode(offsetSeconds: displayedTCIn.offsetSeconds + duration.seconds)` — the same addition, carried through from the now-corrected TC In above, computed at the point a screen renders it (`ACFeatures`-layer, the same "compute at the point of rendering, don't persist a second copy" pattern already established for `WaveformDisplayData`/`CueSheetPageLayout`, though this is plain addition, not I/O — no new Repository method or Use Case). Formatted `HH:MM:SS:FF`, same as TC In, since it's a position, not a length. This is well-defined *whenever `startTimecode` is present* — confirmed during the original review that added this section that `Cue.duration` cannot represent a work's cumulative usage across multiple non-contiguous placements (nothing in `EmbeddedMarker`, a single point per §4.10 not a range, or in `DetectCuesUseCase`'s one-cue-per-contiguous-region construction, supports that reading), so `start + duration` is always a single, well-defined end point for any cue that has a start at all.
- **Length** — `Cue.duration`, formatted **`MM:SS`** — a documented, deliberate exception to §4.8's general `HH:MM:SS` `MediaDuration` formatting rule, scoped specifically to this cue-sheet display context. `Setup.totalMusicRuntime`/`.productionRuntime` (§4.8) keep `HH:MM:SS`, since aggregate production-level runtimes can genuinely run past an hour; a single cue's usage duration realistically never does, and `MM:SS` reads better for that common case without losing information. `Setup.timecodeStart` is a position offset and has no bearing on Length, a pure duration — never added here.

**Why the addition happens at the point of display and nowhere upstream.** `Cue.startTimecode` is produced by `SilenceDetector`/`AudioAnalysisRepositoryImpl` and consumed by `DetectCuesUseCase`'s embedded-marker merge, `UpdateCueUseCase`'s drag/split/merge math, `WaveformMarker`'s waveform-plotting position, and `AudioPlaybackController.play(from:until:)`'s seek target — every one of those genuinely needs the audio file's own internal position, not the film's absolute timecode, to work correctly at all (a marker plotted at a film-absolute offset would render off the waveform entirely; a seek to a film-absolute offset would play the wrong instant of the file). `Setup.timecodeStart` must therefore never be added anywhere in that chain, and `Cue.startTimecode` itself must never be redefined to mean anything other than "offset from the start of the audio file." The one and only place it's correct to add `Setup.timecodeStart` is where an offset is about to become text a human reads as a real-world timecode — TC In/TC Out, above, and nowhere else this document currently specifies a display of a cue's position (checked directly against the implementation, 2026-09-10: `CueDetectionReviewViewModel`'s waveform markers, playhead, and playback controls display no timecode text at all, only visual position — see `docs/DECISIONS.md`).

**The nil-safety rule, stated once here, applying to TC In and TC Out — not Length:** `Cue.startTimecode` is optional (`Timecode?`). A cue created via `UpdateCueUseCase.add` (§4.19 — no longer reachable from any UI as of D10's second round, but still real, correct code) is never tied to any position in the imported audio and is never assigned one automatically — it may permanently stay that way if the user never sets one. This nil-safety rule stays fully documented and defensively implemented regardless of whether the UI path that most obviously exercises it is currently reachable. Whenever `startTimecode` is `nil`: **TC In displays a placeholder, `"—"`, and TC Out — being derived from `startTimecode`, undefined without it — displays the same placeholder**, never a bogus `0 + duration` computation. This is one rule, defined here once; anywhere TC In/TC Out are displayed references this rule rather than restating or independently reinventing it.

**Changing `Setup.timecodeStart` on a project with existing cues: every cue's displayed TC In/TC Out updates automatically, immediately, with no migration and no warning — a deliberate decision, stated here explicitly, not inherited by analogy from `Setup.timecodeFrameRate`'s similar-looking "pure reformat, no migration" behavior (§4.9).** The two cases are semantically different — changing frame rate reformats the same underlying instant into different digits, while changing `timecodeStart` changes *which real-world instant* a cue's displayed timecode names — and are only reached the same conclusion independently, not by treating one as a precedent for the other:

- `Setup.timecodeStart` is a fact about the *production* (where the imported audio's timeline sits relative to the film's own absolute timecode), not a fact about any individual `Cue`. A `Cue`'s own factual content — its position within the audio file — never changes when `timecodeStart` changes; only the one shared, external reference point every cue's display is computed against does.
- Consequently, if `Setup.timecodeStart` was wrong, every previously-displayed TC In/TC Out sourced from it was *already* wrong — not "about to become wrong." Correcting `timecodeStart` doesn't introduce a change to correct data, it corrects an error common to every cue's display in one place, which is the entire reason this value is computed live from one shared field rather than baked into each `Cue` individually (`CLAUDE.md`, "Single Source of Truth": "If you ever need the same piece of state in two places... inject/observe from there — do not introduce a second variable that has to be kept in sync manually"). Baking the offset into stored `Cue.startTimecode` data instead would make this *worse*, not safer: a wrong `timecodeStart` would then require manually re-editing every affected cue to fix, rather than fixing the one field that was actually wrong.
- No warning or confirmation prompt is shown when editing `Setup.timecodeStart` on a project with existing cues, and none should be added later without a real, separate product reason: this isn't a destructive mutation of cue data (no `Cue` field is touched, no `source` reclassification per §4.19 is triggered), it's a live-recomputed display of data that was always defined relative to this field.

**Length has no analogous gap — checked directly, not assumed.** `Cue.duration` is `MediaDuration`, **not optional**: every `Cue` has a real, concrete `duration` value — the type has no `nil` state to represent "no duration yet." `UpdateCueUseCase.add` (`ROADMAP.md` T10.1's add path — kept in code, unreachable from any UI as of D10's second round, §4.19) defaults a freshly-added cue's `duration` to `MediaDuration.zero`, and `00:00` is a legitimate, literal, always-safely-displayable value at that point, not a missing-data state — it means "zero length so far," the same way a fresh numeric field starting at `0` isn't "absent." Length therefore needs no placeholder and no nil-handling anywhere.

### 4.6 Cross-field validation rules (enforced in Domain Use Cases, not in the structs)

- **Per `Cue`, two independent pools — not one per role, and not one combined pool either.** Corrected twice at `ROADMAP.md` D10: the original rule (pre-D10) summed *every* non-`.performer` right-holder into one combined pool, wrongly flagging a valid one-composer-at-100%-one-arranger-at-100% cue as a 200% violation. D10's second round fixed that by making every role fully independent — which then turned out to be itself wrong for Publisher, confirmed against SUISA's own Verteilungsreglement (distribution rules): a publisher's share is carved out of what would otherwise go to the writers, not an independent, additional 100% of its own. **The correct model, as of D10's third round: `Σ rightHolders[role ∈ {.composer, .author, .publisher}].performanceBroadcastShare == 100%` — Composer, Author, and Publisher share one combined pool — and, separately, `Σ rightHolders[role == .arranger].performanceBroadcastShare == 100%` as its own genuinely independent pool.** Each pool is checked only when it has ≥1 member; a pool with zero right-holders has nothing to validate. Applies identically to `mechanicalRightsShare`, below. See `docs/DECISIONS.md` for the full account of both corrections.
- Per `Cue`, the same two-pool rule as above, applied to `mechanicalRightsShare`: `Σ [.composer, .author, .publisher].mechanicalRightsShare == 100%`, and separately `Σ [.arranger].mechanicalRightsShare == 100%`.

  **Rounding/tolerance policy for both sums above:** `performanceBroadcastShare` and `mechanicalRightsShare` are `Decimal` values scaled to exactly 2 decimal places (hundredths of a percent — matching the precision the printed SUISA form supports). The 100%-sum check is **exact equality against `100.00`, with zero tolerance band** — deliberately, not approximately. This is precise specifically *because* `Decimal` performs exact base-10 arithmetic: unlike `Double`, summing `Decimal` values at a fixed scale never accumulates binary floating-point rounding error, so no epsilon/tolerance comparison is needed to absorb arithmetic noise the way it would be with a `Double`-based sum — this is the actual reason `Decimal` was chosen for these two fields in the first place (§4.4). A legitimate uneven split — e.g. three right-holders at `33.33`, `33.33`, `33.34` — sums to exactly `100.00` under `Decimal` arithmetic and passes with no special-casing. A sum of `99.99` or `100.01` is treated as a genuine data-entry error, not a rounding artifact to be tolerated, and is flagged (blocking or warning per `Settings.shareValidationStrictness`, below). The domain model does not enforce the 2-decimal-place scale as a hard, compiler-checked constraint — `Decimal` has no such type-level restriction, and a custom validator for it is unneeded complexity this rule doesn't call for. Constraining user input to 2 decimal places is a Presentation-layer concern (input field formatting), out of scope for this document per §3.

- `Setup.declarant` must be non-`nil`, and `Setup.producer`/`.directorOrPrincipal` must each be non-empty (≥1 entry), before export (§4.2) — the export-required-field checks in this list driven by the type's own "unset" sentinel (`nil` or `[]`) rather than a business condition on otherwise-present data, since `Party` itself has no "none" case to check against.
- `Setup.productionTypes` must be non-empty.
- `Setup.otherProductionTypeDescription` required iff `.other ∈ productionTypes`.
- `Setup.otherAttachmentDescription` required iff `.other ∈ attachmentTypes`.
- `CueRightHolder.publishingContractAttached` must be `true` before export iff `role == .publisher`.
- `CueRightHolder.arrangementAuthorizationAttached` must be `true` before export iff `role == .arranger` and `Cue.isArrangementOfProtectedOriginal == true` (§4.3).
- Whether a failed rule **blocks** export or only **warns** is controlled by `Settings.shareValidationStrictness`.

`Setup.totalMusicRuntime`'s auto-recompute (§4.14) and `Person`/`Label` deletion guarding (§4.12) are separate, non-optional domain rules — not part of this list because they aren't pass/fail validations checked before export; they're invariants enforced continuously as data changes.

### 4.8 `MediaDuration` (renamed from `Duration`)

Renamed from the originally-planned `Duration` to avoid colliding with the Swift standard library's own `Duration` type (`Swift.Duration`), which ships as part of Swift Concurrency (`ContinuousClock`, `Task.sleep(for:)`, etc.) and is implicitly in scope in virtually every file that touches `async`/`await` timing. Reusing that name for an unrelated domain type would produce constant, confusing ambiguity errors the moment both are in scope — a landmine far cheaper to defuse now, before any code exists, than after `ROADMAP.md` D1/T1.4 ships it.

`MediaDuration` was chosen over the alternative `CueDuration` because the type isn't cue-specific: it's also used for `Setup.productionRuntime` and `Setup.totalMusicRuntime` — any length of media time, not just one cue's.

Represents a **length** of time — "how long," never "where." Contrast with `Timecode` (§4.9), which represents a position.

| Field | Type | Notes |
|---|---|---|
| `seconds` | `Double` | total length, in seconds. Deliberately `Double`, not `Decimal` — durations are formatted, compared, and summed for display/scheduling purposes, not accounted to an exact fixed target the way `CueRightHolder` percentage shares are (§4.4 uses `Decimal` specifically because the 100%-sum validation needs exact decimal arithmetic; `MediaDuration` has no equivalent exactness requirement). |

Conformances: `Equatable`, `Comparable`, `Hashable`, `AdditiveArithmetic` (`+`, `-`, `.zero`) — `AdditiveArithmetic` is required directly by §4.14's `Σ cues[].duration` computation. No `Codable` — see `CLAUDE.md`, "Domain Model Value-Type Conformances," for why blanket `Codable` was removed project-wide.

Formatting: `HH:MM:SS`, no frames. Cue durations and runtimes are declared to SUISA as a rights-accounting total, not located frame-accurately within the production — frame precision belongs to `Timecode`, not here.

### 4.9 `Timecode` and `TimecodeFrameRate`

Represents an absolute **position** within an `AudioAsset` — an offset from the start of the file. Contrast with `MediaDuration` (§4.8), a length. Used only by `Cue.startTimecode` and `EmbeddedMarker.position` (§4.10) — both app-internal, never exported to the SUISA document (§4.3 already notes `startTimecode` isn't exported; SUISA wants total usage duration, not on-screen position).

| Field | Type | Notes |
|---|---|---|
| `offsetSeconds` | `Double` | precise offset from the start of the audio file, in seconds; sample-accurate at the point it's captured (derived from a sample index ÷ sample rate during import/analysis — the stored value is a time offset, not a raw sample count) |

**Where the frame rate comes from — this is not audio metadata.** A WAV file carries no video frame rate; nothing in the RIFF/BWF format declares one. AutoCue is not synced to picture, only to itself, so "frame" here is a **display convention borrowed from film/TV editing practice**, not a property of the source audio or a synced video frame boundary. The frame rate used to format a `Timecode` as `HH:MM:SS:FF` comes from `Setup.timecodeFrameRate: TimecodeFrameRate` (§4.2) — a per-production, user-configurable, app-internal field, because different productions AutoCue is used on may be mastered at different frame rates, and a user reading cue positions wants them to match their own edit timeline. `Timecode.offsetSeconds` itself never changes when `timecodeFrameRate` changes — only its *formatted display* does, computed on demand. This also means changing `Setup.timecodeFrameRate` after cues already exist is always safe and needs no migration: it's a pure reformat of already-correct underlying data.

`TimecodeFrameRate` (enum):

| Case | Nominal FPS (`FF` field modulus) | Real FPS (used for frame-count math) | Drop-frame? |
|---|---|---|---|
| `.fps24` | 24 | 24.0 | no — no real/nominal mismatch to correct for |
| `.fps25` | 25 | 25.0 | no |
| `.fps29_97NonDrop` | 30 | 29.97 | no |
| `.fps29_97Drop` | 30 | 29.97 | **yes** |
| `.fps30` | 30 | 30.0 | no |

Default: `.fps25` (PAL/European broadcast convention, matching AutoCue's Swiss/SUISA target market) — arbitrary but documented, freely overridable per `Setup`. Choosing `.fps25` as the default is unaffected by drop-frame support existing as an option: nothing selects `.fps29_97Drop` unless the user explicitly does, for material that's actually NTSC-derived.

Drop-frame support was added in v1 rather than deferred — see `docs/DECISIONS.md` for why (short version: `Timecode`/`TimecodeFrameRate` are foundational types many later milestones depend on directly; retrofitting a second timecode mode after that dependency exists is far more expensive than getting the enum shape and conversion algorithm right once, up front, and NTSC-derived source material is a real case for this app, not a hypothetical one).

**Why only `.fps29_97` needs a drop-frame variant.** Drop-frame numbering exists specifically to reconcile a *real* frame rate that doesn't evenly divide a second (29.97, in this app's case) with a *nominal* display rate that does (30). `.fps24`/`.fps25`/`.fps30` have no such mismatch — real and nominal are identical — so a drop-frame variant of any of them would be meaningless. This is why the enum only splits `.fps29_97` into `NonDrop`/`Drop`, not every case.

**`Timecode` itself stays frame-rate-agnostic.** It stores nothing but `offsetSeconds: Double` — a pure position, with no frame rate and no drop/non-drop mode attached to it. Whether a given offset gets formatted as drop-frame or non-drop is entirely a property of the `TimecodeFrameRate` passed in at format time, never of the `Timecode` value itself. This is deliberate: it's what makes changing `Setup.timecodeFrameRate` later a pure reformat with no data migration (see above), and it's why drop-frame logic must never leak into `MediaDuration` (§4.8) — a length of time has no "position within a minute" to apply a skip-rule to in the first place.

**Frame calculation, non-drop-frame:**

```
totalFrames = round(offsetSeconds × realFPS)
hours   = totalFrames / (nominalFPS × 3600)
minutes = (totalFrames / (nominalFPS × 60)) mod 60
seconds = (totalFrames / nominalFPS) mod 60
frames  = totalFrames mod nominalFPS
```

**Frame calculation, drop-frame (`.fps29_97Drop`) — SMPTE drop-frame numbering.** The real (uncorrected) frame count is first converted into a *display* frame number, by re-inserting the frame-numbers that drop-frame timecode skips, before the same decomposition above is applied to it. The skip rule: **frame numbers 0 and 1 are skipped at the start of every minute, except every 10th minute** (minutes 0, 10, 20, 30, 40, 50). This corrects for 29.97fps running ~0.1% slower than nominal 30fps, so that drop-frame timecode stays aligned with wall-clock time at hour boundaries — e.g. exactly 3600 seconds of real elapsed time reads `01:00:00:00`, not something drifted by several seconds, which is the entire reason drop-frame exists.

```
dropped = 2                                    // frames skipped per non-exempt minute, at nominal 30fps
framesPerMinuteDropAdjusted = 1800 - dropped    // 1798
framesPer10Min = 18000 - dropped × 9            // 17982 (9 non-exempt minutes per 10-minute block)

d = realFrameCount / framesPer10Min             // integer division
m = realFrameCount mod framesPer10Min

if m < dropped:
    displayFrameNumber = realFrameCount + dropped × 9 × d
else:
    displayFrameNumber = realFrameCount + dropped × 9 × d + dropped × ((m − dropped) / framesPerMinuteDropAdjusted)

# then decompose displayFrameNumber exactly as in the non-drop formula above, using nominalFPS = 30
```

The inverse (parsing `HH:MM:SS:FF` back to an offset) reverses this: compute the naive nominal-30fps frame number from the fields, then subtract `dropped × (nonExemptMinutesElapsed)` to recover the real frame count, where `nonExemptMinutesElapsed = totalMinutes − totalMinutes/10`.

**Invalid drop-frame timecodes are rejected, not silently miscomputed.** Under drop-frame numbering, `FF` values 0 and 1 at `SS == 0` of a non-exempt minute don't correspond to any real frame — e.g. `00:01:00:00` and `00:01:00:01` don't exist; the first real frame of minute 1 is `00:01:00:02`. Parsing such a value must fail (return `nil`/throw), not produce a `Timecode` that silently reformats to a different string than what was entered.

Formatted as `HH:MM:SS:FF`, each component zero-padded to 2 digits. Drop-frame timecode conventionally uses a `;` separator immediately before the frame field (`HH:MM:SS;FF`) to visually distinguish it from non-drop timecode — applied here too.

**Verification:** this arithmetic is implemented and unit-tested in `Packages/ACCore/Sources/ACCore/Models/{Timecode,TimecodeFrameRate}.swift` / `Packages/ACCore/Tests/ACCoreTests/TimecodeTests.swift`, including the every-10th-minute exception specifically (the classic bug in drop-frame implementations) and a round-trip sweep across a 3-hour-equivalent frame range.

### 4.10 `AudioAsset`, `EmbeddedMarker`, `BroadcastWaveMetadata`

One `AudioAsset` per `Project`, present once audio has been imported (`Project.audioAsset` is optional — absent before that, §4.1). An immutable, derived snapshot produced by `AudioAnalysisRepository` from the source WAV file; the file on disk remains the source of truth for raw audio (`CLAUDE.md`, Single Source of Truth).

**`AudioAsset.embeddedMarkers` is never edited, including to "correct" a misjudged detection.** `EmbeddedMarker` is a factual record of what's literally embedded in the source WAV file's `cue`/`labl`/`ltxt` chunks — analogous to a photo's EXIF data — and editing it would misrepresent the source file's actual content, not just tweak an app opinion. What the user actually corrects when a detection is wrong is the app's *interpretation* of that data, which is what `Cue` (§4.3) represents, not `AudioAsset` itself. See §4.19 for the full architectural resolution of manual cue correction — it never touches this type, which is what keeps the immutability invariant below intact rather than quietly bent for editing purposes.

**Invariant: `AudioAsset` never contains raw or downsampled sample data (no PCM buffer, no waveform peak array).** It is bounded, metadata-only, and safe to hold fully in memory regardless of source file size — this is what keeps it a plain `ACCore` domain value type despite the "never load a full WAV into memory" constraint applying project-wide. The waveform-display data model this invariant explicitly excludes from `AudioAsset` is `WaveformPeaks` — a separate, explicitly-bounded sibling type on `Project`, not a field here — see §4.15.

**`securityScopedBookmark`'s lifecycle: refreshed, never left to silently go stale.** Resolving a security-scoped bookmark (`URL(resolvingBookmarkData:...)`) reports whether it's stale as a side effect — and a stale bookmark still resolves successfully at the moment it's checked, which is exactly what makes leaving this unhandled dangerous: nothing fails today, but the app keeps resolving increasingly outdated bookmark data indefinitely, until it eventually fails unpredictably (the file moved, a volume was remounted, an OS update changed how the reference resolves) with no obvious cause at that point. `AudioAnalysisRepository.refreshBookmarkIfStale(_:mode:)` (`ROADMAP.md` D8/T8.5) is the dedicated check: `nil` when the bookmark is still current, or a freshly-regenerated replacement when it isn't. Every Use Case that resolves a previously-persisted bookmark (`GenerateWaveformPeaksUseCase`, `GenerateWaveformDetailUseCase` — anything taking an already-imported `AudioAsset`, not a fresh `URL`) calls this first and persists a non-nil result back onto `Project.audioAsset.securityScopedBookmark` before proceeding. `ImportAudioUseCase` never needs this — it always mints a brand-new bookmark from a live, user-just-selected `URL`.

**Security-scoped bookmark creation can fail entirely — the plain-bookmark fallback.** Found during real-machine manual import testing (`ROADMAP.md` D8, post-completion correction — see `docs/DECISIONS.md`): `url.bookmarkData(options: .withSecurityScope, ...)` can itself throw (`NSCocoaErrorDomain` code 256, "Could not open() the item," with no underlying error at all) for a URL that otherwise works completely normally — `startAccessingSecurityScopedResource()` succeeds, ordinary reads succeed, and even a *plain* (non-security-scoped) bookmark succeeds against the exact same `URL`, in the same call, moments apart. This was investigated exhaustively before being treated as unfixable at the app level: URL identity/call-ordering through the full `.fileImporter` → `AudioAnalysisRepositoryImpl.importAudio` chain, entitlements vs. embedded signature, App Translocation, TCC-protected-folder nesting (the test file living inside `~/Desktop/...`), App Sandbox enforcement itself, and `.fileImporter`'s own configuration were all individually verified clean. What's left matches a real, documented macOS defect in the security-scoped-bookmark subsystem (some machines/OS states only) — not a bug in this app's logic, and not something a retry or a different call sequence can route around.

`AudioAsset.bookmarkAccessMode` (`BookmarkAccessMode` enum: `.securityScoped` / `.plainFallback`) exists to make this honest rather than silently masking it. `ImportAudioUseCase`'s underlying `importAudio(from:)` always attempts a real security-scoped bookmark first — that's the only kind that reliably survives an app relaunch under App Sandbox. Only if that creation attempt itself throws does it fall back to a plain bookmark, tagging the resulting `AudioAsset` as `.plainFallback`. A `.plainFallback` bookmark is genuinely usable for the remainder of the *current* app session (the sandbox extension granted at import time is still live), but — unlike `.securityScoped` — **is not guaranteed to still grant access after the app relaunches**; every downstream consumer of `securityScopedBookmark` (`generateWaveformPeaks`, `generateWaveformDetail`, `refreshBookmarkIfStale`) resolves/regenerates it using plain (non-`.withSecurityScope`) options whenever `bookmarkAccessMode == .plainFallback`, never assuming the security-scoped shape unconditionally. The import screen surfaces this to the user directly and honestly rather than as either a silent success or a hard failure: "This file's access may need to be re-selected after restarting the app."

### 4.11 `AnalysisSettings`

App-level audio-analysis defaults, nested under `Settings.audioAnalysisDefaults` (§4.7) rather than flat fields on `Settings` — kept as its own type so it can be passed directly as a parameter to `DetectCuesUseCase`/`AudioAnalysisRepository` without those APIs depending on the whole `Settings` type. This section is the implementation *contract* for `ACAudioKit`'s silence/level detection (`ROADMAP.md` D8) — concrete enough that those Tasks have an unambiguous target, without prescribing the actual DSP code (window-size tuning, exact statistic used for noise-floor estimation, etc. remain implementation detail within this contract).

**Detection approach: windowed RMS level, not instantaneous/peak sample values — refined by a second, SuperFlux-based stage for cue *starts* only.** Audio is analyzed in fixed-length windows (`analysisWindowMilliseconds`), computed every `analysisWindowHopMilliseconds` — overlapping whenever the hop is smaller than the window length, which it is by default; see "RMS time resolution and threshold-crossing interpolation," below, for why window length and hop are two separate parameters — computing each window's RMS level in dBFS via `Accelerate`/vDSP (per `CLAUDE.md`'s "no hand-rolled sample loops" rule). A window is classified silent if its RMS level is below the effective threshold (see calibration, below). Peak/instantaneous-sample thresholding is deliberately not used — a single loud transient sample (a click, a digital pop) would otherwise misclassify an entire otherwise-silent window, and RMS-over-a-window is the standard, more stable technique for gap/silence-gate detection. RMS-threshold detection is stage 1 of a two-stage pipeline: it locates the *candidate region* for each boundary. Stage 2, **SuperFlux-based onset refinement**, then pinpoints the precise moment within that region — see "SuperFlux-based onset refinement," below, for why RMS alone isn't sufficient for every real case and how the two stages combine; "Why offset detection does not use SuperFlux or any onset-detection technique," below, for why this stage is never applied to cue *ends*; and "RMS time resolution and threshold-crossing interpolation," below, for what makes the RMS mechanism itself precise enough to meet the 1-frame target for cue ends without a SuperFlux-equivalent second stage.

**Threshold: manual vs. automatic.** Both are supported, switched via `noiseFloorCalibrationMode` — not an either/or product decision, because a single fixed dBFS threshold across arbitrarily different source recordings (a quiet studio mix vs. a location recording with real room noise) is fragile. In `.manual` mode, `silenceThresholdDb` is used exactly as configured, unchanged for the whole file. In `.automatic` mode, the threshold is computed continuously via **Local Peak-Relative Calibration (LPRC)** — see immediately below. `silenceThresholdDb` plays no role in `.automatic` mode at all, including as a fallback: LPRC never substitutes a fixed absolute value anywhere.

**`.automatic` is the default as of 2026-09-10 — real, multi-fixture evidence, not a preference call.** A real accuracy investigation (`docs/DECISIONS.md`, 2026-09-10) found that no single fixed `.manual` value could correctly serve both a normally-mixed file and a significantly quieter one (e.g. music mixed down as a background bed) with the same threshold — confirmed across four real gain tiers of the same source content (unshifted, `-6`, `-12`, `-24`dBFS), where every fixed candidate tested measurably degraded on the quietest tier even as it improved the others. `.manual` remains fully supported and is the right choice for a project where a specific, known threshold is deliberately wanted — it is not the default because it structurally cannot adapt to a mix's own loudness the way `.automatic` does.

**`.automatic` mode's calibration mechanism — Local Peak-Relative Calibration (LPRC) — replaced the original fixed-cadence leading-window-minimum scheme entirely on 2026-09-22 (`docs/DECISIONS.md`).** The original mechanism (a leading 2.0s sample window, re-measured every `noiseFloorReestimationIntervalSeconds`, an implausible-jump sanity check against the previous interval) is gone, not merely retuned. **Four rejected fix attempts, and the root defect they all failed to solve:** that mechanism calibrated a *minimum* — a noise floor — which pinned to `RMSWindowStream.epsilonClampDb` (`-180.0dBFS`) the instant a leading window happened to land on genuine digital silence, and — because the implausible-jump guard then rejected every subsequent real reading as too-shallow-relative-to-the-pinned-anchor — could never legitimately recalibrate upward again for the rest of the file (confirmed on real production fixtures, `docs/DECISIONS.md`, 2026-09-11 and 2026-09-18: two false merges and one false positive on one file, and −7.94s to −28.99s systematic early onsets dominating nearly an entire 65-minute file on another). Four mechanisms tried to fix this by substituting a different *level* for the floor-pinned reading — a percentile-based floor statistic, N-consecutive-interval confirmation, a fixed-constant fallback, a whole-file-median fallback (Provenance-Tracked Anchor Calibration) — and all four failed the same way: a real file can contain both genuine bit-exact digital silence between cues *and* genuine quiet-but-real dips within a cue (confirmed as low as `-28.164dBFS` on one real fixture), and no single absolute substitute number, however derived, can correctly separate both when their real dB ranges overlap in the same file. See `docs/DECISIONS.md`'s full calibration-floor-pinning thread (2026-09-10 through 2026-09-22) for the complete, real-evidence record of all four rejected mechanisms.

**LPRC never computes a substitute level for the whole file or the whole interval — it computes a *ceiling*, continuously, per measurement.** For every measurement at time `t`, `localPeakDb(t)` is the maximum RMS-in-dBFS reached anywhere within `localPeakRadiusSeconds` of `t`, in *either* time direction — `SilenceDetectionStage1` already operates on the complete in-memory measurement array as a pure function, not a streaming stage, so a symmetric/lookahead window costs nothing extra. The effective main threshold is `localPeakDb(t) − activityMarginDb`, clamped to never fall below `RMSWindowStream.epsilonClampDb` (a local peak that has itself decayed to the epsilon floor means nothing real is nearby, so true digital silence there must still always classify as silent — the clamp is a correctness fix for this exact boundary case, found and fixed during validation, not an aesthetic choice). A local *maximum* cannot floor-pin the way a minimum does: it only reads near the epsilon floor when the entire surrounding neighborhood genuinely is silent, which is exactly the case where that is the correct answer. The moment any real content appears within `localPeakRadiusSeconds`, `localPeakDb(t)` reflects it immediately — no fixed-cadence lag, no implausible-jump rejection (nothing to reject: a rising maximum is never implausible the way a leading-window minimum landing in content was). `activityMarginDb` is a *relative* margin applied against each local passage's own measured ceiling, never an absolute value competing with real content — the same nominal margin means a very different effective dBFS threshold for a loud passage than for a quiet one, automatically, with no mode-internal branching.

**A depth-relative threshold alone still isn't sufficient — real duration data (`docs/DECISIONS.md`, 2026-09-22) shows a second, independent signal is needed.** A real inter-cue gap that sits at a genuinely quiet (not bit-exact-silent) ambient floor can be only as deep, relative to its own neighboring cue's peak, as a real brief-but-deep within-cue dip elsewhere in the same file — depth alone cannot always tell them apart. **Duration does:** real evidence across the validated fixture set shows a genuine inter-cue gap sustains continuously below the LPRC threshold for many seconds (9+ seconds in the real case that motivated this), while a real within-cue dip — even an unusually deep one — sustains for at most ~2.3 seconds. `automaticModeSilenceDurationSeconds` (default `2.6`s) replaces `minimumSilenceDurationSeconds` for LPRC's main-gap closure specifically, chosen from real data to sit inside a real but narrow window — above the deepest real false-dip duration found (`2.35`s) and below the shortest real genuine-gap duration found (ECHTE_SCHWEIZER's own shortest real cue-to-cue gap, `3.15`s of actual bit-exact silence). **This window is real but thin, built from exactly two boundary data points across the entire validated fixture set, not a wide statistical margin — flag and re-validate this value the moment a future real fixture has either a genuinely short hard-cut gap (approaching `2.7`s) or an unusually long within-cue near-dropout (approaching `2.9`s).** `.manual` mode is completely unaffected and keeps using `minimumSilenceDurationSeconds` exactly as before.

**`.automatic` mode's own tail mechanism, `AutomaticModeScanner` — a batch, two-pass redesign, not the real-time race `.manual` mode's `Stage1Scanner` still uses, and re-enabled after a real, working iteration through two failed intermediate designs (`docs/DECISIONS.md`, 2026-09-22, has the complete history).**

The original real-time race (main-duration at the shallow threshold vs. tail-cap-duration at a deeper one, whichever condition is satisfied first in scan order) doesn't carry over correctly once the main threshold is itself already deep (LPRC, not a shallow fixed/floor-pinned value): a real validation case (SEA_STEM cue6, a `-119.29dBFS` within-cue dip) closed a false gap via the tail-cap branch's shorter `0.5`s bar even after `automaticModeSilenceDurationSeconds` was raised specifically to protect against it, and disabling the branch entirely — the first fix tried — fixed that but then undershot real long-lingering tails by up to 8 seconds on other real fixtures (a real regression against the already-documented baseline, not a net improvement).

The mechanism that actually works, validated against real trajectory data on multiple real fixtures:

1. **Pass 1 — classify every below-`mainThreshold` run by its own full, lookahead-computed extent**, not by how quickly a fixed duration is reached from its start: a run shorter than `automaticModeSilenceDurationSeconds` in total is never a real gap, full stop, regardless of how deep it gets. This is what keeps a real, sustained-but-brief within-cue dip (confirmed real case: a genuine musical diminuendo-and-recover reaching `-156.56dBFS` and returning to normal level within ~100ms) from ever triggering the tail-cap branch, at *any* `automaticModeTailToleranceDb` value — structurally excluded before depth is even considered, not by tuning a margin deep enough to miss it.
2. **Pass 2 — within a run already confirmed real, search for the earliest point where the signal sustains continuously below `automaticStricterThreshold` (`mainThreshold − automaticModeTailToleranceDb`) for longer than `tailCapSeconds`, but only within `automaticModeTailSearchBoundSeconds` of the main-threshold crossing** — falling back to the main crossing itself if no such point exists that early. **This bound is load-bearing, not a tuning nicety**: real trajectory data across multiple real fixtures (TWBS, ECHTE_SCHWEIZER) shows the main threshold's own crossing already lands within ~0-2s of the true perceptual end in every real case checked; large real overshoots (confirmed up to `+15.46s` on one real cue) came entirely from searching for a deep confirmation that, for a tail sitting on an extended quiet-but-not-silent plateau (real observed plateau durations: `~5`-`16s`), never arrives until true digital silence. `0.5`s was the smallest bound tested that still let every genuine fast/steep real decay (crossing both thresholds within ~1s) qualify unchanged, while making every observed long-plateau case correctly fall back to the already-accurate main crossing — confirmed to bring every affected real cue's offset accuracy to at or beyond its documented pre-LPRC baseline, not merely "better than the intermediate broken state."

**Minimum Audible Confirmation (MAC), `.automatic` mode only.** A coarse, region-level plausibility gate, not a per-sample silence boundary: a detected region is discarded unless it reaches `minimumAudiblePeakDb` (default `-80.0dBFS`) somewhere within its own span. This closes a narrow, specific gap LPRC's depth-relative threshold alone leaves open — an isolated transient that never gets anywhere near an audible level can still register as a standalone region, because its own excursion contaminates its own local-peak reference (confirmed real case: a SEA_STEM transient peaking at `-96.7dBFS`, independently confirmed inaudible by direct listening, registered as a spurious detected region under LPRC alone). **Deliberately a dedicated field, not a reuse of `silenceThresholdDb`** — an earlier design draft proposed reusing `-40.0dBFS` directly, reasoning it was already validated as "clearly real vs. clearly not." Real validation caught this as wrong before it shipped: `-40.0dBFS` is exactly the fixed `.manual`-mode threshold `.automatic` mode's own default change (2026-09-10) exists to beat, and a real `-50dBFS` mixed-down cue — which `.automatic` mode must keep detecting — would itself never reach `-40dBFS`, so reusing it would silently regress an already-shipped guarantee. `-80.0dBFS` sits with real margin below the quietest legitimate cue level validated so far (`-50dBFS`) and above the one confirmed-inaudible artifact this gate exists to catch (`-96.7dBFS`) — again a real-but-thin, two-point evidence band, not a wide margin; re-validate if a future fixture has a legitimate cue quieter than this or a spurious artifact louder than it.

**Ambience/room tone vs. silence.** The system does not attempt to semantically distinguish "quiet music" from "room tone" — both present identically to a level-based detector as continuous energy above the noise floor, and telling them apart is a *content-identity* question ("is this actually a musical work?"), not a signal-detection one. This is deliberately left to human review, not solved at the DSP layer: every detected boundary produces a `Cue` with `source == .detectedFromAudio` (SPEC.md §4.3), always user-confirmable/editable/deletable before export, never auto-finalized. The one signal-side mitigation is `minimumCueDurationSeconds`: a short blip of room tone bounded by two genuine silence gaps, too brief to plausibly be a musical work, is discarded rather than promoted to a spurious candidate `Cue`.

**RMS time resolution: hop size and threshold-crossing interpolation — closing the gap between the 50ms window and the 1-frame target.** "Boundary accuracy target," below, requires locating a boundary within 1 frame of the project's configured `Setup.timecodeFrameRate` — between roughly `33.3`ms (`.fps30`/`.fps29_97NonDrop`/`.fps29_97Drop`) and `41.7`ms (`.fps24`) depending on frame rate. Taken at face value, `analysisWindowMilliseconds`'s `50.0`ms default is coarser than this target. For cue *starts* this doesn't matter in practice — SuperFlux's stage 2 (below) relocates the boundary directly from the spectrogram, at `superFluxHopSeconds`'s own `10`ms time resolution (see "SuperFlux hop size and reported-boundary resolution," below) — finer than the RMS window's `50.0`ms — so stage 1's own precision is masked by stage 2 regardless. **For cue *ends* it matters completely**, because offsets have no equivalent second stage (see "Why offset detection does not use SuperFlux or any onset-detection technique," below) and are finalized entirely by this RMS mechanism — so the RMS mechanism's own resolution *is* the offset-accuracy budget, with nothing downstream to correct for it. Two additions, both plain RMS/energy-domain techniques — consistent with offsets deliberately staying off any onset-detection-family (spectral/novelty) technique — close this gap:

1. **Hop size, decoupled from window length.** `analysisWindowHopMilliseconds` (default `10.0`) sets how often a new RMS window is computed, independent of `analysisWindowMilliseconds` (the window's *length*, unchanged at its `50.0`ms default). Windows overlap whenever the hop is smaller than the window length, which it is by default — `50.0`ms windows, computed every `10.0`ms, so consecutive windows overlap by `40.0`ms of audio. This is the same frame-length/hop-length decoupling used by any STFT-based technique (SuperFlux's own spectrogram included, above): the window stays long enough to give a stable RMS estimate (this section's original reason for using RMS over instantaneous samples at all), while the hop determines how finely boundaries can be located in time, independent of that stability requirement. At the `10.0`ms default, hop-quantization alone already bounds any threshold-crossing error to at most `10.0`ms — comfortably inside even the tightest 1-frame tolerance (`33.3`ms) with better than 3× margin, before interpolation is even applied.
2. **Threshold-crossing interpolation, not window-quantized reporting.** A crossing is not reported as "the hop-window where the level first crossed" — which would still carry up to one hop's worth of quantization error on its own. Instead, the two RMS measurements straddling the effective threshold (the last window still on one side, the first window on the other) are linearly interpolated *in the dB domain* to locate the crossing instant between their window-center timestamps: `t_cross = t₁ + (thresholdDb − db₁) / (db₂ − db₁) × hop`. Interpolating in dB, rather than in linear amplitude, is deliberate: an exponentially-decaying amplitude envelope — the physically realistic shape of a reverb/release tail — is linear in dB by construction over any span short relative to the decay's own time constant, which one `10.0`ms hop comfortably is for any audible tail. This interpolation applies uniformly to every RMS threshold crossing this contract defines — the main `silenceThresholdDb` gap boundary and the stricter `silenceThresholdDb − tailToleranceDb` reverb-tail-truncation crossing ("Reverb tails," below) both use it, not just one of them.

Together, hop reduction alone already clears the tightest 1-frame tolerance with margin; interpolation removes the residual, hop-bounded quantization error rather than leaving it as a worst-case bound, and keeps the mechanism robust even if a project is ever configured with a coarser custom hop. This is a real, previously-unresolved gap this pass closes, not a restatement of an already-solved problem: before this addition, the RMS mechanism as originally specified — a 50ms window with no documented hop or interpolation — could not have reliably met the 1-frame target for cue ends, which have no downstream stage to correct for it the way SuperFlux corrects for it on cue starts.

**Performance note.** A `10.0`ms hop against a `50.0`ms window means roughly 5× more RMS windows computed than a naive non-overlapping (`hop == window`) implementation over the same file — on the order of ~1 million windows for a 3-hour file, each a small, `Accelerate`/vDSP-computed RMS over a bounded sample range read through the existing streaming reader (`ACAudioKit/Streaming`, per `CLAUDE.md`'s "never load a full file into memory" rule). This is well within the bounded-chunk, vDSP-vectorized architecture `CLAUDE.md`'s Performance Considerations already require, and doesn't change the kind of performance-budget test T8.3 already documents, only the specific budget number confirmed at implementation time. The same finer hop also incidentally sharpens the sustained-duration checks (`minimumSilenceDurationSeconds`, `minimumCueDurationSeconds`) — not the motivating reason for this change, but a consistent side benefit rather than a regression.

**SuperFlux-based onset refinement (stage 2, cue-*start* boundaries only — precise timing, not a semantic classifier).** RMS-threshold detection has a specific, known weakness: for a cue that fades in gradually or is mixed in deliberately quiet, there is no single clean moment where the level crosses any threshold, since the level ramps up by construction — wherever the threshold sits, the crossing point is somewhat arbitrary relative to where a human editor would actually place the cue's start, and tends to land later than the true onset.

Plain spectral flux (frame-to-frame change in FFT magnitude spectrum) is the standard MIR fix for this, but it has a specific failure mode that matters directly for this app's real material: film-score audio leans heavily on sustained strings, legato brass/woodwind swells, and vocal lines, and natural vibrato/tremolo in exactly this material produces small frame-to-frame spectral fluctuations that plain spectral flux reads as a sequence of spurious onsets — the note never actually re-attacked, but its energy wobbled slightly in frequency and amplitude, and a naive frame-to-frame difference can't tell the two apart. Stage 2 therefore uses **SuperFlux** specifically (Böck & Widmer, "Maximum Filter Vibrato Suppression for Onset Detection," DAFx 2013), an enhancement of plain spectral flux that adds an explicit vibrato/tremolo-suppression step — a maximum filter across neighboring frequency bins — before computing the frame-to-frame difference. The paper's published result is up to a 60% reduction in false-positive onsets on solo string and sung-vocal material specifically, without missing genuine onsets — precisely the instrumentation this app's real-fixture library and real-world usage are dominated by. SuperFlux is used here in preference to plain spectral flux as a specific, targeted fix for a failure mode this app's actual material triggers, not as an interchangeable "spectral flux, tuned differently."

**Signal chain, step by step, computed only within the stage-1 candidate region** (bounded by `superFluxRefinementSearchWindowSeconds` on either side of the stage-1 boundary — SuperFlux is never run over a whole file, only this bounded window, keeping stage 2's cost proportional to the number of candidate boundaries, not file length):

1. **Windowed STFT, then log-frequency-scaled magnitude spectrogram.** The candidate region is framed and transformed via STFT using a **Hann window**, computed every `superFluxHopSeconds` (default `0.01`s, `10`ms) — matching Böck & Widmer's own reference SuperFlux implementation, and standard practice for general-purpose spectral analysis of this kind. The window choice is a deliberate, stated choice, not an unspecified default: SuperFlux's novelty function operates on coarse, ~24-bands-per-octave log-frequency energy (step below), not on resolving closely-spaced sinusoidal partials at fine frequency resolution — the concern a different window family (e.g. a narrower-main-lobe/lower-sidelobe choice tuned for partial-tracking) would actually matter for. The resulting magnitude spectrogram is then mapped onto a logarithmic frequency scale via a triangular filterbank, at the paper's reference resolution of **~24 filter bands per octave**. This is documented here as the reference design point, per this section's convention for values that are precise-in-the-literature but implementation-confirmed at build time (the same treatment already given to the noise-floor-estimation statistic, above): the actual resolution used is confirmed at `ROADMAP.md` T8.3 implementation time, and this section is updated with what was chosen and why if it ends up differing from 24 bands/octave. Logarithmic (rather than the STFT's native linear-Hz) frequency spacing is what makes step 3's max filter operate over musically meaningful, roughly semitone-scale neighborhoods instead of arbitrary linear-Hz ones — vibrato/tremolo wobble is a roughly constant *musical* interval regardless of the note's absolute pitch, so a fixed bin-count neighborhood only suppresses it correctly on a log-frequency scale.
2. **Logarithmic magnitude compression.** Each filterbank output is compressed as `Y = ln(1 + γ·|X|)` (paper reference: `γ = 1`), the standard spectral-flux-family step that stops a handful of very loud bins from dominating the frame-to-frame difference computed in step 4 — a quiet secondary onset next to a loud sustained note would otherwise be invisible in the novelty function without this compression.
3. **Maximum filter across neighboring frequency bins — the vibrato/tremolo-suppression step.** For each frame, each bin's compressed magnitude is replaced with the maximum value found within a `superFluxMaxFilterBandwidthBins`-wide neighborhood of bins centered on it (default `3`: one neighboring bin on each side). Vibrato/tremolo shifts a note's energy slightly up/down in frequency and amplitude from one frame to the next without a new musical event occurring; taking the max across a small bin neighborhood means that small shift no longer registers as an *increase* relative to the previous frame's max-filtered value, because the previous frame's max-filtered value already "saw" the nearby energy the wobble shifted into. This is the entire mechanism that makes SuperFlux different from plain spectral flux — every other step in this chain is standard spectral-flux machinery.
4. **Half-wave-rectified frame-to-frame difference — the novelty function.** The novelty value at frame `n` is `Σ_k HWR(Y(n,k) − Ymax(n−1,k))`, where `Y(n,k)` is the (non-max-filtered) compressed magnitude at frame `n`, bin `k`; `Ymax(n−1,k)` is the max-filtered compressed magnitude from the *previous* frame, bin `k`; and `HWR(x) = max(x, 0)` half-wave-rectifies the difference, so only *increases* in energy contribute to the sum. Summing the rectified per-bin differences across all bins produces one novelty value per frame. Only increases counting toward the novelty value is deliberate and load-bearing, not an arbitrary simplification: an onset is, by definition, an increase in spectral energy, and this same property is exactly why the technique family is unsuitable for offsets — see "Why offset detection does not use SuperFlux or any onset-detection technique," immediately below.
5. **Adaptive local peak-picking.** Within the search window, every frame that is a local maximum on the novelty function is tested against a *locally adaptive* acceptance threshold — not a single fixed global sensitivity value — described in full in "Adaptive local peak-picking," immediately below. **Among the frames that pass, the earliest one (in time order) becomes the refined boundary** — not the highest-novelty one (corrected 2026-09-22; `docs/DECISIONS.md` has the full account). This is a refinement policy, not a from-scratch detection policy: stage 2 only ever narrows an already-roughly-known stage-1 candidate, and real fixture data showed "highest novelty in the whole window" is the wrong rule for that job — real music's energy/complexity typically *builds* just after a true onset, so a later, louder, unrelated event routinely outscored the true onset's own transient under the old rule.

**SuperFlux hop size and reported-boundary resolution.** The refined boundary is reported at whichever novelty-function frame the accepted peak (step 5) lands on — a discrete frame selection, not a continuous crossing the way the RMS mechanism's threshold crossing is, so there is no equivalent "point between two measurements" for a linear-interpolation step to locate. That makes `superFluxHopSeconds` (table, above) the entire quantization budget for stage 2's reported time, the direct SuperFlux-side analogue of what `analysisWindowHopMilliseconds` is for the RMS mechanism (2026-08-13). At the `0.01`s (`10`ms) default, this bounds quantization error to at most one hop — comfortably inside even the tightest 1-frame tolerance (`33.3`ms at `.fps30`/`.fps29_97NonDrop`/`.fps29_97Drop`) with better than 3× margin, the same order of margin the RMS mechanism's hop-only bound achieves before its own dB-domain interpolation is even applied. **Unlike the RMS mechanism, no second, interpolation-style step is added on top here.** A standard analogous technique exists in the onset-detection literature — parabolic/quadratic interpolation of the novelty peak across its immediate neighboring frames, fitting a small curve to locate a sub-frame peak position — and would tighten this bound further, but it is deliberately not adopted now: the existing >3× hop-only margin already clears the target with room to spare, so there is no presently-known gap for it to close, unlike the RMS case, where hop alone left no interpolation-free path that also handled a fully-custom, potentially coarser project hop. Per `CLAUDE.md` rule 7, this is added later only if the real-fixture hard-case tier (`ROADMAP.md` T8.3) ever finds the plain hop-bound margin insufficient in practice — not spawned speculatively now alongside a margin that already clears the bar.

**Adaptive local peak-picking — stage 2's direct parallel to stage 1's own local-peak-relative calibration.** A single fixed global sensitivity value has the same category of limitation LPRC already exists to solve for stage 1 (above): the novelty function's baseline level and variance genuinely differ between a dense, loud passage and a sparse, quiet one, so one fixed value can't be well-tuned for both — too permissive and it over-triggers during busy passages (re-litigating exactly the vibrato/tremolo false-positive problem the max-filter step above already suppresses, via a different failure path), too strict and it misses real onsets during quiet ones. Peak acceptance is therefore made **locally adaptive**, per standard onset-detection practice (Bello et al. 2005, already cited above; consistent with the broader onset-detection-novelty-function family's standard adaptive-threshold approach): a candidate frame `n` is accepted only if both hold —

1. **Local maximum:** `novelty(n) ≥ novelty(n−1)` and `novelty(n) ≥ novelty(n+1)`, with at least one strict inequality (so a flat run of equal novelty values can't repeatedly qualify as "a peak").
2. **Clears the local adaptive threshold:** `novelty(n) > median(novelty, window) × superFluxAdaptiveThresholdMultiplier + superFluxAdaptiveThresholdOffset × peakNoveltyInSearchWindow`, where `median(novelty, window)` is the median novelty value over a window of length `superFluxAdaptiveThresholdWindowSeconds` centered on frame `n`, and `peakNoveltyInSearchWindow` is the single highest novelty value anywhere in the current stage-2 search window (`superFluxRefinementSearchWindowSeconds`) — the fixed reference `superFluxAdaptiveThresholdOffset`'s fraction is taken against, per that field's definition in the table above.

To give frames near the search window's own edges a well-formed, non-truncated local median rather than an asymmetric one computed from fewer samples than frames nearer the center get, the novelty function is actually computed over the search region padded by `superFluxAdaptiveThresholdWindowSeconds / 2` on each side — a small, still-bounded extension of stage 2's cost (proportional to one search window per candidate boundary, per "Signal chain," above — never a whole-file computation), not an exception to that boundedness.

**`superFluxOnsetSensitivity` is retired outright, not kept alongside these three fields.** A single global sensitivity value and a locally-adaptive threshold are two different, non-composable models of the same decision (accept vs. reject a candidate peak) — keeping both would leave it ambiguous which one actually governs acceptance, or require them to somehow combine, neither of which is a real design worth having. The adaptive threshold is the strictly more capable replacement (it degrades gracefully to a roughly-fixed threshold on a novelty function with genuinely uniform baseline level and variance, which is exactly the case a fixed global value was already adequate for), so there is no case where the old field was doing something the new fields can't.

**This does not replace stage 1 and does not run standalone** — it only ever refines a boundary stage 1 has already roughly located, narrowing an arbitrary level-crossing point down to the actual moment of musical/spectral change. **Fallback:** if no candidate frame clears the adaptive threshold anywhere within the search window (e.g. a steady tone with no meaningful spectral change crossing the RMS threshold), stage 2 leaves the stage-1 boundary unchanged rather than relocating it to a spurious or arbitrary peak — the same "fall back to the simpler, already-defined behavior when refinement is inconclusive" pattern `noiseFloorCalibrationMode`'s automatic-mode fallback already establishes, above.

**Scope, deliberately and permanently bounded to cue starts.** This stage refines *silence→sound* (cue-start) boundaries only, where SuperFlux's onset-detection strength directly applies. See "Why offset detection does not use SuperFlux or any onset-detection technique," immediately below, for cue *ends* — a structurally different problem this stage is never applied to, by design, not by current omission.

**Explicitly out of scope: speech/music discrimination and any ML-based/trained classification.** This app's audio imports are music-only — never dialogue or sound design — so there is no music-vs-speech ambiguity for `SilenceDetector` to resolve, and no classifier of any kind is needed. This was a real technique considered during the research that led to adding spectral-flux-based refinement, and deliberately ruled out as inapplicable to this app's actual input material — not an oversight. See `docs/DECISIONS.md`, 2026-08-13, for the full record of both the addition and this scope boundary.

**Why offset (cue-*end*) detection does not use SuperFlux, plain spectral flux, or any onset-detection technique — a permanent architectural boundary, not a gap to fill.** Step 4 above half-wave-rectifies away energy *decreases*, keeping only increases, because that is definitionally what an attack transient is — this is not an arbitrary choice that could simply be flipped for offsets. Applying the same class of technique to find where a cue *ends* has two options, and both fail: dropping the rectification turns the novelty function into a generic "any spectral change, in either direction" detector, which loses the entire vibrato-suppression benefit this design exists for (a vibrato-driven energy *decrease* would then false-positive exactly like an unsuppressed increase would); inverting the rectification to look specifically for *decreases* still fails, because the largest spectral/energy decrease in a decaying musical passage occurs at the **start** of the decay — the moment the direct sound stops and the mix transitions into its reverb/release tail — not at the point the tail has decayed into inaudibility, which is where a human editor actually marks a cue's end. Flux-based novelty functions would therefore reliably mark cue ends too early, at the reverb-tail's onset rather than its perceptual end. This is a documented, structural limitation of onset/flux-based methods applied to offsets, not something tunable away by adjusting sensitivity or search-window parameters: general onset-detection surveys treat offset detection as a substantively different, less-developed problem not solved by the same techniques — see Bello, Daudet, Abdallah, Duxbury, Davies & Sandler, "A Tutorial on Onset Detection in Music Signals," *IEEE Transactions on Speech and Audio Processing*, 2005, cited here as a general onset-detection tutorial that makes this onset/offset distinction, not as a dedicated offset-detection study (no such study is being cited as if it were one).

Offset detection instead uses — confirmed here, explicitly, as the correct and unchanged approach — the existing two-threshold reverb-tail mechanism described in "Reverb tails," immediately below. That mechanism deliberately isn't a spectral/novelty technique at all: it tracks the same windowed-RMS values stage 1 already computes — now interpolated to sub-hop precision per "RMS time resolution and threshold-crossing interpolation," above, so lacking a SuperFlux-equivalent second stage doesn't mean lacking adequate time resolution — applying a second, *stricter* absolute-dB reference level than the main `silenceThresholdDb` gate, so a slowly-decaying tail can't extend a cue's measured end by an implausible amount, while a tail that decays into and stays in genuine silence is still correctly absorbed into the preceding cue's duration. Whichever comes first ends the candidate-tail state: (a) the level has stayed continuously below the stricter reference (`silenceThresholdDb − tailToleranceDb`, i.e. `tailToleranceDb` further down than the main threshold) for longer than `tailCapSeconds` — both already numerically defined in the table above (`6.0` dB, `0.5` s) — at which point the cue's end is hard-truncated to the point that stricter threshold was first crossed; or (b) the level rises back above the stricter reference before either condition is met, which is effectively a new onset — in which case the provisional tail-truncation candidate is simply abandoned and ordinary stage-1 sustained-silence logic continues, absorbing the region back into the ongoing cue rather than truncating anything, since it never sustained qualifying silence. This two-threshold design is a deliberately simple, non-adaptive proxy for a decaying reference curve tracking the tail's energy — not a continuously-adaptive envelope follower modeling the tail's actual decay shape, which "Reverb tails," below, already rules out as "a much harder DSP problem than this contract calls for" — and it remains, unchanged by this pass, the correct mechanism for offsets specifically.

**Stated plainly, for any future session: onset and offset detection are two genuinely different problems, solved by two different mechanisms, in this codebase.** Don't "simplify" this by unifying them onto one shared detector — doing so would silently reintroduce the "cue ends land at the reverb tail's onset, not its perceptual end" failure this section exists to rule out.

**Reverb tails.** This is the mechanism that governs cue *ends* — see "Why offset detection does not use SuperFlux or any onset-detection technique," above, for why this two-threshold approach, not a spectral/novelty technique, is the deliberate and permanent choice for offsets. A decaying tail after a musical passage ends can sit above a naively-chosen threshold for a while, which would otherwise delay gap detection and push a cue's measured end later than where the audible "music" really stopped. Two things bound this, deliberately without attempting perceptual/spectral tail modeling (a much harder DSP problem than this contract calls for):

1. Because a boundary requires *sustained* silence (`minimumSilenceDurationSeconds`) rather than a single below-threshold instant, a tail that decays into real silence and stays there is naturally absorbed into the *preceding* cue's measured duration — its end boundary sits at the start of the qualifying silence run, tail included. This is treated as correct, not a bug: the tail was audibly part of that work's use.
2. To stop a slowly-decaying tail from extending a cue's measured end by an implausible amount, a second, stricter threshold applies during a candidate tail: if the level has been continuously below `silenceThresholdDb − tailToleranceDb` (i.e. `tailToleranceDb` further down than the main threshold) for longer than `tailCapSeconds`, the cue's end is hard-truncated to the point that stricter threshold was first crossed — located via the interpolation described in "RMS time resolution and threshold-crossing interpolation," above, not merely rounded to the nearest RMS window — rather than waiting for the full decay to cross the main (less strict) threshold.

**`.manual` mode only, as of 2026-09-22 — see "Local Peak-Relative Calibration," above, for why `.automatic` mode never evaluates this branch at all.**

**`tailCapSeconds` must stay strictly below `minimumSilenceDurationSeconds` — a real correctness requirement, proven here, not a tuning preference.** The stricter-threshold gap tracked by item 2 can only start counting once the signal has *already* dropped below the deeper `silenceThresholdDb − tailToleranceDb` reference — which, during a decaying signal, happens no earlier than the point the ordinary main-threshold gap (item 1) started, since the level must pass through the shallower main threshold before it can reach the stricter one. So at every instant during a candidate tail, `stricterGapDuration ≤ mainGapDuration`, by construction — the stricter gap can never be "further along" than the main gap it's nested inside. Consequently, if `tailCapSeconds ≥ minimumSilenceDurationSeconds`, the main-gap condition (`mainGapDuration ≥ minimumSilenceDurationSeconds`) always resolves at or before the stricter condition (`stricterGapDuration > tailCapSeconds`) ever could — item 2's branch is mathematically unreachable, and every cue end silently falls back to item 1's earlier, shallower truncation point regardless of how the tail actually decays. **This was the app's actual shipped configuration through 2026-09-09** (`tailCapSeconds` defaulted to `2.0`, exactly equal to `minimumSilenceDurationSeconds`'s own `2.0` default) — confirmed dormant not just by this proof but by a real multi-cue fixture file (`docs/DECISIONS.md`, 2026-09-10) where zero of six region ends resolved via item 2 across the whole file, several of which should have. Corrected by lowering the default to `0.5` — comfortably below `minimumSilenceDurationSeconds` with margin against the real per-tail delays observed in that fixture (0.2–1.0s between the main and stricter crossings) — which is what actually makes item 2 a real, reachable mechanism rather than a documented-but-inert one.

**Clarified at D8/T8.3 implementation time, updated 2026-09-22 — this "Reverb tails" subsection describes `.manual` mode's behavior specifically; `.automatic` mode's own tail mechanism (`AutomaticModeScanner`, "Local Peak-Relative Calibration," above) follows the same two-threshold spirit but with its own bounded, batch-lookahead shape, not this section's real-time race.** In `.manual` mode, "the main threshold"/"`silenceThresholdDb`" means the raw field, used directly and unchanged for the whole file — no per-interval calibration exists in `.manual` mode. The stricter tail reference is always `tailToleranceDb` below that value.

As with every detected boundary, this is a starting point for the editor, not a guaranteed-final value — the user can always adjust it.

**Borderline/flickering regions.** A region hovering right at the threshold (classic noise-gate "chatter") is handled by the same sustained-duration requirement as ordinary gap detection (`minimumSilenceDurationSeconds`), not a separate hysteresis threshold — a region must remain classified as silence *continuously* for the full minimum duration to register as a gap at all, which already suppresses single-window or short-burst threshold crossings without a second configurable value.

**Boundary accuracy target: 1 frame, not a fixed time value.** A detected boundary (silence-detected or embedded-marker-confirmed) must land within **1 frame of the project's configured `Setup.timecodeFrameRate`** (§4.9) of the true boundary — expressed in frames, deliberately, rather than as a fixed millisecond/sample number, because one frame is a different duration at different frame rates (§4.9's "Real FPS" column: `1/24s` at `.fps24`, `1/25s` at `.fps25`, `1/29.97s` at `.fps29_97NonDrop`/`.fps29_97Drop`, `1/30s` at `.fps30`) and this is a display-timecode accuracy guarantee, not a signal-processing one. `SilenceDetector` converts this into a sample-count tolerance at run time from the `AudioAsset`'s actual sample rate and the configured `TimecodeFrameRate`'s real FPS (`sampleTolerance = round(sampleRate / realFPS)`) — never a hardcoded sample-count or millisecond constant, since either would silently stop matching "1 frame" the moment a project uses a different sample rate or frame rate than whatever value was hardcoded. See `docs/DECISIONS.md`, 2026-08-12, for why frames rather than fixed time, and for this contract's two-tier test coverage (synthetic clean-transition buffers plus a hand-verified real-audio fixture library covering fade-ins, quiet-under-ambient mixes, and short non-silent gaps — cases a synthetic buffer alone doesn't exercise).

**How each boundary type actually achieves this tolerance.** For cue *starts*, this target is met by SuperFlux's stage-2 refinement (above), which reports the boundary at the novelty function's own `superFluxHopSeconds` frame resolution (`10`ms default) — see "SuperFlux hop size and reported-boundary resolution," above, for the margin arithmetic (better than 3× inside the tightest `33.3`ms tolerance on the hop-quantization bound alone) — comfortably finer than any RMS window's own resolution. For cue *ends*, which have no equivalent second stage (see "Why offset detection does not use SuperFlux or any onset-detection technique," above), this target is met entirely by the RMS mechanism's own resolution — `analysisWindowHopMilliseconds`'s default (`10.0`ms) plus threshold-crossing interpolation, both in "RMS time resolution and threshold-crossing interpolation," above — which together bound RMS-mechanism error well inside even the tightest 1-frame tolerance (`33.3`ms at `.fps30`/`.fps29_97NonDrop`/`.fps29_97Drop`). This was a real, previously-unresolved gap, not an already-solved problem restated: before that addition, a 50ms RMS window with no documented hop or interpolation could not have reliably hit this target for cue ends.

**This is the mechanism's own quantization budget, not a claim that real fixtures land within it.** Confirmed 2026-09-22 (`docs/DECISIONS.md`): on the real, complex multi-instrument-master fixture set, cue-*end* boundaries land within 1 frame of ground truth on only a small minority of real cues (roughly `7`/`85`), essentially unchanged both before and after that date's LPRC/tail-cap mechanism work — the quantization bound above is real and correctly derived, but on real material the *which point gets selected as the tail's end* question dominates final accuracy far more than sub-frame quantization does. This is flagged as its own open, pre-existing gap, not folded into the LPRC/SuperFlux mechanism work it was discovered alongside.

**Combining with embedded markers.** This setting governs raw signal detection only; merging its output with `AudioAsset.embeddedMarkers` is `DetectCuesUseCase`'s job (`ROADMAP.md` D9/T9.1), using `embeddedMarkerMergeToleranceSeconds` from this same settings value so the whole detection pipeline is configured from one place. Rule: an embedded marker is always authoritative. A silence-detected boundary within `embeddedMarkerMergeToleranceSeconds` of an embedded marker is treated as confirming that marker, not as a second, competing detection — it does not produce a separate candidate. Two silence-detected boundaries (no marker involved) within the same tolerance of each other are merged into one.

**Resolved at D9/T9.1 implementation time — a real reading gap the rule above left open, not a parameter change:** the rule above only states what happens when an embedded marker *is* within tolerance of a silence-detected boundary (confirms it) and when two silence-detected boundaries are near each other (merge). It doesn't say what happens to a marker with **no** silence-detected boundary within tolerance at all — a marker sitting inside a continuous non-silent stretch (the exact attacca/segue case that has no silence transition for stage 1 to find in the first place, §4.15/§4.19's "Split and merge" motivation) or inside a genuine silence gap between two detected regions. **Resolution: "an embedded marker is always authoritative" is unconditional, not conditioned on a nearby detected boundary existing** — an unconfirmed marker still produces its own cue-start, exactly as if the user had manually ⌥-clicked to split at that point (§4.15/§4.19): if it falls inside an existing candidate region's span, that region is split at the marker's position, the earlier half keeping the region's own classification up to the marker and a new `.embeddedMarker`-sourced cue beginning exactly at the marker running to the region's original end; if it falls in silence between two regions (or before the first/after the last), it still produces a new `.embeddedMarker` cue, ending at whichever boundary (confirmed marker or detected-region start) comes next, or at the file's total duration if none does. **Two alternatives were considered and rejected:** silently dropping a marker with no nearby detected boundary (rejected — directly contradicts the rule's own unconditional "always authoritative" wording, and defeats the entire reason markers matter most: exactly the segue/attacca case detection structurally cannot find on its own); giving an unconfirmed marker a zero-duration placeholder cue, matching "+ Add Cue"'s default (rejected — needlessly worse than what the surrounding data already implies, when D9's own accuracy bar requires every detected cue to already look plausible before human review, not force a manual extension on first render for a case the app already has enough information to resolve correctly). See `docs/DECISIONS.md`.

**Clarified at D8/T8.3 implementation time:** `SilenceDetector` itself (the raw-signal side of this pipeline, `ROADMAP.md` D8/T8.3) never actually needs to perform the "two silence-detected boundaries... merged into one" step described above. Its own single, sequential forward scan of the RMS timeline produces exactly one boundary instant per qualifying silence↔sound transition, by construction — there is no path within `SilenceDetector`'s own algorithm that could emit two independent candidates for the same physical transition for anything to merge. This sentence describes the shape of the *combined* problem `DetectCuesUseCase` (D9) actually has to solve once embedded markers are in the picture, not a step `SilenceDetector` performs on its own output. `SilenceDetector` accepts `embeddedMarkerMergeToleranceSeconds` as part of `AnalysisSettings` (so the whole pipeline stays configured from one settings value, as this section already states) but does not consume it internally.

**First Frame of Action exclusion — added after D9's own detection-accuracy investigation found real professional-workflow leader material in scope, not a parameter change.** `Setup.timecodeStart` (§4.2) already defines where the imported audio's own timeline sits relative to the film's absolute timecode. Nothing previously stopped a detected or embedded-marker-derived candidate from landing before **First Frame of Action** — `10:00:00:00`, the industry-standard FFOA convention marking where the actual programme begins — even though nothing can exist before the film itself starts: real production audio always carries a 2-pop, sync tone, or leader material before FFOA, never real music, and a 2-pop's own embedded cue point is a common real case. `DetectCuesUseCase`'s `FirstFrameOfActionExclusion` step (applied to its combined, embedded-marker-merged output, immediately before persisting — never to `SilenceDetector`'s own raw regions, which stay audio-file-relative and FFOA-agnostic by design, consistent with `Cue.startTimecode` never absorbing `Setup.timecodeStart` anywhere upstream of display, per the TC In/TC Out rule above) excludes or truncates accordingly:

- **A candidate whose entire span (`Setup.timecodeStart.offsetSeconds + cue.startTimecode.offsetSeconds` through its own end) falls before FFOA is never constructed as a `Cue` at all.** This is the pure leader/2-pop/sync-tone case — real, but definitionally not music.
- **A candidate that straddles FFOA (starts before it, ends at or after it) is truncated to start exactly at FFOA, not dropped outright.** Found to be a real case, not a hypothetical, during this investigation (`docs/DECISIONS.md`, this date): one real fixture's detected region began a few milliseconds before FFOA while running ~70 seconds past it, almost entirely real music matching the fixture's own hand-verified ground truth. Dropping the whole region under an exclude-only rule would have silently deleted that real content; truncating preserves it while still guaranteeing no `Cue` ever starts before FFOA.
- **Applies uniformly regardless of source — `.detectedFromAudio` and `.embeddedMarker` candidates alike.** "An embedded marker is always authoritative" (above) resolves *which real candidate wins* when detection and an embedded marker compete; it was never meant to admit material that's categorically not music. A 2-pop's own embedded marker is excluded/truncated by this same rule, not exempted by that authoritativeness.
- **FFOA (`10:00:00:00`, `36000.0` seconds) is hardcoded — never `Setup`-configurable.** Only `Setup.timecodeStart` varies per project; the FFOA convention itself does not. `10:00:00:00` has `0` frames, so this comparison is exactly frame-rate-independent, the same property `Setup.timecodeStart`'s own default (`09:59:52:00`) already relies on.
- **No-op when `Setup.timecodeStart` is `nil`.** With no absolute reference point, there is nothing to exclude or truncate against.
- **Scope: gates only `DetectCuesUseCase`'s own freshly-produced/merged output, on that detection run.** It does not retroactively remove already-persisted cues if `Setup.timecodeStart` is edited afterward (matching the "no migration, no warning" precedent the TC In/TC Out rule above already establishes for that field), and it does not constrain manually-placed cues (`UpdateCueUseCase.add`/split) — a user retains the ability to place a cue before FFOA deliberately, for whatever real reason they might have.

**Re-running detection and manually-adjusted cues.** Re-running `DetectCuesUseCase` warns before discarding any `Cue` not sourced as `.detectedFromAudio` — `.embeddedMarker` and `.manual` cues are protected, `.detectedFromAudio` cues are freely regenerated. This is precise, not incomplete, *because* of §4.19's reclassification rule: the moment a user edits any field of a `.detectedFromAudio` cue (repositioning its `startTimecode`, correcting its duration, anything), its `source` becomes `.manual` as a direct side effect of that edit — so it is automatically protected by this same rule from that point forward, with no separate "was this .detectedFromAudio cue subsequently touched by a human" check required. A `.detectedFromAudio` cue the user has looked at and left unchanged is still freely discardable on re-run, which is correct: the user hasn't actually confirmed or corrected anything about it yet.

**Known gap:** this schema doesn't yet support a per-import override distinct from the app-wide default (e.g. "use different silence settings for this one unusually noisy production"). `ImportAudioUseCase`/`DetectCuesUseCase` can already accept an `AnalysisSettings` value directly at the call site without a schema change — whether that becomes user-facing UI (persisted per-`Project` vs. one-shot per-run) is a product decision for `ROADMAP.md` D9 (Cue Detection), not resolved here.

### 4.12 Referential Integrity for `Person`/`Label` (delete guard)

`Party.person(Person.ID)` / `.label(Label.ID)` are bare `UUID` references into `Project.people`/`Project.labels` — there is no SwiftData `@Relationship` cascade/nullify behind them (Domain-layer types don't know about SwiftData at all; see `CLAUDE.md`). Without an explicit rule, deleting a `Person`/`Label` that's still referenced would silently orphan every place it's used, with no compiler or runtime error.

**Rule: deletion is blocked, never cascaded, never nulled, whenever a reference exists.**

A dedicated Use Case — `DeleteRightHolderUseCase`, exposing `deletePerson`/`deleteLabel` methods (built at `ROADMAP.md` D3/T3.3, as the shared-Use-Case option this section originally left open) — is the *only* sanctioned way to remove a `Person`/`Label` from `Project.people`/`Project.labels`. Before deleting, it scans every `Party`-typed field reachable from the `Project`, plus `Settings.defaultDeclarant`:

- `Setup.producer`
- `Setup.directorOrPrincipal`
- `Setup.declarant`
- `Settings.defaultDeclarant` (app-level, not project-scoped, but still a live reference)
- every `Cue.rightHolders[].party`, for every `Cue` in `Project.cues`

If any reference is found, the Use Case returns a typed failure listing exactly where:

```swift
enum PartyReferenceLocation: Equatable {
    case setupProducer
    case setupDirectorOrPrincipal
    case setupDeclarant
    case settingsDefaultDeclarant
    case cueRightHolder(cueID: Cue.ID)
}
```

so the calling ViewModel/View can tell the user precisely what to edit first, rather than showing a generic "can't delete" message. Deletion proceeds only once the returned reference list is empty — the user must reassign or remove every reference first. This is a hard block by design: nullifying a required field like `Setup.declarant`, or silently dropping the last remaining entry from a required list like `Setup.producer`, would each create an invalid `Setup`, and cascade-deleting a `CueRightHolder` row would silently break that `Cue`'s 100%-share invariant (§4.6) without the user's knowledge — all are worse outcomes than refusing and explaining exactly why.

### 4.13 `PartyResolver`

Resolving a `Party` value into something displayable (a name, an address) requires looking it up against `Project.people`/`Project.labels` — every screen that shows a right-holder needs this. To avoid that scan-and-match logic being reimplemented slightly differently in every ViewModel, it lives in exactly one place: `PartyResolver`, a stateless, pure (no I/O, no async) type in `ACCore/Models/PartyResolver.swift` — a plain function/namespace, not a Use Case, since it has no Repository dependency and nothing to orchestrate (see `CLAUDE.md` Naming Conventions).

```swift
enum PartyResolver {
    static func resolve(_ party: Party, people: [Person], labels: [Label]) -> ResolvedParty?
}

struct ResolvedParty: Equatable {
    let displayName: String        // "First Last" for a Person, or the company name for a Label
    let address: PostalAddress?    // nil if the referenced Person's address isn't set (Person.address is optional; Label.address is always present)
    let ipiNumber: String?
}
```

Returns `nil` only if the referenced `id` isn't found in either array — i.e. exactly the dangling-reference case §4.12's delete guard exists to prevent. Any caller that hits `nil` here, once §4.12 is correctly enforced everywhere deletion happens, indicates a bug, not a valid state to design UI around.

### 4.14 `Setup.totalMusicRuntime` — Source of Truth and Update Rule

`Setup.totalMusicRuntime` (§4.2) is a single persisted field — there is no separate "derived" shadow value; the field itself is both the exported value and the thing kept in sync. Ownership:

- **Source of truth:** the `Setup.totalMusicRuntime` field, always. It is what gets exported.
- **Update rule:** whenever `Project.cues` changes (add/edit/delete/reorder-with-duration-change) **and** `Settings.autoComputeTotalMusicRuntime == true`, the field is recomputed as `Σ cues[].duration` and written atomically as part of the same mutation — never as a separate, possibly-forgotten follow-up step.
- **Owning Use Case:** `UpdateCueUseCase` (planned for `ROADMAP.md` D10/T10.1) is responsible for triggering this recompute after every Cue mutation it performs. The actual sum logic lives in exactly one place — a pure static helper, `RecalculateTotalMusicRuntimeUseCase.recalculate(cues:) -> MediaDuration` — so it's computed identically everywhere it's needed, never copied.
- **Manual override:** when `Settings.autoComputeTotalMusicRuntime == false`, `UpdateCueUseCase` leaves the field untouched; it can then only be changed via `UpdateSetupUseCase` (an explicit user edit of `Setup` directly).
- **Toggling the setting:** flipping `autoComputeTotalMusicRuntime` from `false` → `true` immediately triggers one recompute via the same helper (invoked from the settings-update path, e.g. `UpdateSettingsUseCase`), so the field can't be left stale after re-enabling auto-compute. Flipping `true` → `false` leaves the current value as-is — it simply stops being overwritten going forward.

This resolves the original derived-vs-stored ambiguity by making the calculation a single, named, reusable piece of domain logic invoked from exactly two call sites (Cue mutation, settings toggle) — not two independent implementations of the same sum.

### 4.15 `WaveformPeaks` and `WaveformPeakBucket`

Resolves a gap flagged in an earlier revision of this document: `CLAUDE.md`'s folder structure names `ACDesignSystem/Components/WaveformView`, but nothing in the schema or the audio pipeline (`ROADMAP.md` D8) produced any data for it to render. This section is that missing piece.

**Representation: a fixed-size, downsampled min/max peak array — never raw or full-resolution sample data.** For each of a fixed number of time buckets spanning the whole file, `WaveformPeaks` stores the minimum and maximum normalized sample amplitude reached in that bucket. Min/max-per-bucket (not average/RMS) is the standard waveform-rendering technique specifically because it preserves visible transients (a single sharp peak) that an averaging approach would smooth away.

| Field | Type | Notes |
|---|---|---|
| `id` | `UUID` | |
| `audioAssetID` | `AudioAsset.ID` | which `AudioAsset` this summarizes |
| `resolution` | `Int` | bucket count; fixed at `4096` for the persisted overview (see below) |
| `buckets` | `[WaveformPeakBucket]` | length always equals `resolution` |

**`WaveformPeakBucket`:**

| Field | Type | Notes |
|---|---|---|
| `min` | `Float` | normalized amplitude, `-1.0...1.0` |
| `max` | `Float` | normalized amplitude, `-1.0...1.0` |

Conformances (both types): `Equatable`, `Hashable`, `Sendable`. No `Codable` — see `CLAUDE.md`, "Domain Model Value-Type Conformances."

**Memory bound.** `resolution` is fixed regardless of file length — a 3-hour file and a 3-minute file both produce exactly 4096 buckets. At 2 × `Float` (8 bytes) per bucket, the persisted overview is `4096 × 8 = 32,768` bytes — trivially safe to hold fully in memory or persist, independent of source file size. This is what lets `WaveformPeaks` exist as a plain `ACCore` value type without violating the "never load a full WAV into memory" constraint, the same way `AudioAsset`'s metadata-only invariant does (§4.10).

**v1 simplification: mono mixdown, not per-channel.** Multi-channel source audio is summed to a single mono trace before peak extraction. A dual-trace (or per-channel) stereo waveform display is a real, plausible future enhancement, but not designed as part of this change — see §6.

**Generation.** `ACAudioKit`, behind `AudioAnalysisRepository` — the same layer and protocol responsible for everything else audio-related, per `CLAUDE.md` rule 3 ("new audio analysis techniques are added inside `ACAudioKit`, behind the existing `AudioAnalysisRepository` protocol"). Computed via the streaming reader (`ACAudioKit/Streaming`) in bounded chunks: each chunk contributes to whichever bucket(s) its sample range maps to, via a vDSP min/max reduction (`vDSP_minv`/`vDSP_maxv` or equivalent) per `CLAUDE.md`'s "no hand-rolled sample loops" rule — never a second, separate full-file read distinct from the pass import/analysis already performs.

**Ownership and lifecycle: generated once, automatically, right after import.** `GenerateWaveformPeaksUseCase` (`ACCore/UseCases/`) runs immediately after `ImportAudioUseCase` completes, producing the fixed-resolution overview and persisting it to `Project.waveformPeaks` (§4.1) — not lazily generated on first view, so the editor's waveform is never shown mid-computation for a file the user already finished importing.

**Progressive rendering for long files: two-tier, not a single resolution and not a full mip-map pyramid.**

1. **Overview** — the persisted `WaveformPeaks` described above, one fixed 4096-bucket summary of the entire file. This is what renders the full-timeline view. For a 3-hour file, 4096 buckets means roughly 2.6 seconds per bucket — coarse, but that's expected and correct for a full-file overview; it's not meant for boundary-level precision.
2. **On-demand detail** — when the editor UI is zoomed into a specific time range (e.g. adjusting a cue boundary) **via `WaveformView`'s own horizontal-zoom gesture, `ROADMAP.md` D9/T9.3** (this section previously assumed a zoom trigger existed without specifying where it lived or what actually invoked it — that gap is closed by T9.3's zoom mechanism, below), `GenerateWaveformDetailUseCase` computes peaks for just that visible range, at a resolution supplied by the caller (driven by the actual pixel width of the zoomed-in view, not a fixed constant). This is deliberately **not persisted or cached** — a bounded time-range read via the streaming reader is cheap even against a 3-hour source file, and caching zoom-dependent results would be speculative complexity for a cost that's already negligible (see §6 for this as an explicit non-goal, not an oversight).

A full multi-resolution mip-map (as some professional DAWs build) was deliberately not designed — two tiers (bounded overview + on-demand bounded detail) covers this app's actual editing workflow (confirm/adjust cue boundaries, not sample-accurate waveform editing) without the added complexity of maintaining a resolution pyramid.

**What `WaveformView` (`ACDesignSystem`) itself consumes.** Per `CLAUDE.md`'s Design System rules, `ACDesignSystem` has zero knowledge of domain types — so `WaveformView` never takes a `WaveformPeaks` directly. It takes a design-system-local, domain-free `WaveformDisplayData` (defined in `ACDesignSystem`, not `ACCore`) — the same "local adapter struct" pattern already established for `CueTableView`'s row protocol. A Feature-layer mapper (in `ACFeatures`) converts `WaveformPeaks`/detail-region buckets into `WaveformDisplayData` at the point a screen renders it. See `CLAUDE.md`, Design System section, for the adapter type's shape.

`WaveformView` also has an **interactive mode** — cue-boundary markers overlaid on the waveform, draggable to reposition a `Cue`'s `startTimecode` — used for manual cue correction (§4.19). This still takes no domain type: boundary positions cross the component boundary as plain `Double` offsets via closures (e.g. `onBoundaryDragged: (Int, Double) -> Void`), with the `ACFeatures`-layer mapper converting to/from `Timecode` at the call site, same as the display-only path above. `ROADMAP.md` D9/T9.3 is where `WaveformView` is actually built — it wasn't previously scoped as a buildable component anywhere in the roadmap despite being named in `CLAUDE.md`'s folder structure since the project's first commit.

**Horizontal (time-axis) zoom — now explicitly scoped, `ROADMAP.md` D9/T9.3.** `WaveformView`'s interactive mode gains a zoom gesture (trackpad pinch, plus +/− controls as a fallback) that narrows/widens the visible time range — the actual trigger the "on-demand detail" tier (above) always assumed existed without specifying where it lived. Crossing the `ACDesignSystem` boundary follows the same closure-based, domain-free pattern as the drag gesture: a plain `visibleRangeSeconds: ClosedRange<Double>` value, never a domain type. That state is owned by a new `ACFeatures`-layer `CueDetectionReviewViewModel` — not `WaveformView` itself, consistent with `CLAUDE.md`'s MVVM rule that Views hold no business/orchestration state — which calls `GenerateWaveformDetailUseCase` for the narrowed range once it passes the point the persisted overview can no longer usefully serve it, at a resolution driven by the view's actual pixel width, and maps the result to a replacement `WaveformDisplayData` via the same adapter pattern the overview tier already uses. **A boundary marker's drag-offset math must be computed against the current `visibleRangeSeconds` window's pixel-to-time mapping, not the full-file range, whenever zoomed in** — an implementation that keeps using the full-file mapping while zoomed would silently reposition a dragged boundary to the wrong offset, by exactly the zoom factor's error, with no visible sign of failure short of checking the resulting `Timecode`. See `ROADMAP.md` D9/T9.3's dedicated Acceptance Criterion for this specifically, and `docs/DECISIONS.md`, 2026-08-14, for why this was added as a scope correction ahead of D9 rather than discovered mid-implementation.

**Horizontal pan — the necessary complement to zoom, found in the same review that found zoom itself missing (`docs/DECISIONS.md`, 2026-08-14).** A zoom control with no way to move the visible window afterward is incomplete: once `visibleRangeSeconds` is narrower than the file's full duration, `WaveformView` gains a pan mechanism that shifts that same range left/right at **constant width** — a two-finger trackpad scroll as the primary gesture (the idiomatic macOS convention for panning a zoomed view), plus click-and-drag on empty waveform background as a mouse-compatible fallback, mirroring zoom's own "primary gesture + fallback control" shape (pinch + buttons). **Disambiguation from the pre-existing boundary-marker drag — both are horizontal drags on the same component:** a drag gesture that starts within a boundary marker's hit-region is *always* treated as marker-reposition, by hit-testing precedence, never pan, regardless of zoom state; and once a marker-drag is in progress, a concurrent pan input (e.g. a scroll event arriving mid-drag) is ignored for the duration of that drag rather than being allowed to interleave. A **grab-cursor affordance** (open hand while idle over a zoomed, non-marker area; closed/grabbing while actively panning) is shown only when `visibleRangeSeconds` is narrower than the file's full duration *and* the pointer isn't over a marker's hit-region — no affordance at all while unzoomed, since there's nothing to pan (the same cursor-communicates-affordance pattern `ROADMAP.md`'s D6 hover-cursor fix already established in this codebase). Panning is clamped so `visibleRangeSeconds` can never extend past `[0, fileDuration]`. **Panning into a not-yet-fetched time range triggers the same debounced `GenerateWaveformDetailUseCase` call zoom-narrowing already does** (above) — sliding the window is not exempt from needing on-demand detail merely because its width didn't change.

**Vertical (amplitude) zoom — a pure rendering transform, no new data.** `WaveformView` also gains a vertical-scale control (e.g. a corner slider) that multiplies each drawn peak's height by a `verticalScale: Double` gain factor at draw time, applied directly against `WaveformPeakBucket`'s existing normalized `-1.0...1.0` `min`/`max` values (above) — no new field, no repository/Use Case involvement, and no interaction with the horizontal-zoom/on-demand-detail mechanism described above. **Deliberately ephemeral, per-screen state** — held locally by `WaveformView`/its host, reset to a default scale every time the view is reopened, never persisted to `Project` or `UserDefaults`. This was confirmed directly with the project owner rather than assumed either way (`docs/DECISIONS.md`, 2026-08-14), and mirrors other purely-visual, non-business UI state elsewhere in this app (e.g. `AppState.selectedSection`, `CLAUDE.md`'s Document & Window Model) rather than being treated as data worth saving.

**Split and merge — two more `WaveformView` gestures, closing the attacca/segue gap detection structurally cannot solve (`docs/DECISIONS.md`, 2026-08-14).** Two musical works edited back-to-back with no silence between them (a segue/attacca, common in film scoring) produce no candidate boundary for stage 1's silence-gap detection to find at all — there's no silence transition to locate — and stage 2 (SuperFlux) is never run outside a stage-1 candidate region, by design, to keep its cost bounded (§4.11: "SuperFlux is never run over a whole file... keeping stage 2's cost proportional to the number of candidate boundaries, not file length"). Extending stage 2 to scan whole files for internal onsets was considered and explicitly rejected — it would reintroduce exactly the unbounded, file-length-proportional cost that bounded scoping exists to avoid, with high false-positive risk on the sustained, legato material SuperFlux's own vibrato-suppression already works to avoid over-triggering on. **The fix is manual, not automated:**

- **Split** — an **⌥-click (Option-click)** on empty waveform background, strictly within an existing cue's plotted region (between its `startTimecode` and TC Out, §4.3) — never on a marker, never in silence/gap space, never reachable on a cue with no plotted region (`startTimecode == nil`, which has no waveform position to click on in the first place). **Not a double-click** — see "Split's trigger: ⌥-click, not double-click," below, for why this changed from an earlier version of this pass and why a modifier is the right call here specifically. Inserts a new boundary at the clicked time offset, dividing that one `Cue` into two, via a new `split` operation on `UpdateCueUseCase` (`ROADMAP.md` D10/T10.1) — not a new Use Case type, consistent with `UpdateCueUseCase` already owning every other structural `Cue` mutation. **No minimum resulting-segment length is enforced** — deliberate, not an oversight: `minimumCueDurationSeconds` (`AnalysisSettings`, §4.11) exists to reject algorithmically-spurious noise blips from *automated* detection, a different problem from a human *deliberately* marking a short segment; reusing it here would fight the user's explicit intent. The only rejected case is an ⌥-click within `0.001`s — a floating-point-precision epsilon, not a meaningful duration threshold — of either of the cue's own existing endpoints: not a "too short" rule, just excluding the degenerate zero-length-half case. See §4.19's "Split and merge" entry for the exact field-by-field data behavior.
- **Merge** — dragging a boundary marker **vertically off the waveform strip** (past its top or bottom edge — an axis with no existing meaning anywhere in this component, since every other marker-drag interaction here is purely horizontal, so it cannot collide with reposition or pan). Combines that marker's `Cue` with its immediately preceding `Cue`, via a new `merge` operation on the same `UpdateCueUseCase`, **but only when they're genuinely contiguous** — the preceding cue's TC Out within `0.001`s of this cue's `startTimecode`. Deliberately **not** `embeddedMarkerMergeToleranceSeconds` (§4.11's `1.0`s default): that tolerance solves a different, much coarser problem — "are two independently-*detected* boundaries close enough to be the same" — and reusing it here would let a user silently merge across up to a full second of real, audible silence, defeating the entire premise this capability exists for. Dragging a marker with no eligible preceding neighbor (the first cue in the project, or a genuine gap before it) off the strip is a no-op — no merge affordance appears, and the drag cancels on release. See §4.19's "Split and merge" entry for the exact field-by-field data behavior.

**Gesture classification is decided once, not continuously re-evaluated.** A marker-drag is classified the *first* time it either (a) exceeds the waveform strip's vertical bounds — from that point on, horizontal movement is ignored and the gesture resolves to merge-if-eligible-else-cancel-to-original-position on release — or (b) ends while still within those bounds — the existing horizontal reposition behavior, using whatever offset was reached at release. This is a one-time branch, not a reversible state machine: a drag that briefly crosses the vertical bound and comes back is still committed to the merge-or-cancel path, not silently returned to reposition behavior.

**Click-to-play and play-cue-span — closing a separate, equally real gap: hearing whether a boundary is actually right, not just looking at it (`docs/DECISIONS.md`, 2026-08-14).** `WaveformView`'s interactive mode gains two plain-click (no drag, no modifier) behaviors, backed by a new `AudioPlaybackController` (§4.20):

- **Click (no drag) on empty background** — plays from the clicked time offset, with no end bound (runs to the end of the file, or until stopped). Resolves the instant the click completes — no timing-window wait, since (per "Split's trigger," below) nothing else on background competes with a plain, unmodified click.
- **Click (no drag) on a marker's hit-region** — plays that marker's `Cue`'s exact span, `startTimecode` to TC Out, auto-stopping at the end. Resolves immediately — a marker click has no double-click meaning to disambiguate against either, so there's nothing to wait out here.
- Both respect the current `visibleRangeSeconds` window's pixel-to-time mapping whenever zoomed in, the same requirement already stated for boundary-marker drag math, above — a naive full-file-mapping click handler would play from the wrong offset by exactly the zoom factor's error.
- Clicking a new point while already playing seeks and continues, rather than requiring an explicit stop first — the expected behavior for a click-to-audition workflow, not left to be improvised at implementation time.

A **playhead indicator** renders during playback — a separate `WaveformView` parameter (`playheadOffsetSeconds: Double?`, `nil` when not playing), never folded into `WaveformDisplayData`: the playhead updates continuously (many times a second) during playback, while `WaveformDisplayData` is comparatively stable, recomputed only on zoom/pan changes — bundling the two would force needless recomputation of the stable data on every playhead tick. Display-only in this pass — not draggable/scrubbable; that would be a new input gesture beyond what's actually asked for here, not an oversight.

**Split's trigger: ⌥-click, not double-click — reconsidered after the rest of this section was already drafted, and changed for a stated reason, not silently.** An earlier version of this pass specified split as a double-click, on the reasoning that SwiftUI's native double-click recognition doesn't collide with drag-based gestures. That's still true, but it has a real cost this section didn't originally weigh: **every** background click — including the plain click-to-play gesture immediately above, the single most-repeated action in the whole review workflow — would have had to wait out the system's double-click timing window (`NSEvent.doubleClickInterval`, roughly a quarter to half a second) before committing to "this was a single click, not the start of a double-click," to correctly avoid firing play-from-point an instant before a genuine double-click resolved into split. That's a real, repeated tax on the most frequent action in this surface, not a one-time cost — reconsidered and rejected once actually weighed against click-to-play's frequency, not defaulted into by not checking. **⌥-click (Option-click) replaces double-click for split**, freeing plain click for play-from-point with zero disambiguation delay. Three alternatives to double-click were compared before choosing this one — see `docs/DECISIONS.md`, 2026-08-14, for the full comparison against a right-click context menu and a hover-revealed icon affordance, and for why a modifier is the right call *here* even though a modifier was explicitly rejected, twice, for pan-vs-drag and merge-vs-reposition disambiguation elsewhere in this same section: those two already had a modifier-free, self-disambiguating alternative that worked well (drag axis, hit-region); split-vs-click did not — the modifier-free option (double-click timing) is exactly the one with the cost being avoided here, so this isn't the same tradeoff being decided differently, it's a different tradeoff. The ⌥ modifier only matters for **background** clicks (where it disambiguates play-from-point vs. split) — it has no effect on **marker** clicks, which are unambiguous either way and always mean "play this cue's span."

**The full disambiguation set, seven interactive-mode behaviors on one component, stated once:** pinch or the +/− controls → zoom; two-finger scroll, or a click-drag starting on background while zoomed in → pan; a click-drag starting on a marker's hit-region, staying horizontal → reposition; a click-drag starting on a marker's hit-region, crossing the strip's vertical bounds → merge (if eligible, else cancel); a plain click (no drag, no modifier) on a marker's hit-region → play that cue's span; a plain click (no drag, no modifier) on background → play from that point; an ⌥-click (no drag) on background, within a cue's plotted region → split. **Marker hit-region takes precedence for every drag-based gesture** (a drag starting on a marker is always reposition-or-merge, never pan — the precedence rule pan vs. reposition already established, above, extended here to merge); **for click-based (non-drag) gestures, marker hit-region determines meaning rather than precedence** — a click on a marker always plays that cue's span, a click on background always plays from that point or splits, depending on the ⌥ modifier — there's no competing interpretation to arbitrate between at a given target, only between targets. Double-click is no longer assigned any meaning in this component, now that split has moved off it — deliberately left unclaimed, not filled speculatively.

### 4.16 `CueSheetPageLayout` — the shared preview/export layout model

See `CLAUDE.md`'s Export Architecture section for why this exists (in short: the on-screen preview and the exported PDF must be pixel-identical, which requires computing layout exactly once, not twice). **This section describes the mechanism only — it is not itself the WA Film registration form's layout.** As of 2026-09-27, this type backs `ROADMAP.md` D11/T11.2's producer-facing cue sheet PDF (landscape, its own column-based design — §6's Known Gaps entry has the real, evidence-based column/header/footer set), now actually built. That document is confirmed genuinely distinct from the literal SUISA WA Film form, whose own layout is a separate, not-yet-scoped concern (`ROADMAP.md` D12). ### 4.17 `ProgressUpdate` and `OperationProgress<Success>`

The shared progress-reporting shape used by every long-running operation — see `CLAUDE.md`'s "Long-Running Operations: Progress & Cancellation" section for the full rationale and which operations use it.

```swift
public struct ProgressUpdate: Sendable, Equatable {
    public let fractionCompleted: Double   // 0.0...1.0
    public let message: String?             // optional human-readable status
}

public enum OperationProgress<Success: Sendable>: Sendable {
    case progress(ProgressUpdate)
    case completed(Success)
}
```

Both are plain `ACCore` value types (`ACCore/Models/`) — Foundation-only, no dependency on `Progress` (Foundation's KVO-based class) or any other framework. A Repository/Use Case method that reports progress returns `AsyncThrowingStream<OperationProgress<T>, Error>`, where `T` is whatever that operation ultimately produces (`AudioAsset` for import, `[Cue]` for detection, `WaveformPeaks` for the waveform overview, a file `URL` for export).

### 4.18 Cue Deletion: Save Timing, Confirmation, and Undo

Resolves a gap in an earlier revision of this document: `UpdateCueUseCase`'s delete path was specified as a data operation (`ROADMAP.md` D10/T10.1), but nothing specified the save timing this operation actually uses, or the interaction contract around it (confirmation? undo?).

**Save timing: structural cue mutations are never debounced — they save immediately.** `CLAUDE.md`'s "Autosave is debounced, not triggered on every keystroke/edit" rule was written with continuous field-editing in mind (typing a title, adjusting a percentage share) and is correct for that case — debouncing exists specifically to avoid a save-per-keystroke storm. Deleting, adding, or reordering a `Cue` is a different shape of action: discrete, complete the instant it happens, with nothing further to type. Debouncing a delete would mean a deleted row could still exist in persisted state for up to the debounce interval, which is exactly the gap that makes "does Review & Export update immediately" a real question rather than a given. **Resolution:** `UpdateCueUseCase`'s add/delete/reorder operations write through to `ProjectRepository` immediately (still `async`, just not debounce-delayed) — only continuous field-level edits within a `Cue` remain debounced. `CLAUDE.md`'s Performance Considerations section is updated to state this distinction explicitly, not left as a blanket "autosave is debounced" claim that this section would otherwise contradict.

**Live propagation to Review & Export.** Because the delete write is immediate, it republishes into `ProjectRepository`'s live-observation stream (`CLAUDE.md`, "Single Source of Truth") immediately too — `ReviewViewModel`, subscribed to that same stream, observes the updated `Project.cues` (and re-runs `ValidateCueSheetUseCase` against it) without `CueDetectionReviewViewModel` and `ReviewViewModel` needing any direct reference to each other, and without either performing an explicit "refresh." This is verified, not just asserted: `ROADMAP.md` D11 specifies a concrete test constructing both ViewModels against the same fake `ProjectRepository` and asserting the propagation actually happens end-to-end.

**Confirmation: none. Deletion is a direct, single-step action, regardless of how many `CueRightHolder` entries are attached.** A confirmation dialog is the wrong safety mechanism for a common, easily-reversible action — Apple's HIG stance on this (no confirmation for actions with a real, discoverable undo path) applies directly here, and adding one anyway would be redundant friction on top of the undo mechanism below, not additional safety. Deleting a `Cue` deletes its `[CueRightHolder]` entries atomically as part of the same operation — there is no scenario where a `Cue` is deleted but its right-holders survive orphaned, so there's no additional risk from "how many right-holders were attached" to confirm against.

**Undo: yes, via standard ⌘Z, through the environment `UndoManager`.** At the point of deletion, the ViewModel registers an inverse action (re-insert the deleted `Cue`, with its `[CueRightHolder]` entries, at its original index) with the window's `UndoManager` — the standard SwiftUI/AppKit mechanism, not a bespoke undo stack. This is what makes "no confirmation dialog" the correct call rather than a corner cut: the safety net is real and standard, not assumed.

### 4.19 Manual Cue Correction

Resolves a gap in an earlier revision of this document: `AudioAsset.embeddedMarkers` had no editing path, `AudioAsset` is documented as an immutable derived snapshot (§4.10), and nothing let a user correct a detection `DetectCuesUseCase` got wrong.

**Architectural home: correction happens entirely at the `Cue` level. `AudioAsset`/`EmbeddedMarker` are never mutated, and this is not a workaround — it's the correct model.** `EmbeddedMarker` is a factual record of the source WAV file's contents (§4.10); `Cue` is the app's editable interpretation, already built from that raw data plus signal analysis by the time a user would ever want to correct something (`DetectCuesUseCase`, `ROADMAP.md` D9/T9.1, per §4.11's "Combining with embedded markers" merge rule). Once that merge has happened, "correcting a misjudged detection" and "editing a `Cue`" are the same action — there is no separate "marker" concept left to correct independently, and inventing one would duplicate `Cue`'s already-existing edit/delete/add capability (`ROADMAP.md` D10/T10.1's `UpdateCueUseCase`) for no benefit, which is exactly what `CLAUDE.md` rule 7 (no premature abstraction) argues against.

**Four required capabilities remain reachable from the UI** (originally five, then briefly six with reorder — see the removal note immediately below the numbered list for both "Add" and "reorder"):

1. **~~Add a cue the analysis missed entirely~~ — removed as a UI capability at `ROADMAP.md` D10, second round.** Originally a "+ Add Cue" action in `CueTableView`. Confirmed with the project owner and removed: every real cue goes through AutoCue's own detection process, including cues later found to need splitting — split (capability 4, below) already covers every real case that used to motivate a disconnected, position-less manually-added cue, so there is no real scenario left requiring one. `UpdateCueUseCase.add` itself is **not removed** — it stays in `ACCore`, fully correct and tested, simply unreachable from any UI, in case a future revision needs it again. See `docs/DECISIONS.md`.
2. **Remove one the analysis wrongly created.** The exact same delete control specified in §4.18 (the X button in `CueTableView`) — no separate "reject detection" UI. A wrongly-detected cue is simply a cue to delete, like any other.
3. **Reposition a cue's timecode.** Two entry points, both writing through `UpdateCueUseCase`'s existing edit path (which triggers the §4.3 reclassification rule — the cue's `source` becomes `.manual` the moment either is used):
   - **Direct timecode field edit — removed as a UI capability at `ROADMAP.md` D10, second round.** Originally a text field bound to `Cue.startTimecode` in `CueRowDetailView`, formatted/parsed via `Timecode`'s existing `HH:MM:SS:FF` formatting and `init?(components:frameRate:)` parsing (§4.9). Confirmed with the project owner and removed: `CueRowDetailView` is now exclusively the right-holder/"Royalty Split" editor (§4.22), and a start timecode is irrelevant there. `CueDetectionReviewViewModel.startTimecodeChanged`/`saveStartTimecode` are **not removed** — same "kept unused, may be useful later" treatment as capability 1's `UpdateCueUseCase.add` above. The drag-in-waveform entry point below is unaffected and remains the only reachable way to reposition a cue's start.
   - **Drag in the waveform view** — `WaveformView` (`ACDesignSystem`) is extended to render, per cue, up to two boundary markers — a start marker at `startTimecode` and an end marker at the derived TC Out (`startTimecode + duration`) — and support a drag gesture on either. Per `CLAUDE.md`'s Design System rule (components take no domain types, only closures/bindings), the drag interaction crosses the `ACDesignSystem` boundary as a plain callback identifying which cue and which edge (start or end) moved, plus the new offset in seconds — an `ACFeatures`-layer mapper converts the resulting offset to/from `Timecode`/`MediaDuration` at the point it's applied via `UpdateCueUseCase.moveBoundary` (see "Boundary markers: contiguous vs. non-contiguous," below), the same adapter-at-the-edge pattern already established for `WaveformDisplayData` (§4.15). This is genuinely new work — `WaveformView` was named in `CLAUDE.md`'s folder structure from the project's start but never actually scoped as a buildable component anywhere in `ROADMAP.md` until this section — see `ROADMAP.md` D9/T9.3 for where it's now built, including this interactive mode alongside the plain display mode §4.15 already specifies.

   **Whether dragging one cue's edge affects a neighboring cue depends entirely on whether the two are currently contiguous — see "Boundary markers: contiguous vs. non-contiguous," below, for the full model.** An earlier revision of this section said dragging "adjusts only the one cue... it does not automatically ripple onto a neighboring cue's boundary," stated as a permanent scope limit — correct as far as it went for a cue with a real gap on either side, but never actually the complete picture once an independently-draggable end marker existed: two cues that are genuinely touching (no gap) need their shared edge to move together, to preserve the "cues never overlap" invariant a linear medium requires. This is a real, deliberate reversal of that earlier scope limit, not a silent extension of it — see `docs/DECISIONS.md`.
4. **Split a cue the analysis wrongly left as one continuous work, when two adjacent works were actually edited back-to-back with no silence between them (a segue/attacca) — a case detection cannot produce a candidate boundary for at all.** Stage 1 needs a silence transition to find one; stage 2 never runs outside a stage-1 candidate region, by design, to keep its cost bounded — see §4.15's "Split and merge" for the full reasoning, including why scanning whole files for internal onsets was considered and rejected. An ⌥-click on the waveform within an existing cue's region (`ROADMAP.md` D9/T9.3) inserts a new boundary at that point, dividing the `Cue` in two, via a new `split` operation on `UpdateCueUseCase` (`ROADMAP.md` D10/T10.1) — not a new Use Case type, consistent with `UpdateCueUseCase` already owning every other structural `Cue` mutation (add/delete/reorder, above). Exact field-by-field behavior below.
5. **Merge two adjacent cues the analysis (or an earlier split) wrongly separated, when they're actually one continuous work with no real gap between them** — the inverse of split. Dragging their shared boundary marker off the waveform strip (`ROADMAP.md` D9/T9.3) combines them via a new `merge` operation on the same `UpdateCueUseCase`. Exact field-by-field behavior below.

**A sixth capability, reorder, was added at `ROADMAP.md` D10 and then removed as a UI capability again in the same Deliverable's second round, for the same reason "Add" was.** Reorder existed specifically to let a manually-added cue (the now-removed capability 1) move somewhere other than the end of the list, having no `startTimecode`/waveform position of its own to derive an order from. With "+ Add Cue" gone, every cue on `Project.cues` always has a real `startTimecode` (detected, embedded-marker, or split — all three always produce one), so display order is always already correct by position, and there is no real remaining case that needs manual reordering. `UpdateCueUseCase.reorder` and its ViewModel-level wiring are **not removed** — same treatment as `.add`: left in `ACCore`/`ACFeatures`, fully correct and tested, simply unreachable from any UI. If a real need resurfaces, it's a pure array move with no `Cue` field changes and — unlike every other structural mutation in this section — no `source` reclassification, since nothing about the cue itself would be edited. See `docs/DECISIONS.md` for both removals.

**Boundary markers: contiguous vs. non-contiguous.** Every `Cue` with a `startTimecode` has, conceptually, two independently-draggable markers on the waveform: a start marker (`startTimecode`) and an end marker (derived TC Out, `startTimecode + duration`). Whether a boundary between two adjacent cues behaves as one shared point or two independent ones is **not a stored property of either `Cue`** — it is purely a function of the current gap between them, recomputed fresh every time it matters, the same way `merge`'s eligibility check already works (below).

- **Non-contiguous (a real gap exists, > `0.001`s — the same epsilon `merge` uses):** the preceding cue's end marker and the following cue's start marker are two fully independent markers. Dragging one never moves the other. Dragging *away* from the neighbor is unconstrained (aside from the dragged cue's own minimum-length floor). Dragging *toward* the neighbor **clamps at exactly zero gap** — the marker cannot be dragged past the neighbor's current position, and continuing to hold/drag past that point has no further effect. This closes a real, pre-existing gap as a side effect: the earlier single-marker (start-only) drag had no such clamp at all and could already silently produce overlap.
- **Contiguous (gap ≤ `0.001`s):** the two markers are pixel-coincident, hit-tested and dragged as one. Dragging it *away* from the touching position (opening a gap) is a single-cue write — only the cue whose marker was actually grabbed changes, and the boundary becomes non-contiguous per the case above, with no confirmation or separate action required. Dragging it *further into* the neighbor — which, since there's no gap left to consume, would otherwise overlap — instead carries the neighbor's matching edge along by the same amount, in one atomic two-cue write, so both cues shift together and stay exactly touching. Reversing direction mid-drag immediately stops carrying the neighbor (it stays wherever it last moved to) and resumes independent, gap-opening movement of just the originally-grabbed marker.
- **Which branch applies is decided from the gap as it stood before this specific drag gesture began, not from any intermediate position reached mid-drag** — this is why reversal needs no special path-tracking state: the use case re-derives the branch fresh, from actual repository state, at the point the gesture is committed (drag release), and nothing is written to the repository mid-drag. In practice this means a gap can only be clamped shut (never crossed) within one continuous drag that starts non-contiguous — reaching the touching point and continuing to hold produces no further effect for that gesture. To push the now-touching pair further (the atomic case), the user drags again, in a new gesture, which now starts from contiguous. No modifier key, no separate tool mode — every transition described here happens via the same ordinary drag gesture already used for repositioning.
- **A coincident hit at a contiguous boundary resolves to the following cue's start marker** — an arbitrary but deterministic tie-break, chosen to match the marker identity that already existed in the codebase before end markers were added. It has no effect on which *behaviors* are reachable (both directions, both branches above, are available regardless of which of the two coincident markers is nominally "grabbed") — it only determines which cue's `duration`/`startTimecode` field is the one that changes when the gap-opening direction is dragged.
- **A push never cascades past the immediate neighbor.** If carrying a neighbor's edge along (the atomic branch above) would in turn carry it into a *third* cue, the push clamps at that third cue's current position instead of cascading further — matching `split`/`merge`'s existing pairwise-only scope. Only the two cues sharing the boundary being dragged ever move in one gesture.
- **The very first cue's start marker and the very last cue's end marker have no neighbor on that side, ever** — they remain single, independently-draggable markers with no contiguous counterpart possible, clamped only by their own cue's opposite edge (minimum length) and, at the very start/end of the file, the file's own bounds.
- **Registered with `UndoManager` — reversed from this section's original design (2026-09-14).** This section originally read: "Not registered with `UndoManager`. Like the pre-existing single-marker reposition drag (which also registers no undo action), a boundary drag — including the atomic two-cue case — is fully, losslessly reversible by dragging again; nothing is discarded the way merge's field-combination is. This is unlike split/merge, whose registered undo actions exist specifically because their forward direction can discard or combine data a plain re-drag can't recover." That reasoning was technically correct but didn't match how users actually expect ⌘Z to behave in this view: a consistent, universal undo across every mutating gesture, not one that works for delete/split/merge but not dragging — especially given this app's DAW/editor-adjacent target audience's own muscle memory around ⌘Z. See `docs/DECISIONS.md` (2026-09-14) for the full reversal record. Each completed drag (on release, once the resulting write is issued) now registers a real inverse action restoring the affected marker(s) to their exact pre-drag position(s) — one cue for the independent branch, both cues atomically for the contiguous push-through branch, mirroring how the forward drag itself moves them. Same known exception as merge's own undo, below: the restored cue's `source` reclassifies to `.manual` rather than its exact pre-drag value, since the restore routes through the same `edit`-based path every other field-level correction already uses.
- **`UpdateCueUseCase` gains one new operation, `moveBoundary`, not two.** It determines internally, from current repository state at call time, whether the requested move is a single-cue or two-cue write, rather than requiring the caller (`ACFeatures`) to decide which of two operations to invoke. This is a fourth operation alongside `edit`/`split`/`merge`, not a new Use Case type — consistent with `UpdateCueUseCase` already owning every other structural `Cue` mutation.
- **Split's new boundary is not a special case.** The moment `split` creates two cues from one, the new shared edge between them is contiguous (gap = 0, by construction — split never introduces a gap) and immediately behaves exactly like any other contiguous boundary described above, including being pullable apart by an ordinary drag. Nothing about how a boundary was created (originally detected, from an embedded marker, or freshly split) affects how it behaves afterward.
- **Merge is unaffected and still a distinct, deliberate action.** Contiguity alone never merges two cues automatically — `merge` remains reachable only via the existing vertical-drag-off-strip gesture, and still only succeeds when the two cues involved are genuinely contiguous at the moment it's triggered (the same `mergeNotContiguous` check as today). Dragging either the preceding cue's end marker or the following cue's start marker off the strip resolves to the same pair and the same merge call — which side was grabbed doesn't change what merges.

**Split and merge: exact field-by-field behavior — specified explicitly, not left to be improvised at implementation time.**

*Split.* The earlier resulting half keeps the original `Cue.id` and every non-position field unchanged (`title`, `workNumber`, `notes`, `isArrangementOfProtectedOriginal`, `rightHolders`); only `startTimecode` (unchanged) and `duration` (recomputed to end at the split point) describe it. The later half gets a fresh `UUID`; `nil` `workNumber`/`notes`, `isArrangementOfProtectedOriginal == false`; its `startTimecode` is the clicked split offset and its `duration` runs to the original cue's TC Out. **`title`/`rightHolders` are auto-populated per §4.22** (`"ProjectTitle_Score_Cue-N"` plus the project's Composer/Arranger rosters split into their own independent pools), not left empty — corrected at D10, second round, from this section's original "empty title, empty rightHolders" wording, which predated §4.22's auto-population rule. The two halves' spans always exactly reconstruct the original — no gap, no overlap, by construction. **Copying the *original* cue's own title/right-holders onto both halves was considered and rejected:** split's entire reason for existing is that the two halves are usually two *different* musical works, so copying one work's composer/rights onto what's very likely a different work would be a real SUISA-accuracy risk — a worse outcome than the later half getting its own fresh roster-based default (§4.22), which is a materially safer starting point than either an empty or a copied one. Both halves report `source == .manual`, via the existing reclassification rule (§4.3) — split is a `UpdateCueUseCase`-driven mutation like any other. Write-through is immediate, not debounced (a structural mutation, §4.18, like split/merge/delete), and registers an inverse ("merge back") action with the environment `UndoManager`.

*Merge.* The earlier cue's `id` is kept as the merged result's `id`; the later cue's record is deleted — the exact inverse of split's `id` rule. `startTimecode` is the earlier cue's, unchanged. `duration` is the sum of both originals' durations (the merged TC Out equals the later cue's original TC Out). `title`, `workNumber`, and `notes` each follow **one shared rule, stated once: prefer the earlier cue's value if non-empty/non-nil, otherwise use the later cue's** — not a silent pick-one-side rule, since it specifically avoids discarding a real value in favor of a blank one. `isArrangementOfProtectedOriginal` is the **logical OR** of both cues' values (true if either was flagged true) — a deliberately conservative choice: this flag gates a real downstream compliance requirement (`arrangementAuthorizationAttached`, §4.4/§4.6), and silently dropping a `true` is a worse outcome than over-flagging one that turns out unnecessary. `rightHolders` is **the concatenation of both cues' `[CueRightHolder]` lists, verbatim — no deduplication, no automatic reconciliation of the resulting share sums.** Two alternatives were considered and rejected: silently keeping only one side's right-holders (would discard real, plausibly-correct data — merge's entire premise is "these are actually one work," so both sides' entered right-holders are plausibly all real and correct); and a new blocking "reconcile now" dialog (this app has no other blocking-dialog-driven editing flow anywhere — every other validation issue, including the exact "shares don't sum to 100%" case a naive concatenation can produce, is already surfaced non-blockingly via `ValidateCueRightHolderSharesUseCase` and shown wherever per-cue validation state is already displayed, `ROADMAP.md` D10's existing Acceptance Criteria — reusing that already-built mechanism instead of inventing a new one is the direct application of `CLAUDE.md` rule 7). If the combined list happens to duplicate the same `(party, role)` pair from both original cues, that surfaces as an ordinary two-row entry a user can consolidate manually via `CueRightHolderEditorView` (`ROADMAP.md` T10.3) — no different from a user who happened to add the same right-holder twice by hand. The merged result reports `source == .manual`. Write-through is immediate, not debounced, same as split, and registers an inverse ("split back at the original point") action with the environment `UndoManager`.

**Undo losslessness — a real correctness requirement, stated explicitly rather than left implicit.** Merge's forward direction is lossy by design (`title`/`workNumber`/`notes`/`rightHolders` are combined or one side is dropped per the rules above) — its registered inverse action must therefore be a **snapshot-based restore of both original `Cue` records**, not a "computed" reversal that re-derives the discarded side's values from the merge rules, which cannot recover data the forward direction already discarded. Split's inverse is simpler and needs no full snapshot: undo deletes the newly-created second `Cue` and restores the first `Cue`'s pre-split `startTimecode`/`duration` — every other field on the first `Cue` was never touched by split in the first place.

**One field is a stated, deliberate exception to "exactly as they existed," corrected here to match what's actually implemented (2026-09-14), not left overstating it:** `source` on the restored preceding cue reclassifies to `.manual` (SPEC.md §4.3's existing reclassification rule, applied by the same `edit`-based restore path every other field-level correction already uses) rather than being restored to whatever it was immediately before the merge. This is not a new inconsistency — merge's own forward direction already force-sets `source == .manual` unconditionally (above), so a cue that has been through a merge-then-undo cycle shows the same `source` a merge-only cycle would have shown anyway. Every other field — `title`, `workNumber`, `notes`, `rightHolders`, `isArrangementOfProtectedOriginal`, `startTimecode`, `duration` — is restored exactly, including data the forward merge combined or dropped. If `source`-provenance surviving a merge/undo cycle ever becomes something worth preserving (e.g. distinguishing "still `.detectedFromAudio`, never human-touched" from "a human explicitly merged and later undid it"), that needs a restore path that doesn't route through `edit`'s reclassification — not scoped now, since nothing currently depends on it.

**Boundary-drag undo (2026-09-14) follows the same losslessness bar, and the same `source` exception, via the same mechanism.** `moveBoundary`'s undo is a snapshot-based restore of the affected cue(s)' exact pre-drag `startTimecode`/`duration` — one cue for an independent move, both cues (via two sequential `edit` calls, each individually exact) for an atomic contiguous push-through — not a computed reversal. Every field restores exactly except `source`, which reclassifies to `.manual` on restore for the same reason it does for merge's undo above: the restore routes through `edit`'s existing reclassification rule (§4.3), and the forward drag itself already force-sets `source == .manual` unconditionally on every cue it touches (`UpdateCueUseCase.moveBoundary`'s "Boundary markers" entry above), so a drag-then-undo cycle shows the same `source` a drag-only cycle would have shown anyway.

**Where this is reachable from — not the transient detection-progress view.** `CueDetectionProgressView` (`ROADMAP.md` D9/T9.2) is a progress indicator for the duration of the detection run itself; it is not where correction happens, since showing "detection is running" and "let me review what it found" are different moments in the workflow, not one screen. The waveform-based review/correction surface built in D9/T9.3 and the direct-field/table-based editing in D10 are both reached from the Cue Sheet Editor, once `Project.cues` has actually populated — one place to edit cues, not two.

### 4.20 Audio Playback

Resolves a gap found while finalizing D9/D10, not present in any earlier revision of this document: nothing anywhere let a user actually *hear* the imported audio — `AVFoundation` was scoped (`CLAUDE.md`'s Technology Stack table) exclusively for `AVAudioFile`-based streaming **read** (import/analysis), never playback. Checked thoroughly before concluding this — grepped this document, `CLAUDE.md`, `ROADMAP.md`, `docs/DECISIONS.md`, `CONTRIBUTING.md`, `docs/DefinitionOfDone.md`, and `README.md` for any prior mention; none exists. A real product need, confirmed directly: play from an arbitrary point (§4.15's click-to-play), play a specific cue's exact span to verify its boundaries actually *sound* right and not just look right on the waveform, see a moving playhead, and pause/stop.

**A new protocol, `AudioPlaybackController` — deliberately not a `Repository`, and deliberately not using the `OperationProgress<T>` contract.**

```swift
public protocol AudioPlaybackController: Sendable {
    func prepare(securityScopedBookmark: Data, mode: AudioAsset.BookmarkAccessMode) async throws
    func play(from startSeconds: Double, until endSeconds: Double?) async throws
    func pause() async
    func stop() async
    var stateUpdates: AsyncStream<PlaybackState> { get }
}

public enum PlaybackState: Sendable, Equatable {
    case stopped
    case playing(positionSeconds: Double)
    case paused(positionSeconds: Double)
}
```

- **Not suffixed `Repository`, even though it follows the exact same architectural shape as one (a protocol in `ACCore`, implemented by a Data-layer package, injected via `DependencyContainer`).** "Repository" already has a precise, established meaning in this codebase — data CRUD/observation (`CLAUDE.md`, Single Source of Truth) — and playback is a real-time transport-control surface, not that; forcing the suffix would be misleading, not merely inconsistent. It still lives in `ACCore/RepositoryProtocols/` alongside the real Repositories: that folder groups by *architectural role* (a Domain-defined protocol a Data package implements), which this fits exactly, even though its name doesn't match every other resident's suffix.
- **One `play(from:until:)` method, not two.** `until: nil` covers "play from an arbitrary point, no end bound" (click-to-play, §4.15); a real `until` value covers "play this cue's exact span, auto-stop at the end" (marker-click, §4.15) — one parameterized method serving both needs, not two near-duplicates, per `CLAUDE.md` rule 7.
- **Not the `OperationProgress<T>`/`AsyncThrowingStream<OperationProgress<T>, Error>` contract (`CLAUDE.md`, "Long-Running Operations").** That contract's shape — zero-or-more `.progress` events, then exactly one `.completed(T)` — fits a bounded, terminating, result-producing operation (WAV import, waveform generation, cue detection, export). Playback has no such shape: it's indefinite, freely pausable and resumable, and produces no final result value a `Success` type could meaningfully represent. `GenerateWaveformDetailUseCase` already establishes that not every operation needs the full contract (§4.15); this is the same principle for a more structural reason — there's no completion value here at all, not merely "reporting progress would be pointless ceremony." `stateUpdates: AsyncStream<PlaybackState>` is the correct, simpler shape: one small `Sendable`/`Equatable` value type carrying both "is it playing at all" and "where," the same "small precise value type over a loose boolean/tuple pair" preference already established for `ProgressUpdate`.
- **`prepare(securityScopedBookmark:mode:)` reuses `AudioAsset.securityScopedBookmark`/`.bookmarkAccessMode` (§4.10) — no new sandboxed-file-access mechanism.** Called once when the review screen appears; resolves and opens the file a single time, so subsequent `play`/`pause`/`stop` calls operate on an already-open player rather than re-resolving the bookmark and re-initializing on every click. **`mode:` was missing from this method's original signature — a real, previously-unflagged inconsistency, not a late addition for its own sake.** This section was written 2026-08-14, three weeks before §4.10's `.plainFallback` bookmark fallback existed (2026-09-04); nobody revisited this protocol once that fallback landed. Every other consumer of `securityScopedBookmark` (`generateWaveformPeaks`, `generateWaveformDetail`, `refreshBookmarkIfStale`) already takes `mode:` and resolves with plain vs. `.withSecurityScope` options accordingly — without it here, `AudioPlaybackControllerImpl` would have no way to correctly resolve a `.plainFallback`-mode asset's bookmark (which was never created as security-scoped) and would either throw or silently misresolve. Found and fixed during D9 pre-implementation cross-referencing, before `AudioPlaybackControllerImpl` was written — see `docs/DECISIONS.md`.
- **Calling `play(from:)` while already playing seeks and continues — it does not require an explicit `stop()` first.** The expected behavior for a click-to-audition workflow; a naive implementation that requires stop-then-replay, or that spins up a second concurrent player instead of retargeting the existing one, would produce overlapping audio on rapid re-clicking.
- **Backing implementation: `AVAudioPlayer`, not `AVAudioEngine`.** This need — play one already-imported file from an offset, pause/stop, report position — has no real-time mixing, effects graph, or multiple simultaneous sources for `AVAudioEngine`'s heavier API to justify; `AVAudioPlayer`'s `currentTime`/`play()`/`pause()`/`stop()` covers everything here directly, including seeking (`currentTime = X` before `play()`). Bounded-span playback (the `until` case) is a standard poll-and-stop pattern (checking `currentTime` against the bound, calling `pause()` once reached) — no exotic API needed.

**Package placement.** `AudioPlaybackController` (protocol) → `ACCore/RepositoryProtocols/`. `AudioPlaybackControllerImpl` → `ACAudioKit` (the same package that already owns `AudioAnalysisRepositoryImpl`; no new package, no new dependency-graph edge — `ACAudioKit → ACCore` only, as already established). Per `CLAUDE.md`'s Performance Considerations ("ViewModels are `@MainActor`; anything that touches audio I/O is not"), `AudioPlaybackControllerImpl` is not `@MainActor`-bound; its `stateUpdates` stream crosses to the `@MainActor` `CueDetectionReviewViewModel` (§4.15) the same already-established way `OperationProgress` streams cross from background Repository/Use Case calls to `@MainActor` ViewModels.

**No `Cue` mutation, no dependency on `UpdateCueUseCase`.** Unlike split/merge/reposition, playback only *reads* `Cue.startTimecode`/`duration` to know where to play — no new `UpdateCueUseCase` operation, no `source` reclassification, no write path at all. Structurally simpler than every other capability added this pass.

### 4.21 Resuming an Already-Imported Project on Reopen

Resolves a real, previously-unscoped gap flagged during D8's own close-out but never actually closed: nothing anywhere reads `Project.audioAsset`/`.waveformPeaks`/`.cues` back on reopen and routes to the corresponding screen — `AudioImportViewModel.init` (`ROADMAP.md` D8/T8.6) unconditionally starts at `.idle`, so reopening a Project that was fully imported, waveform-generated, and cue-detected in a previous session re-shows the import prompt instead of the review screen, with no way to reach the already-computed data short of re-importing (which would mint a new `AudioAsset`/bookmark and discard `Project.cues` entirely — not a resume, a restart). See `ROADMAP.md` D9/T9.5.

**This is a state machine over three already-existing sibling fields on `Project` (§4.1), not new data.** `audioAsset: AudioAsset?`, `waveformPeaks: WaveformPeaks?`, and `cues: [Cue]` were each already independently optional/emptiable — this section is the first place anything actually enumerates the combinations and defines what each one means for navigation:

| State | Condition | What the Cue Sheet section shows |
|---|---|---|
| `.needsImport` | `audioAsset == nil` | `AudioImportView` (`ROADMAP.md` D8/T8.6) — the import prompt, unchanged |
| `.needsWaveformGeneration` | `audioAsset != nil && waveformPeaks == nil` | Resumes waveform-peak generation alone, against the already-persisted `AudioAsset` — no re-import. See "Partial-import resume," below |
| `.needsCueDetection` | `audioAsset != nil && waveformPeaks != nil && cues.isEmpty` | `CueDetectionProgressView` (`ROADMAP.md` D9/T9.2) |
| `.readyForReview` | `audioAsset != nil && waveformPeaks != nil && !cues.isEmpty` | `CueDetectionReviewView` (`ROADMAP.md` D9/T9.3) directly — waveform and previously-detected cues, immediately |

**Partial-import resume is a real, reachable state, not a hypothetical.** `AudioImportViewModel.importFile(from:)` chains `ImportAudioUseCase` then `GenerateWaveformPeaksUseCase` as two sequential calls within one `Task` (`ROADMAP.md` D8/T8.6); `ImportAudioUseCase` persists `Project.audioAsset` as part of its own completion, before the waveform call even starts. A quit/crash/force-terminate between those two steps leaves exactly `audioAsset != nil && waveformPeaks == nil` on disk. Resuming from this state calls `GenerateWaveformPeaksUseCase.generate(projectID:asset:)` directly against the persisted `AudioAsset` — that method already needs only an `AudioAsset`, never a fresh `URL`, since it resolves file access via the asset's own bookmark — with no re-import step and no new Use Case.

**Architectural home: a new coordinator ViewModel, not `AudioImportViewModel` and not `AppState`.** Deciding which of the four screens above to show requires an async read of `Project` state before any of those screens' own ViewModels would even be the right one to construct — this doesn't fit inside `AudioImportViewModel` (whose whole reason to exist is running an import, not deciding whether one is needed) without inverting that type's purpose, and it's architecturally foreclosed from `AppState`, which `CLAUDE.md`'s "Document & Window Model" documents as holding "no business data and no reference to any Repository or Use Case" — this decision is derived directly from persisted `Project` fields, which makes it business data by definition. `CueSheetSectionViewModel` (`ROADMAP.md` D9/T9.5) is that coordinator: constructed once per window, the same "`@State`-held, constructed via a `DependencyContainer` factory in `ProjectWindowView.init`, self-loads asynchronously against `ObserveProjectsUseCase.observeAll()`" pattern `SetupViewModel` already establishes (`CLAUDE.md`'s Dependency Injection Pattern). `ProjectWindowView.detail`'s `.cueSheet` case switches on its exposed resume state, the same architectural shape already used one level up for `setupViewModel.projectNotFound` gating the whole `detail` switch.

**Security-scoped bookmark re-validation needs no new mechanism.** `GenerateWaveformPeaksUseCase`/`GenerateWaveformDetailUseCase` already call `AudioAnalysisRepository.refreshBookmarkIfStale(_:mode:)` before resolving any previously-persisted bookmark (§4.10, `ROADMAP.md` D8/T8.5) — unchanged whether that call happens moments after import or months later on a resumed project. **The `.readyForReview` overview render itself needs no file access at all**, and therefore triggers no bookmark check — `WaveformPeaks` is fully persisted (§4.15), so the initial waveform paints from disk-backed data regardless of whether the bookmark would still resolve. The bookmark is only touched, lazily, the first time the user zooms past the overview's resolution (`GenerateWaveformDetailUseCase`) or plays audio (`AudioPlaybackController.prepare`, §4.20) — both already covered by the existing refresh contract. This is what makes `ROADMAP.md` D9's bookmark-survives-relaunch Acceptance Criterion (deferred from D8) actually exercisable for the first time: before this section, no screen existed that a reopened Project would even route to that could attempt that code path.

**When that lazy resolution genuinely fails (e.g. a `.plainFallback` bookmark that no longer resolves), the failure is surfaced explicitly, not assumed to reach the user automatically.** `CueDetectionReviewViewModel` (`ROADMAP.md` D9/T9.3) exposes an `errorMessage: String?` set on a thrown `GenerateWaveformDetailUseCase`/`AudioPlaybackController` error, displayed via the app's existing `.errorAlert(message:)` modifier — the same mechanism `SetupViewModel`/`RightHolderDirectoryViewModel` already use, not a new one. This is stated explicitly here, rather than left to be assumed automatic, because this exact class of gap — a ViewModel's `errorMessage` set correctly but no View ever binding `.errorAlert` to display it — already occurred once in this codebase (`ROADMAP.md` D7's Status note, `RightHolderDirectoryViewModel`). The displayed message distinguishes this specific case (re-import to restore access) from a generic error string, per `ROADMAP.md` D9/T9.3–T9.4.

### 4.22 Default Cue Title and Right-Holder Auto-Population

Added at `ROADMAP.md` D10, second round, alongside the corrected independent-per-role validation model (§4.6) and the removal of "+ Add Cue"/reorder as UI capabilities (§4.19) — all three land together because a cue is now expected to arrive with a real title and (where a roster exists) a real, already-valid share split the moment it's created, rather than starting blank and needing every field filled in by hand.

**Applies at exactly the two real cue-creation points: `DetectCuesUseCase` (freshly detected/embedded-marker cues, on import and on re-run) and `UpdateCueUseCase.split`'s later half.** Both are genuinely new cues in the sense that matters here — neither inherits an existing title or right-holder list from anywhere. Never re-applied to an already-existing cue later (e.g. if the Setup roster changes after the cue was created) — this is a one-time default at creation, freely editable afterward, the same "computed once, not live-synced" behavior already established for `Setup.totalMusicRuntime`'s inputs elsewhere in this document.

**Default title: `"ProjectTitle_Score_Cue-N"`, a real, persisted value — not a `TextField` ghost placeholder left over an empty `Cue.title`.** `ProjectTitle` is `Setup.title`; `N` is the cue's own 1-indexed position in `Project.cues` at the moment of creation, matching the same display number `CueTableView`/the waveform's "CUE N" label already show. This is a genuine default a user can freely overtype, exactly like any other field — not a hint that leaves the underlying data empty. Chosen deliberately over a lighter ghost-text-only approach: this data feeds a real SUISA declaration, where an empty work title reaching export would be a real compliance problem, not just a cosmetic gap.

**Default right-holders: the project's existing Komponist\*in/Arrangeur\*in rosters (`Person.intendedRoles`, §4.5) are auto-assigned, each as its own independent 100% pool (§4.6's corrected model), with no manual action required.** For a role's roster of `N` people: each gets `100 / N` percent (both `performanceBroadcastShare` and `mechanicalRightsShare`, identically), with the *first-listed* person absorbing any remainder from uneven division — e.g. 3 people → 34%/33%/33%, not 33%/33%/34%. `N = 1` → 100%; `N = 2` → 50/50; `N = 4` → 25% each. Composer and Arranger rosters are drawn from and split completely independently of each other, consistent with §4.6's corrected per-role-pool model — one composer and two arrangers on the same cue auto-populates as 1×100% (composer pool) + 2×50% (arranger pool), never a combined percentage across both. An empty roster for a given role simply contributes nothing — the cue's `rightHolders` list only ever contains what a real roster produces.

**Never auto-populated: Author, Publisher, or Performer — even though `Person.intendedRoles` has an Interpret\*in (`.performer`) bucket of its own.** `PersonIntendedRole` (§4.5) has no Composer/Author distinction and no Publisher case at all — only `.composer`, `.arranger`, `.performer` — and this auto-population deliberately only ever draws from the first two. A person's Interpret\*in roster membership is informational-only (§2.2/§4.4) and never produces an automatic `CueRightHolder` row. Author and Publisher stay exactly as they already were: fully manual, added one at a time via the right-holder editor if and when a real one applies.

**Author is additionally hidden from the right-holder role picker's selectable options — a Presentation-layer detail, not a schema change.** `CueRightHolderRole` (§4.4) is unchanged; the case still exists, and existing data using it round-trips correctly. Only the picker's own list of choosable roles narrows to Composer/Arranger/Publisher/Performer. Out of scope for this document's own stated boundary (§3: "UI flows... are out of scope"), noted here only because it's directly adjacent to the auto-population rule above — full detail in `docs/DECISIONS.md`.

**Correction, D11 planning:** `.performer` was originally hidden from the picker alongside `.author` at D10, then re-enabled — a real, SUISA-accepted cue sheet surfaced during D11 planning showed a populated Interpret*in column for a licensed third-party track, directly contradicting the original hide. Re-enabled unconditionally (every cue). See `docs/DECISIONS.md`.

### 4.23 Royalty Split Editing Model and "Copy Split to Other Cues"

Added at `ROADMAP.md` D10, second round — corrects a real bug in the Royalty Split sheet's original (first-round) editing mechanism and adds one new bulk-editing capability.

**The bug: a live, per-keystroke write-through design clamped/rejected input once a role's pool was already at or over 100%.** The sheet's original design wrote every right-holder field edit (share value, role, party, attachment flag) through `UpdateCueUseCase.edit` immediately or after a short debounce, independently per field, while the sheet was still open. Confirmed with the project owner across three concrete symptoms — an existing share edit that would push a pool past 100% being rejected mid-keystroke; a newly-added right-holder's share fields stuck at 0 and uneditable — all three traced to the same root mechanism: independent, racing per-keystroke round trips against a pool that was already full.

**The fix: right-holder editing is a single local, freely-editable buffer, checked and committed exactly once.** `CueRowDetailView` seeds a local `[CueRightHolder]` array from the cue when the sheet opens; `CueRightHolderEditorView` (`ACFeatures`) is a plain, synchronous editor over that array with no `ProjectRepository`/`UpdateCueUseCase` access, no async, and no debounce — every add/remove/role/party/attachment/share edit is an ordinary in-memory array mutation. **Free numeric entry at all times, for every right-holder's share, regardless of the current running total** — nothing is checked while the sheet is open. `ValidateCueRightHolderSharesUseCase` (§4.6) runs exactly once, when "Done" is pressed, purely to decide whether to show a warning — **never to gate the commit itself, which always happens.** The whole buffer is committed in one write (`CueDetectionReviewViewModel.commitRightHolderEdits`, one `UpdateCueUseCase.edit` call), not one write per field.

**A failing pool shows a clear, non-blocking alert — acknowledging it returns to the same, still-open sheet, not out to the cue list.** Corrected at D10's third round, same date as the §4.6 pool-grouping fix: the alert's "OK" button originally also dismissed the whole sheet, which meant confirming the warning abandoned the edit session with the mistake left unresolved — the opposite of what a warning (as distinct from a hard error) is supposed to let the user do. "OK" now closes only the alert; the sheet, with the buffer's current values intact, stays open so the user can actually fix the pool. The commit already happened before the alert ever shows (the warning is purely informational about already-saved data, per the non-blocking model above) — pressing "Done" again after correcting the values re-validates and, if now valid, closes the sheet normally.

**The alert's message names precisely what actually failed — corrected at D10's fourth round from a fixed, generic string that could be, and was, wrong.** The original message always read "the combined pool, or the Arranger pool, doesn't sum to 100%," regardless of *which* issue `ValidateCueRightHolderSharesUseCase.validate()` actually returned. Confirmed with real runtime evidence: a cue whose shares genuinely summed to exactly 100% in both pools still showed that exact message, because the real, only issue present was `.missingPublishingContractAttachment` on a Publisher row — a checkbox, not a share-sum problem. `CueRightHolderValidationMessageFormatter` (`ACFeatures`) now converts the real issue list into one message per issue — naming the specific pool and its actual total for a share-sum failure, or the specific right-holder's resolved display name (via `PartyResolver`, §4.13) for a missing-attachment failure — and the alert shows **every** issue currently present, not just the first, so a second, unrelated problem is visible in the same pass rather than discovered only after a later "Done" press. A plain, non-View type specifically so this formatting logic has direct unit test coverage, unlike `CueRowDetailView` itself.

**"Copy Split to Other Cues"** — a button in the Royalty Split sheet, left of "Done". Copies the sheet's current right-holder list (including any not-yet-committed local edits — from the user's perspective, "this cue's" split at the moment the button is pressed) onto **every** cue in the project, as a wholesale replace, not a percentage-pattern-only copy: each other cue's own right-holder list is discarded entirely and replaced with an exact copy of the source's. A deliberate, intentional bulk action — it will overwrite cue-specific right-holder differences elsewhere in the project, with no confirmation dialog (mirroring §4.18's "delete is deliberate, no confirmation" precedent) since the action is fully, atomically undoable.

**Undo is a single, atomic action covering every affected cue, not one per cue.** `UpdateCueUseCase.copyRightHolders(projectID:rightHolders:)` and its inverse, `.restoreRightHolders(projectID:snapshot:)`, each write every touched cue in one `ProjectRepository.update(id:transform:)` call. `CueDetectionReviewViewModel.copySplitToOtherCuesRequested` snapshots every cue's pre-copy `rightHolders` and registers exactly one `UndoManager` action restoring that whole snapshot together — one ⌘Z fully reverses the entire bulk copy; ⌘⇧Z re-applies it, via the same alternating-registration pattern already established for delete/split/merge (§4.18/§4.19). Both directions reclassify every touched cue's `source` to `.manual` (§4.3) — consistent with `edit()`'s own unconditional reclassification rule, and matching the one already-accepted asymmetry merge's own undo established: a restore is no less exact than the state the forward operation itself produced, and `source` was never going back to `.detectedFromAudio` after either direction touched a cue.

### 4.24 `WAFormTemplateReference` and the WA Film Form Export Overlay

Added `ROADMAP.md` D12/T12.1–T12.2. Backs the literal, pixel-accurate SUISA WA Film registration form export — genuinely separate from §4.16's `CueSheetPageLayout` mechanism and the producer-facing cue sheet it backs (§3, §4.16).

**AutoCue never bundles or ships SUISA's own form PDF.** Confirmed via `pdfinfo`: the real form has no AcroForm fields (`Form: none`) — it is a flat, non-interactive layout, so "auto-fill" cannot mean native PDF form-filling. Instead, the user imports their own legitimately-obtained copy of both real files (`WA Film 2007-01` main form, `WA Film II 2007-01` continuation form, §2.1) once — via one combined file picker, auto-identifying which selected file is which (`ROADMAP.md` D12/T12.4) — not per-`Project`, since it is the same file reused for every declaration. The export feature then draws `Setup`/`Cue` data as a plain Core Graphics (`CGPDFDocument`/`drawPDFPage`) overlay directly on top of the user's own imported pages, producing a brand-new output PDF; the user's original files are never modified. This sidesteps the redistribution question a bundled copy would raise entirely.

**Storage: a private copy inside AutoCue's own sandbox container, not a security-scoped bookmark to the external file — corrected at `ROADMAP.md` D12/T12.4, reversing this section's original design.** The original design mirrored `AudioAnalysisRepositoryImpl`'s bookmark pattern (§4.10) defensively, assuming the same external-file-staleness risk `AudioAsset` genuinely has applied here too. A real relaunch-survival test on that design actually passed (both bookmarks resolved `.securityScoped` and reopened cleanly after a genuine cold app restart) — but the project owner's explicit requirement was a fully automatic experience with zero *ongoing* dependency on the original external file continuing to exist at its original location, for a document that, unlike `AudioAsset`'s own recording, never legitimately changes. `WAFormTemplateRepositoryImpl` therefore copies both user-selected files into AutoCue's own private Application Support directory at import time and reads from that copy from then on — no bookmark, nothing that can go stale. See `docs/DECISIONS.md` for the full investigation and the real `.fileImporter`-stacking bug this round also found and fixed.

**`WAFormTemplateReference`** (struct, `ACCore/Models/`) — no `id` field (single app-level value, not an entity with independent identity, same shape as `Settings`); pure display metadata now, no bookmark/file-location data at all:

| Field | Type | Notes |
|---|---|---|
| `mainFormFileName` | `String` | the user's original filename, display only |
| `continuationFormFileName` | `String` | same, for the continuation-form file |
| `importedAt` | `Date` | display only |

Conformances: `Equatable`, `Sendable`. No `Codable` — no real feature needs it. Persisted via a new `WAFormTemplateRepository` protocol (`ACCore/RepositoryProtocols/`), implemented by `WAFormTemplateRepositoryImpl` (`ACExport`) — `UserDefaults`-backed for the metadata (the same lightweight, non-`SwiftData` precedent `ProjectWindowFrameStore` already establishes elsewhere in this codebase) plus a fixed, deterministic filesystem location (`WAFormTemplateStorage`, package-internal to `ACExport`) for the real copied files, reached through a proper Domain protocol specifically because both `ACFeatures` (to know whether a template is configured, and to open the real files for its own on-screen preview) and `ACExport` (to render/export) need it. `WAFormTemplateRepository.templateFileURLs()` hands back the real, ready-to-open file URLs — no security-scoped access bracketing is needed around them, since they point inside AutoCue's own sandbox container rather than a user-selected external location.

**Auto-detection: `WAFormTemplateClassifier` (`ACFeatures`), not a second manual "which file is which" picker.** Both files are selected in one `.fileImporter(allowsMultipleSelection: true)` step; each is classified by its own extracted text content (`PDFKit`'s `PDFDocument.string` — a deliberate, explicitly-approved third use of PDFKit beyond this document's existing "in-app preview of an already-generated PDF only" scope: read-only text extraction from a user-*imported* file purely for classification, no rendering/generation involved) checked for "WA Film II"/"Zusätzliche Werke"/"Additional Works" (continuation) versus plain "WA Film" (main form), with the main form's own confirmed, fixed 2-page length as a fallback when text extraction is inconclusive. If either file can't be confidently and distinctly classified, the import is refused with a specific, named error — never a guess.

**Layout mechanism: `CueSheetPageLayout` reused unchanged, overlay-only.** §4.16's own open question (whether the WA form reuses `CueSheetPageLayout`/`CueSheetLayoutElement`/`LayoutRect` or gets its own analogous type) is resolved: reused as-is, with zero `ACCore` changes — the type was already content-agnostic (`{pageIndex, pageCount, elements: [{frame, content: text|rule}]}`). A new `WAFormLayoutComputer` (`ACExport`) computes `[CueSheetPageLayout]` containing **only the dynamic field values** (and checkbox "X" marks, drawn as plain `.text` elements — no new `LayoutElementContent` case needed, since the checkbox square itself is already printed on the background template page). A new `WAFormRenderer` (`ACExport`) draws each computed page on top of the corresponding real template page (`context.drawPDFPage`) rather than reconstructing the form's own labels/boxes/lines from scratch.

**Fixed-position, fixed-capacity layout — a different shape from the cue sheet's dynamic, pack-to-capacity pagination (§4.16).** Every coordinate was extracted directly from the user-supplied real reference PDFs (`pdftotext -bbox-layout` for text-anchored fields, the real vector-drawn checkbox squares' own path coordinates via `pdftocairo -svg` for every checkbox) — not estimated, and not assumed shared between the two documents (the continuation form's own left margin and per-work pitch are genuinely, if only slightly, different from the main form's, confirmed by direct measurement). Real, confirmed structural facts this extraction surfaced, beyond what `docs/DECISIONS.md`'s 2026-09-27 T11.3 checkpoint already established:

- The main form's 5-work capacity really is an uneven 2+3 split across its two pages (not an approximation) — works 1–2 on page 1, works 3–5 on page 2, each work block at a confirmed, fixed 150.48pt vertical pitch (152.2pt on the continuation form).
- **A real, previously-unknown capacity ceiling: each work's right-holder block has exactly 3 blank rows on the physical form.** A `Cue` with more than 3 total non-`.performer` right-holders has nowhere on the real form to go beyond those three — `WAFormLayoutComputer` silently draws only the first 3; `ValidateWAFormUseCase` (`ROADMAP.md` D12/T12.3) surfaces this as a non-blocking, `Settings.shareValidationStrictness`-gated `.cueExceedsRightHolderCapacity` issue, kept strictly separate from `ValidateCueSheetUseCase`'s own issue type so it can never leak onto the producer-facing Review & Export screen, which has no such limit (see `docs/DECISIONS.md`).
- **A second real, previously-unknown ceiling: the continuation-form file itself is finite, not an infinitely reusable single page.** SUISA's own distributed file happens to ship with a fixed number of pre-captioned pages (the copy checked had 5, covering works 6–25 in blocks of 4); nothing in the form's own text indicates this is a SUISA-enforced process limit rather than a property of that specific file. `WAFormLayoutComputer.computeLayout(for:continuationPagesAvailable:)` therefore takes the real, live page count of whatever the user actually imported (via `CGPDFDocument.numberOfPages`, never hardcoded) and silently caps output there; `ValidateWAFormUseCase` surfaces the same ceiling as a non-blocking `.cueCountExceedsFormCapacity` issue, exactly like the one above.

### 4.25 `ComposerProfile` and `IPINumber` — "That's Me" auto-fill

Added ahead of `ROADMAP.md` D15 (Settings), 2026-10-03. The app owner's own composer/right-holder identity — name, real IPI Name Number, address — stored once, app-level, used to auto-fill a new `Person` entry anywhere this same individual is added as a right-holder (`PartyPickerView`'s "That's Me").

**Deliberately narrow — not a general cross-project name-matching system.** A broader "has this exact person already been entered somewhere else" lookup risks a false match between two different people sharing a name, a real concern on a document carrying financial/legal weight. `ComposerProfile` only ever represents this app's own user, confirmed explicitly by them at save time, never inferred.

**`ComposerProfile`** (struct, `ACCore/Models/`) — no `id` field, same "single app-level value, no independent identity" shape as `Settings`/`WAFormTemplateReference`:

| Field | Type | Notes |
|---|---|---|
| `firstName` | `String` | |
| `lastName` | `String` | |
| `ipiNumber` | `String` | always the full, real, validated IPI structure — see `IPINumber` below. Unlike `Person.ipiNumber` (optional, unvalidated free text), a stored `ComposerProfile` never holds a partial/invalid value |
| `address` | `PostalAddress?` | |
| `email` | `String?` | |
| `swissPerformNumber` | `String?` | |

Conformances: `Equatable`, `Sendable`. No `Codable` — `ComposerProfileRepositoryImpl` round-trips individual `UserDefaults` keys per field, the same pattern `WAFormTemplateRepositoryImpl` already establishes, so no real serialization use case exists to justify it (`CLAUDE.md` rule 16). Persisted via `ComposerProfileRepository` (`ACCore/RepositoryProtocols/`), implemented by `ComposerProfileRepositoryImpl` (`ACPersistence`) — `UserDefaults`-backed, reached through the Use Case layer (`ComposerProfileUseCase`) only, never a `SettingsRepository`-shaped dependency (none exists yet; `ROADMAP.md` D15/T15.1).

**`IPINumber`** (`ACCore/Models/`) — the real CISAC IPI Name Number structure, confirmed against independent sources and hand-verified against two real example numbers, not guessed: **11 digits total — the first 9 are the base number, the last 2 are real check digits**, computed by weighting the first 9 digits `[10,9,8,7,6,5,4,3,2]`, summing, reducing mod 101, and (if nonzero) subtracting from 101 mod 100. `IPINumber.isValid(_:)` implements this; `ComposerProfileUseCase.saveProfile` rejects a profile whose `ipiNumber` fails it, before it ever reaches storage — the one real business rule this feature has, enforced in the Use Case (not only the Settings screen's own `canSave` UI gate), since an invalid number here would silently propagate into every future "That's Me" auto-fill.

`IPINumber.grouped(_:)` is a **separate display convention**, not a structural claim — but it must still show every real digit; it must never drop or fabricate one. **Corrected 2026-10-03 — twice the same day, the second time by real evidence, not reasoning (`docs/DECISIONS.md`):** the original version dropped a stored number's first 2 digits (mistaking them for a padding prefix outside the real 9-digit base) and grouped the remaining 9 as `3-2-2-2`, a real, confirmed bug. A same-day interim fix grouped the real 9-digit base `3-3-3` with a hyphenated 2-digit check — reasoned correctly from `isValid`'s own internal structure, but **itself wrong**, corrected the same day once the project owner directly read their own real, previously-submitted, SUISA-accepted cue sheet: it displays its IPI number as `"00386 75 75 00"` — the full, unmodified 11 digits, grouped `5-2-2-2`, **no hyphen and no visual base/check split at all**. `isValid`'s internal 9+2 structure governs validation only; it has no bearing on how the number is displayed. The corrected, real-evidence-confirmed convention: `"00123456789"` → `"00123 45 67 89"`. Promoted here from `ACExport/PDF/CueSheetLayoutComputer+Header.swift` (which now forwards to it) once a second real consumer — the Settings screen's own save-confirmation step, below — needed the identical convention (`CLAUDE.md` rule 7). **Every cue sheet PDF reviewed across D11/T11.2's rounds showed one of the two earlier, wrong formats wherever an IPI number appeared** — see `ROADMAP.md`'s D11 status note for the fresh visual re-confirmation this requires.

**UI entry points, both reached without a new navigation destination:**

- **Settings scene** (`AutoCueApp.swift`'s existing `Settings { }` scene, previously a placeholder) — `ComposerProfileSettingsView`/`ComposerProfileSettingsViewModel` (`ACFeatures/Settings/`). The very first save shows a confirmation step displaying the entered IPI back in `IPINumber.grouped` form before anything is persisted; every later edit saves directly (no confirmation), worded as affecting future "That's Me" entries only — already-created right-holder entries are never retroactively changed.
- **"That's Me"** (`PartyPickerView`, every instance that lists `Person` entries) — shown whenever a profile is on file, regardless of `allowsCreatingNewEntries` (selecting one's own already-confirmed identity is a different action from creating an arbitrary new entry, so it isn't gated by that flag — including for Declarant). Matches by IPI against the project's existing directory first (selects the existing `Person` directly, avoiding a duplicate); only when no match exists does it open the "+ New Artist" sheet pre-filled — visibly and editably, never locked — from the stored profile.

**Fixture scope at this feature's own introduction: zero existing, already-reviewed PDF/XLSX test fixtures needed to change.** Confirmed via a full-repository search before implementation: every placeholder IPI number already in use across existing fixtures (`ProjectFixture`, PDF/XLSX structural tests) was either not subject to real-structure validation at all (`Person.ipiNumber` is free text) or part of `IPINumber.grouped`'s own display-format tests. **That second category did need to change, days later** — once `grouped`'s original format was found to be a real, confirmed bug (above), every test asserting its old output was updated to the corrected expected string, not left passing against a wrong value; see `docs/DECISIONS.md`, 2026-10-03.

## 5. Scope of This Document

This document is now fully self-contained: every domain type referenced anywhere in `CLAUDE.md` (`AudioAsset`, `Timecode`, `TimecodeFrameRate`, `MediaDuration`, `AnalysisSettings`, `PartyResolver`, `WaveformPeaks`, `CueSheetPageLayout`, `OperationProgress`, etc.) is fully specified above in §4, not deferred to an external document. An earlier draft of this project referenced an "original architecture document" for `AudioAsset`/`Timecode`/`AnalysisSettings`; that document does not exist anywhere in this repository's history and has been superseded — §4 above is the sole authoritative source for all domain types going forward.

There is intentionally no separate persisted `CueSheet` type: the exportable cue sheet is the combination of `Setup` + `[Cue]`, assembled on demand by `ExportCueSheetUseCase` — introducing a distinct `CueSheet` model would duplicate data already owned by `Project`.
